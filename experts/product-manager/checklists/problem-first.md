# Problem first

A request arrives as a solution. Accepting it as written is how a team builds
the wrong thing correctly, on time, to specification.

| #   | Check                                                                | How                                                   | Source                                                                 |
| --- | -------------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------- |
| P1  | The problem is one sentence somebody in the room could disagree with | read it aloud; if nobody could argue, it says nothing | —                                                                      |
| P2  | Who has it is a named group, not "users"                             | read the brief                                        | Jobs to be done                                                        |
| P3  | How often it happens is stated                                       | read the brief; "sometimes" is not a frequency        | —                                                                      |
| P4  | What people do today instead is written down                         | ask; there is always a workaround                     | Jobs to be done — the existing solution is the competitor              |
| P5  | What happens if nothing is built is stated                           | ask; "nothing" is a legitimate and useful answer      | —                                                                      |
| P6  | The solution in the original request is separated from the problem   | compare the two; are they the same sentence           | —                                                                      |
| P7  | Assumptions are labelled as assumptions, not stated as findings      | grep for confident claims with no source              | —                                                                      |
| P8  | Any persona has evidence behind it — interviews, tickets, data       | ask where it came from                                | A persona with a name and no evidence becomes a citation by repetition |
| P9  | The evidence is named: how many people, asked what, when             | read the research summary                             | —                                                                      |
| P10 | Interview questions were not leading                                 | read them; "would you use X" is not a question        | Research practice                                                      |

## Why each one

**P4 is the row people skip and the one that sizes the work.** There is always
a workaround — a spreadsheet, a colleague, giving up. What it is tells you how
much pain there is, and it is the baseline anything new gets compared against
whether or not you chose it as one.

**P5** makes "do nothing" a visible option. Most of the time the answer is
uncomfortable and correct, and shipping something is how a team avoids saying
it out loud.

**P10** decides whether P8 and P9 are worth anything. "Would you use a
dashboard?" gets a yes from almost everybody and predicts nothing; "show me
what you did last time this came up" gets the truth.
