# rust-cli — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The fourth `cli` blueprint and the catalog's first Rust anything. It keeps the
shape of `go-cli`, `python-cli` and `node-cli` — the work, the command surface
and the entry point as separate files — and adds what those three left as
findings: an argument is validated by the function that uses it, and a failure
has one type, one message on stderr and a status code that is asserted.

The manifest claims `tier: community` and `provenance: generated`, and
`requirements: [ci, testing]`. It does not claim `cd`, and `overview.md` says
under "What it is NOT for" that there is no release workflow.

## Findings

### 1. No advisory check on the dependency graph — `low`

- **Where:** `blueprints/rust-cli/setup.md:357` (step 9, the generated CI
  workflow)
- **Standard:** NIST SSDF SP 800-218 v1.1, **RV.1** (identify and confirm
  vulnerabilities on an ongoing basis); OWASP Top 10:2025 **A03 Software
  Supply Chain Failures**
- **What:** the workflow formats, lints, tests and builds. Nothing compares
  `Cargo.lock` against the RustSec advisory database.
- **Why it matters:** clap is pinned exactly (`=4.6.7`), which is the right
  default for reproducibility and the wrong one for hearing about a fix. With
  an exact pin, a patched clap does not arrive by `cargo update`; somebody has
  to be told. Today nothing tells them.
- **Fix:** a scheduled `cargo audit` or `cargo deny check advisories` job in
  the generated workflow. Not added here: either tool is a further pinned
  install and fetches the advisory database from outside the package
  registries, and the recipe could not run it. Recorded as the first thing a
  real project adds, and the exact-pin trade-off is stated in `overview.md`.

### 2. `Cargo.lock` is produced by the recipe rather than shipped — `low`

- **Where:** `blueprints/rust-cli/setup.md:429` (step 11)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** step 11 runs `cargo generate-lockfile`, which records whatever
  versions and checksums crates.io served that day for everything under
  clap. From then on every command takes `--locked`.
- **Why it matters:** the same shape as `go.sum` in `go-cli`: after the first
  commit the graph is pinned by checksum, which is stronger than version
  pinning alone. The residual risk is the moment of generation, when nobody
  has read the file.
- **Fix:** already addressed as far as a recipe can: `AGENTS.md` says the lock
  file is committed, that every build uses `--locked`, and that its diff is
  the supply chain and is read. Recorded so the next reviewer does not have
  to re-derive it.

### 3. The 1.85 floor is not exercised by this catalog's own recipe test — `info`

- **Where:** `blueprints/rust-cli/manifest.yaml` (`requires_tools`),
  `blueprints/rust-cli/setup.md:397` (the `msrv` job)
- **Standard:** SLSA v1.2, build track — what the build is known to run on
- **What:** `rust-version = "1.85"` comes from clap 4.6.7's declared
  `rust-version` and the 2024 edition's minimum; every transitive crate read
  from crates.io on 2026-09-25 declares 1.85 or lower. The catalog's
  `setup-test` runs the recipe on one current toolchain, not on 1.85.
- **Why it matters:** a declared floor that no build has exercised is a claim.
  Here it is exercised, but by the generated project's CI on its first push,
  not by this repository.
- **Fix:** none needed for a merge. The generated workflow's `msrv` job builds
  and tests on exactly 1.85.0, the edition-2024 resolver prefers versions that
  fit `rust-version`, and `overview.md` states the gap under "Cons".

### 4. A closed stdout is reported as an error — `info`

- **Where:** `blueprints/rust-cli/setup.md:187` (step 6, `run`)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**
- **What:** `example greet Ada | head -0` prints
  `error: could not write the output: Broken pipe` and exits 1.
- **Why it matters:** this is the deliberate alternative to `println!`, which
  panics on the same condition and exits 101. Some tools prefer to exit
  quietly on a broken pipe; that is a choice, and it is written down in
  `overview.md` rather than left for a user to discover.
- **Fix:** none. Recorded as a decision.

## What was checked and found sound

- **One error type, one exit path** (OWASP Top 10:2025 A10). Every failure is a
  variant of `Error`; `main` is the only place that prints one and the only
  place that chooses a status. There is no `From<io::Error>`, so a later `?`
  on a file read cannot borrow the message for a failed write — the most
  common way a single error enum starts lying.
- **Exit codes are an asserted interface.** 0, 1 and 2 are each checked against
  the compiled binary in `tests/cli.rs`, with what lands on stdout and stderr,
  and again by the recipe's last two steps.
- **No panic on a closed stdout** (A10). Output goes through a writer and a
  failed write is `Error::Output`; the unit test in `src/main.rs` drives `run`
  into a writer that returns `BrokenPipe` and asserts the variant.
- **Arguments are validated by the code that uses them** (OWASP ASVS 5.0,
  Validation chapter). A blank name is refused by `greet` with its own variant
  and message — the finding raised against `go-cli`, `python-cli` and
  `node-cli` does not recur here.
- **The command definition is checked whole.** `Cli::command().debug_assert()`
  walks every subcommand and argument, not only the path a test happens to
  take.
- **`--help` and `--version` come from `Cargo.toml`**, and both are asserted
  against `CARGO_PKG_DESCRIPTION` and `CARGO_PKG_VERSION`, so they cannot
  drift.
- **The crate forbids `unsafe_code`** through `[lints.rust]` in `Cargo.toml`.
- **Dependencies** (A03; Twelve-Factor II). One direct dependency, pinned with
  `=`; a lock file with checksums; `--locked` on every build, lint and test
  command in the recipe and in CI. The versions were read from the crates.io
  API on 2026-09-25.
- **No toolchain file.** A `rust-toolchain.toml` would make rustup download a
  toolchain from a host that is not a package registry in the middle of the
  recipe. The toolchain is pinned in the CI workflow instead.
- **`publish = false`**, so the example cannot be pushed to crates.io by a
  stray `cargo publish`.
- **The generated CI workflow** (SSDF PS.1, SLSA v1.2): actions pinned by
  commit SHA with the version in a comment, `permissions: contents: read`,
  `persist-credentials: false` on checkout, a pinned toolchain for lint and
  test, and a second job on the declared minimum.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The recipe names no host; `cargo` reaches crates.io only.

## Not applicable

- **Authentication, authorization, session management (ASVS 5.0).** No users,
  no server, no requests.
- **OWASP API Security Top 10.** `project_type: cli`; no API.
- **OWASP LLM 2025 and Agentic 2026.** Nothing is exposed to a model.
- **CIS Docker Benchmark.** No container.
- **Configuration and secrets (Twelve-Factor III).** The tool reads no
  configuration and no environment variables, and `overview.md` says so.
- **Release integrity (SLSA provenance for artefacts).** No release workflow
  and no published artefact; `requirements` does not claim `cd`, and
  `overview.md` lists releasing under "What it is NOT for".

---

## Verdict

**MERGE.** Two `low` findings and two `info`, none blocking.

The one worth acting on in a real project is the first: an exact pin is a
promise that nothing moves without somebody deciding, and that promise needs
something that tells somebody when to decide.

`tier: official` is not available while `provenance: generated` (ADR 0011).
