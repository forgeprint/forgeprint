# terraform-module — architecture and security review

- Date: 2026-09-23
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first `infra` blueprint and its first `iac`.

The open question the catalog plan raised about this category was whether an
`infra` blueprint can be verified honestly at all, since applying to a cloud
needs an account and the catalog's first filter forbids that. This answers it:
`terraform test` applies for real against the `random` provider, so the module
is genuinely exercised — outputs asserted, validations proved to refuse — with
no credentials anywhere.

That is also the blueprint's main limitation, and it is stated rather than
hidden: the resource is a `random_pet`, so what is proved is the module's own
logic and nothing about a cloud.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. The test strategy stops working the moment the resource is real, and only prose says so — `medium`

- **Where:** `blueprints/terraform-module/setup.md:160` (step 6), against
  `AGENTS.md`, "Testing without an account"
- **Standard:** the catalog's own rule that a verification must prove what a
  reader thinks it proves; NIST SSDF, verification practices
- **What:** `terraform test` with `command = apply` costs nothing against
  `random`. Replace `random_pet` with an S3 bucket and the same suite creates
  real infrastructure, needs credentials, and fails in CI — or, worse, is
  quietly deleted by whoever hits that first.
- **Why it matters:** this blueprint's most valuable property is that it makes
  Terraform testing look easy, and the reason it is easy here does not
  generalise. A reader who copies the pattern and swaps the resource inherits a
  suite that cannot run.
- **Mitigating:** `AGENTS.md` addresses it directly under its own heading, and
  names the three honest options — plan-only runs, provider mocks, or accepting
  that the tests need credentials and saying so. `overview.md` repeats it under
  Cons.
- **Fix:** none to the code. What would close it is one `run` block with
  `command = plan` alongside the `apply` ones, showing the reader the form that
  survives the swap. A small addition, worth making before this blueprint gains
  a cloud-shaped sibling.

### 2. `.terraform.lock.hcl` is ignored, and the reason is not written down — `low`

- **Where:** `blueprints/terraform-module/setup.md:246` (step 7)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** the lock file is in `.gitignore`. For a reusable module that is the
  conventional choice — the consumer's lock file is the one that governs — but
  for a root module it is wrong, and the file gives no hint which case it is.
- **Why it matters:** this blueprint will be copied as a starting point for
  root modules, because it is the only Terraform blueprint here. Somebody will
  inherit an ignored lock file in a configuration that should have committed
  one, which is exactly the drift `required_providers` pinning is meant to
  prevent.
- **Fix:** a comment in `.gitignore`, or a line in `AGENTS.md`. `overview.md`
  raises it under Cons, which is the right place to notice it and the wrong
  place to fix it.

### 3. Provider pinning is exact and the Terraform floor is open, which is correct and worth recording — `info`

- **Where:** `blueprints/terraform-module/setup.md:18` (step 1)
- **Standard:** OWASP Top 10:2025 **A03**; SLSA v1.2
- **What:** `required_version = ">= 1.9.0"` and `random = "3.7.2"`.
- **Why it matters:** the asymmetry is deliberate and the reverse is the common
  mistake. A module pinned to one Terraform version cannot be composed; an
  unpinned provider changes a consumer's plan without changing their code. The
  comments say both.

## What was checked and found sound

- **Validation lives at the edge.** Both inputs have `validation` blocks with
  messages written in the module author's words. A module that accepts anything
  fails inside a provider, naming a field the caller has never seen
  (ASVS 5.0, Validation).
- **The refusals are tested.** `expect_failures` on an unknown environment and
  a capitalised name. Most modules test the happy path twice and never learn
  that a validation condition has a typo — this is the single most unusual
  thing in the blueprint.
- **The caller's tags win the merge**, and a test asserts it.
- **`keepers` ties the random value to the inputs**, so a plan that touches the
  module does not propose a change. Without it people learn to ignore the diff,
  which is how a real change gets approved unread.
- **`-backend=false` everywhere**, so nothing in the recipe or in CI needs
  credentials for a backend it would never write to.
- **The example is initialised and planned**, which is the only check that the
  module is consumable by its documented path, and **the plan is inspected**
  rather than merely produced — the JSON is read and the resource type
  asserted, so a change that adds a second resource is visible.
- **`terraform fmt -check` in the recipe and in CI**, which removes the one
  thing every Terraform review otherwise argues about.
- **Actions pinned by commit SHA** with the version in a comment;
  `permissions: contents: read` only (A03; least privilege).
- **State, tfvars and crash logs are git-ignored** — `*.tfstate` in particular,
  which routinely contains secrets in plain text (CLAUDE.md §5b).
- **No secrets, no personal data, no employer information.** No cloud account,
  no region, no organisation name anywhere.

## Not applicable

- **Authentication, authorization, session management (ASVS 5.0).** No running
  service.
- **OWASP API Security Top 10.** No API.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: infra`; nothing is
  exposed to a model.
- **CIS Docker.** No container.
- **Cloud-specific controls** — encryption at rest, IAM least privilege,
  network policy. There is no cloud resource to apply them to, which is the
  blueprint's declared scope and the subject of finding 1.

---

## Verdict

**MERGE.** One `medium`, one `low`, one `info`.

The `medium` is the interesting one and it is a scope finding rather than a
defect: the blueprint makes Terraform testing look easy, and the reason it is
easy here is that the resource is free to create. That is disclosed in two
places and would be closed properly by a single plan-only `run` block showing
the form that survives a real provider.

This blueprint answers the question the catalog plan left open about `infra`,
which is worth recording: a module can be verified honestly without an account,
as long as the blueprint is equally honest about what that verification covers.

`tier: official` is not available while `provenance: generated` (ADR 0011).
