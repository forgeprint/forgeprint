# blazor-web-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21). ASVS control numbers were read from the 5.0 source in the OWASP
  ASVS repository on the date of this review.
- Reviewer: maintainer's Claude Code agent, `blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
A Blazor Web App on .NET 10 with ASP.NET Core Identity on SQLite, static server
rendering by default and Interactive Server by opt-in. It claims
`requirements: [auth, testing, ci]` and `project_type: web`, so the review is
ASVS 5.0 V3 (web frontend), V6 (authentication), V7 (session management) and
V8 (authorization), plus SSDF and SLSA for the workflow.

The single most important thing a reader should know: **the template's
authentication defaults are a demo's, and this blueprint changes five of
them.** The first draft followed the template and this review found two `high`
findings, three more against ASVS level 1, and a supply-chain advisory in the
template's SQLite library. All six were fixed in the recipe before the pull
request opened, each with a test that fails when the fix is removed (checked by
reverting each fix and re-running `dotnet test`). What is left open is three
`medium` gaps, all disclosed in `overview.md` and `AGENTS.md`.

The manifest claims `tier: community` and `provenance: generated`.

## Resolved before the pull request

These were found in the draft and fixed in the recipe under review. They are
recorded because the fix is the design, and a later edit that undoes one should
be recognisable as a regression.

### R1. Password lockout off on the login page — `high`

- **Where:** the template's `Components/Account/Pages/Login.razor`, which calls
  `PasswordSignInAsync(..., lockoutOnFailure: false)`
- **Standard:** OWASP ASVS 5.0 **6.3.1** (L1), brute-force controls; **6.1.1**,
  documentation of how they are configured
- **Fix, now in the recipe:** `LockoutSignInManager`
  (`blueprints/blazor-web-app/setup.md:61`, step 11) overrides
  `CheckPasswordSignInAsync`, which every password path goes through, to force
  lockout on; `options.Lockout` is written out in `Program.cs` (step 12) and
  documented in `AGENTS.md`. `PasswordTests` signs in five times with
  `lockoutOnFailure: false` — exactly what the page passes — and asserts the
  account is locked, and that the right password then fails too.

### R2. Confirmation links shown on the page in every environment — `high`

- **Where:** the template registers `IdentityNoOpEmailSender` unconditionally,
  and `RegisterConfirmation.razor` prints the confirmation link whenever that
  sender is registered
- **Standard:** OWASP ASVS 5.0 **13.4.2** (development features disabled in
  production); OWASP Top 10:2025 **A02 Security Misconfiguration** and **A07
  Authentication Failures**
- **Why it was high:** anybody could register with an address they do not own
  and confirm it themselves, which makes `RequireConfirmedAccount = true`
  meaningless, and nothing in the running application says so.
- **Fix, now in the recipe:** the sender is registered only in Development, and
  `Program.cs` throws at startup outside Development unless a real
  `IEmailSender<ApplicationUser>` is registered (`setup.md:184` and `:191`).
  `AccountTests` boots the application in Production and asserts it refuses.

### R3. Six-character passwords with composition rules — `high`

- **Where:** Identity's `PasswordOptions` defaults, which the template keeps
- **Standard:** OWASP ASVS 5.0 **6.2.1** (at least 8, 15 strongly recommended)
  and **6.2.5** (no composition rules), both L1
- **Fix, now in the recipe:** `RequiredLength = 15` and every `Require*` rule
  off (`setup.md:163`). `PasswordTests` asserts that a 14-character password
  with every character class is refused and a 21-character lower-case
  passphrase is accepted. Maximum length is 100 in the template's forms, which
  meets **6.2.9**.

### R4. Authentication cookies only `Secure` when the request was — `high`

- **Where:** cookie authentication's default `CookieSecurePolicy.SameAsRequest`
  and unprefixed names, for the Identity and antiforgery cookies
- **Standard:** OWASP ASVS 5.0 **3.3.1** (L1): `Secure`, and a `__Host-` or
  `__Secure-` prefix
- **Why it was high:** behind a proxy that terminates TLS the application sees
  http and issues the session cookie without `Secure`, silently.
- **Fix, now in the recipe:** `PostConfigureAll<CookieAuthenticationOptions>`
  sets `Always` and a `__Host-` prefix on every authentication cookie, and the
  antiforgery cookie gets the same (`setup.md:135`, `:140`). `TransportTests`
  checks all four Identity schemes; `AccountTests` checks the antiforgery
  `Set-Cookie` header.

### R5. HSTS for thirty days — `medium`

- **Standard:** OWASP ASVS 5.0 **3.4.1** (L1): a max-age of at least one year
- **Fix, now in the recipe:** `AddHsts` with 365 days (`setup.md:147`), asserted
  in `TransportTests`. `includeSubDomains` (the L2 half of 3.4.1) is left to
  whoever owns the domain.

### R6. SQLite native library under a high-severity advisory — `high`

- **Where:** `dotnet new blazor --auth Individual` resolves
  `SQLitePCLRaw.lib.e_sqlite3` 2.1.11, GHSA-2m69-gcr7-jv3q
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF v1.1 **RV.1** (identify and confirm vulnerabilities)
- **Fix, now in the recipe:** EF Core Sqlite 10.0.12 (step 6), and
  `Directory.Build.props` (step 10) turns the NuGet audit over the transitive
  graph into a build error, so the next advisory fails CI rather than printing a
  warning nobody reads.

## Findings

### 1. No check against common or breached passwords — `medium`

- **Where:** `blueprints/blazor-web-app/setup.md:163`, step 12 (`options.Password`)
- **Standard:** OWASP ASVS 5.0 **6.2.4** (L1): passwords checked against at
  least the top 3000 that match the policy; **6.2.12** (L2) for breached sets
- **What:** length is enforced; whether the 15 characters are
  `passwordpassword` is not.
- **Why it matters:** length rules without a blocklist leave the passwords
  people actually choose at that length.
- **Why `medium`:** disclosed under "What it is NOT for" in `overview.md` and
  "What this does not do" in `AGENTS.md`, so a reader who looks will not assume
  it.
- **Fix:** an `IPasswordValidator<ApplicationUser>` that checks a bundled
  top-passwords list, registered with `.AddPasswordValidator<>()`, and a test
  beside the length test.

### 2. Sign-out does not revoke a copied session cookie — `medium`

- **Where:** `Program.cs` (step 12) and the template's `/Account/Logout`
  endpoint in `MapAdditionalIdentityEndpoints`
- **Standard:** OWASP ASVS 5.0 **7.4.1** and **7.4.2** (L1)
- **What:** Identity's cookie is self-contained. Sign-out deletes it from the
  browser; a copy taken earlier stays valid until it expires (14 days,
  sliding) or the user's security stamp changes, which the cookie validator
  checks every 30 minutes. Deleting an account ends its sessions within that
  window, not immediately.
- **Why `medium`:** a real weakness with a workaround, and disclosed in
  `AGENTS.md` with the method that closes it.
- **Fix:** call `UserManager.UpdateSecurityStampAsync` on sign-out (which also
  signs the user out on other devices, a product decision), and shorten
  `SecurityStampValidatorOptions.ValidationInterval` if 30 minutes is too long.

### 3. No Content-Security-Policy, `nosniff` or Referrer-Policy — `medium`

- **Where:** the pipeline in `Program.cs` (step 12, `setup.md:197`–`:219`)
- **Standard:** OWASP ASVS 5.0 **3.4.3**, **3.4.4**, **3.4.5**, **3.4.6** (L2)
- **What:** HSTS is the only security header the application sends.
- **Why it matters:** a CSP is the defence in depth against an injection in a
  component that renders `MarkupString`, and `frame-ancestors` against
  clickjacking the account pages.
- **Why `medium` and not higher:** these are level 2 requirements, Razor
  encodes output by default, and the gap is disclosed in `overview.md` and
  `AGENTS.md`. A CSP that is right for a template is wrong for the application
  it becomes, which is why it is left to the reader rather than guessed.
- **Fix:** a middleware setting the headers, with a CSP that allows `'self'`
  for scripts and `connect-src 'self'` for the circuit's WebSocket, and a test
  that reads them from a response.

### 4. The local SQLite database is tracked by default — `low`

- **Where:** `Data/app.db`, created by the template in step 4; `.gitignore`
  from step 2 does not exclude it
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**;
  CLAUDE.md §5b (personal data never in a repository)
- **What:** the file is empty and migrated when created, then collects every
  account registered while developing. A `git add .` commits them.
- **Fix:** documented in `AGENTS.md` (add it to `.gitignore` once the
  application has been used). A recipe step that ignores it would also stop
  the empty database from being shared, which the template relies on for the
  first run; the trade was left to the reader.

### 5. Failed sign-ins are not logged, and there is no health endpoint — `low`

- **Where:** the template's `Login.razor` (logs success and lockout, not
  failure); `Program.cs` maps no health check
- **Standard:** OWASP ASVS 5.0 **16.3.1** (L2, all authentication operations
  logged); OWASP Top 10:2025 **A09 Security Logging and Alerting Failures**
- **What:** a password-guessing run shows up only as lockout warnings, one per
  five attempts per account; an operator has no liveness endpoint to probe.
- **Fix:** log the failure branch in `Login.razor` (without the password or the
  full address), and `AddHealthChecks` with a `/health` that does not touch the
  database, as `dotnet-web-api` does.

### 6. Transitive packages are resolved, not locked — `low`

- **Where:** no `packages.lock.json`; `Directory.Build.props` (step 10)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; SLSA
  v1.2 build track (reproducible inputs)
- **What:** every package a project names is pinned; the packages those depend
  on are resolved at restore, deterministically for a given feed state but not
  frozen.
- **Fix:** `RestorePackagesWithLockFile` and `dotnet restore --locked-mode` in
  CI, when the project is real. Consistent with the other .NET blueprints here,
  none of which lock yet.

### 7. `AllowedHosts: "*"` — `low`

- **Where:** the template's `appsettings.json`
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**; ASP.NET
  Core security documentation (host filtering)
- **What:** any `Host` header is accepted, and the login redirect is built from
  it.
- **Fix:** set the production host names in `AllowedHosts` through the
  environment at deployment.

### 8. Interactive Server holds a circuit per user — `info`

- **Standard:** ASP.NET Core security documentation (Blazor server-side threat
  mitigation); OWASP API Security Top 10 2023 **API4** (resource consumption)
  as the nearest named risk
- **What:** each interactive tab holds server memory and a connection. The
  framework's limits (retained disconnected circuits, buffered render batches,
  message size) are left at their defaults, which is the documented
  starting point. `overview.md` names concurrency as a reason not to pick this
  blueprint, and `AGENTS.md` keeps interactivity per component rather than
  global.

## What was checked and found sound

- **Authorization boundary** (ASVS 5.0 **8.2.1**, **8.3.1**): `/auth` carries
  `[Authorize]`, which puts the policy on the endpoint so the authorization
  middleware redirects before anything renders. Tested with a real request and
  by the recipe's final check against the running application. `AGENTS.md`
  says `<AuthorizeView>` is display, not a boundary, and that interactive
  handlers re-check the user.
- **Cross-site request forgery** (ASVS 5.0 **3.5.1**): `UseAntiforgery` refuses
  a form post without a token with 400; a second test sends the rendered token
  and gets through, so the 400 is proved to come from the token. Sign-out is a
  POST (**3.5.3**).
- **Session tokens** (ASVS 5.0 **7.2.1**, **7.2.4**): Identity's cookie is
  issued anew on sign-in and verified on the server; the circuit revalidates the
  security stamp every 30 minutes.
- **Secrets** (.NET secrets guidance; Twelve-Factor III): the configuration
  holds none. The connection string names a local file; a production one comes
  from `ConnectionStrings__DefaultConnection`, as `AGENTS.md` says. The test
  passwords are obviously fake, and `example.com` addresses are reserved.
- **Error handling** (OWASP Top 10:2025 **A10**; ASVS 5.0 **16.5.1**,
  **16.5.3**): `UseExceptionHandler` outside Development; the missing email
  sender and a missing connection string stop the application at startup
  instead of failing a request after a row was written.
- **Test strategy:** eleven tests. The nine that cover a security control were
  each shown to fail when that control was removed from a generated project;
  the two bUnit tests cover component behaviour. The test database is built from the migrations
  on every run, so a model change without a migration fails CI.
- **CI** (SLSA v1.2; NIST SSDF v1.1 **PS.1**): `permissions: contents: read`,
  both actions pinned by full commit SHA at their latest releases,
  `global-json-file` so CI and developers use the same SDK, and the format
  check, build and tests all gate the workflow.
- **Boundaries** (Clean Architecture's dependency rule): not claimed. The
  blueprint is one project where components call the data layer, and
  `overview.md` presents that as the reason to choose it; `AGENTS.md` sets the
  one rule that matters on a circuit (a `DbContext` per operation).

## Not applicable

- **CIS Docker Benchmark:** no container is built; `containerization` is not
  claimed.
- **OWASP API Security Top 10** beyond the nearest-risk reference in finding 8:
  `project_type` is `web`, and there are no JSON endpoints.
- **ASVS V9 and V10** (self-contained tokens, OAuth and OIDC): no bearer tokens
  and no external identity provider are configured.
- **OWASP LLM, Agentic and MCP references:** not an agent.
- **WCAG 2.2:** `accessibility` is not claimed. The template's pages are not
  reviewed for it, and nothing here says they meet it.
