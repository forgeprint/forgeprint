# tauri-desktop-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c),
and the catalog's first `desktop` one. A desktop app has a security boundary a
web app does not: the webview runs HTML and JavaScript, the Rust process runs
with everything the user can do, and IPC is the only door between them. The
blueprint keeps that door to one command, grants it by capability to one
window, denies everything from Tauri's core and every plugin, and pins all of
it with tests.

The most important thing to know before building on it: **the catalog's own
CI never compiles the shell** — on Linux it needs WebKitGTK, installed with
root, which a recipe may not do. `overview.md` says so under "What CI can
prove, and what it cannot", and the generated project's CI builds the shell on
all three platforms from its first push.

The manifest claims `tier: community`, `provenance: generated` and
`requirements: [testing, ci]`. It does not claim `cd`, `auth` or
`notifications`, and `overview.md` lists signing, installers in CI and the
updater under "What it is NOT for".

## Findings

### 1. The Windows IPC origin in the CSP is reasoned, not observed — `low`

- **Where:** `blueprints/tauri-desktop-app/setup.md:600` (step 17,
  `tauri.conf.json`), and the matching constant in step 19
- **Standard:** OWASP ASVS 5.0, V3 Web Frontend Security (the Content Security
  Policy requirements); OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** `connect-src ipc: ipc.localhost` writes the Windows IPC origin
  without a scheme, where Tauri's examples write `http://ipc.localhost`. A
  scheme-less source matches the page's own scheme, which is `http` for a
  Tauri page on Windows, so the two should be equivalent. The recipe's linter
  refuses a URL to a non-registry host, which is why it is written this way.
- **Why it matters:** not a weakening — if the reasoning is wrong the policy
  is stricter, not looser, and Tauri falls back from the custom protocol to
  `postMessage` IPC, which still works. The cost would be speed and a console
  warning on Windows, not exposure.
- **Fix:** none needed for a merge. Disclosed in `overview.md` ("That the CSP
  is right for WebView2") and the CHANGELOG. The first Windows run of the
  generated app settles it; if it is wrong, the fix is one string in two
  files.

### 2. No advisory check on either dependency graph — `low`

- **Where:** `blueprints/tauri-desktop-app/setup.md:839` (step 24, the
  generated CI workflow)
- **Standard:** NIST SSDF SP 800-218 v1.1, **RV.1** (identify and confirm
  vulnerabilities on an ongoing basis); OWASP Top 10:2025 **A03 Software
  Supply Chain Failures**
- **What:** Tauri is pinned with `=` and the frontend with exact versions,
  with both lock files committed. Nothing compares `Cargo.lock` (about 420
  crates) or `package-lock.json` against an advisory database.
- **Why it matters:** exact pins are right for reproducibility and wrong for
  hearing about a fix. A desktop app ships its dependency tree to every
  user's machine, and a Tauri security release would not arrive by
  `cargo update`.
- **Fix:** a scheduled `cargo audit` or `cargo deny check advisories` job and
  `npm audit` in the generated workflow. Not added here: both fetch their
  databases from outside the package registries a recipe may reach. Stated as
  the first thing to add under `overview.md`'s trade-offs and in the
  CHANGELOG's "Planned".

### 3. The Linux shell job's apt packages are not version-pinned — `low`

- **Where:** `blueprints/tauri-desktop-app/setup.md:903` (step 24,
  `shell-linux`)
- **Standard:** SLSA v1.2, build track (what the build trusts); OWASP Top
  10:2025 **A03**
- **What:** the container image is pinned by tag and digest, but
  `apt-get install libwebkit2gtk-4.1-dev libxdo-dev libssl-dev` takes whatever
  Debian bookworm serves that day.
- **Why it matters:** two builds of the same commit can link against
  different WebKitGTK patch releases. Debian stable's security updates are the
  usual reason a version moves, so the drift runs in the safe direction; it is
  still an input the build does not record.
- **Fix:** accepted and disclosed in `overview.md` ("Container for the Linux
  shell job"). Pinning Debian package versions breaks as soon as the archive
  drops the pinned one, which is worse for a template than the drift.

### 4. An unexpected IPC failure is hidden from the user and logged nowhere — `low`

- **Where:** `blueprints/tauri-desktop-app/setup.md:165` (step 6,
  `src/commands.ts`)
- **Standard:** OWASP Top 10:2025 **A09 Security Logging and Alerting
  Failures**
- **What:** a rejection that is not the command's own message string — a
  command the ACL denied, no Tauri runtime — becomes a generic sentence for
  the user, and the original error is dropped.
- **Why it matters:** the user-facing half is right (the error is not a
  message meant for them, and a denied command should not explain the ACL to
  the page). But a developer debugging a capability change sees only the
  generic sentence.
- **Fix:** log the original with `console.error` in that branch when the app
  grows a logging story (Tauri's log plugin is a plugin, and the policy test
  would ask for it to be justified). Recorded rather than fixed, because the
  blueprint deliberately ships without a plugin.

### 5. The shell's IPC tests open their own `main` window — `info`

- **Where:** `blueprints/tauri-desktop-app/setup.md:512` (step 15, the tests in
  `src-tauri/src/lib.rs`)
- **Standard:** OWASP ASVS 5.0, V8 Authorization (access control enforced
  where the request is served, and tested)
- **What:** windows declared in `tauri.conf.json` are opened when the app
  runs, which a test does not do, so the test builds a window with the same
  label. The capability grants by label, so the access decision tested is the
  real one — the same configuration, capability and app manifest the shipped
  app compiles in.
- **Why it matters:** a reader might assume the test proves the config's
  window exists. It does not; `src/tauri-policy.test.ts` pins that
  separately, and the two together cover it.
- **Fix:** none. Recorded so the next reviewer does not re-derive it.

## What was checked and found sound

- **Least privilege on the IPC surface** (OWASP ASVS 5.0 V8 Authorization;
  OWASP Top 10:2025 A01 Broken Access Control). `build.rs` lists `greet` in
  Tauri's app manifest, which turns on access control for app commands —
  without it Tauri allows every registered app command from every local
  window, and the capability would be decoration. The one capability grants
  `allow-greet` to `main` and nothing else: no `core:default`, which Tauri's
  own templates grant and which covers window, event, path, app, menu, tray
  and webview commands this page does not use. The shell's test calls
  `plugin:app|version` and asserts the refusal.
- **The surface cannot grow silently** (A01, A02). `src/tauri-policy.test.ts`
  fails when the capability grants anything but the app's own commands, when
  `build.rs` and `generate_handler!` disagree (the way a new command would
  escape the ACL), when a second capability file or window appears, when the
  CSP changes by a character, when `withGlobalTauri`, `freezePrototype`,
  `devCsp`, `dangerousDisableAssetCspModification` or the
  `app.security.capabilities` allowlist move, and when any `tauri-plugin-*`
  crate or `@tauri-apps/plugin-*` package appears. Verified by breaking a copy:
  adding `core:default` fails the test.
- **No remote content with IPC** (A01). No `remote` block in the capability,
  no window pointed at an external URL, `withGlobalTauri` off so the API is
  not on `window` for any script in the page.
- **Content Security Policy** (ASVS 5.0 V3; A02). `default-src 'self'`, IPC
  only in `connect-src`, `object-src`, `base-uri`, `form-action` and
  `frame-ancestors` all `'none'`, no `'unsafe-inline'` or `'unsafe-eval'`.
  The recipe checks that the built page has no inline script; Vite emits the
  entry as a module file. Tauri adds hashes for its own injected scripts at
  build time, which is why the asset CSP modification is left on.
- **Input from the webview is validated in Rust** (ASVS 5.0, Validation and
  Business Logic chapter). `app_core::greet` trims, refuses empty input,
  counts characters rather than bytes against a limit, and refuses control
  characters, each with a unit test. The HTML `maxlength` is a convenience;
  the Rust check is the control.
- **Errors cross IPC as a message and nothing else** (A10 Mishandling of
  Exceptional Conditions). The command returns `Result<String, String>` from
  the error's `Display`; no source chain, path or type name reaches the page.
- **Output encoding** (A05 Injection). The page writes the result with
  `textContent`, never `innerHTML`, and `AGENTS.md` makes that a rule with its
  reason.
- **Boundaries** (Hexagonal architecture; Clean Architecture's dependency
  rule). `app-core` has no dependencies at all, and in particular no `tauri`;
  the shell depends on it and not the other way round. The workspace's
  `default-members` keeps a bare `cargo test` on the core crate, which is also
  what makes it testable on a machine without a webview.
- **Dependencies** (A03; Twelve-Factor II). Tauri and tauri-build pinned with
  `=`, npm packages exact, both lock files committed, `--locked` and `npm ci`
  everywhere in CI. The versions were read from crates.io and the npm
  registry on 2026-09-25. Tauri 3 is in alpha and not used. Every crate in the
  resolved lock file declares a `rust-version` of 1.85 or lower.
- **MSRV** (SLSA v1.2 build track). `rust-version = "1.85"` is kept by an
  `msrv` job in the generated CI. The core crate's tests were also run on Rust
  1.85.0 against the recipe's own lock file on 2026-09-25, locally.
- **The generated CI workflow** (SSDF PS.1; SLSA v1.2). Actions pinned by
  commit SHA with the version in a comment, `permissions: contents: read`,
  `persist-credentials: false` on every checkout, a pinned toolchain. The
  Linux shell job is root only inside a container pinned by digest; there is
  no `sudo` anywhere.
- **Config validated by Tauri itself.** The recipe's last step loads
  `tauri.conf.json` through the pinned CLI, which validates it against its
  bundled schema; an unknown key makes it exit 1 (checked by breaking a copy).
- **No toolchain file.** `rust-toolchain.toml` would make rustup download a
  toolchain mid-recipe from a host that is not a package registry.
- **`unsafe_code` forbidden** workspace-wide; `publish = false`.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The bundle identifier is `com.example.desktop`, a reserved documentation
  domain.

## Not applicable

- **Code signing, notarization, installer integrity and the updater** (SLSA
  provenance for artefacts; ASVS 5.0 V15 Secure Coding and Architecture as it
  applies to update channels). Out of scope by design: no release workflow, no
  signing key, no update endpoint. `requirements` does not claim `cd`, and
  `overview.md` lists shipping signed installers under "What it is NOT for".
  `AGENTS.md` says not to add the updater plugin without a signing key kept
  outside the repository and an endpoint the owner controls.
- **Authentication and session management (ASVS 5.0).** No users, no
  accounts, no server.
- **OWASP API Security Top 10.** `project_type: desktop`; IPC is in-process,
  not a network API, and no port is opened by the built app.
- **OWASP LLM 2025 and Agentic 2026.** Nothing is exposed to a model.
- **CIS Docker Benchmark.** The container in the generated CI is a build
  environment, not a shipped image.
- **Configuration and secrets (Twelve-Factor III).** The app reads no
  configuration and no environment variables at run time; the Vite config
  reads `TAURI_ENV_PLATFORM`, which the Tauri CLI sets at build time.
- **Mobile targets.** Tauri 2 supports iOS and Android; nothing here targets
  them and `platforms` does not list them.
