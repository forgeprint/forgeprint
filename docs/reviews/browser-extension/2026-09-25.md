# browser-extension — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check
  due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first `project_type: extension`, added by decision D23 of the
2026-09-24 expansion plan: a Manifest V3 extension for Chrome and Firefox built
with WXT, with a background service worker, a content script on one declared
site, and a popup. The similarity report puts it far from everything else (32%
tags, 16% `AGENTS.md`, 19% `setup.md` against the closest,
`nextjs-fullstack-app`).

The single most important thing a reader should know: **an extension's attack
surface is its permission list and its message boundary**, and this blueprint
turns both into checks rather than conventions. The permission list is a file
(`extension-policy.json`) that a build step holds the shipped manifest to; the
message boundary is one parser plus a sender check in the background. What CI
cannot show is the extension running in a browser, and the blueprint says so.

The manifest claims `tier: community`, `provenance: generated`, and
`requirements: [testing, ci]`. No `critical` or `high` findings are open. Two
`low` findings found during this review (a content script and a popup that
threw when the background did not answer) were fixed before the pull request
opened, and are recorded under "Fixed before merge".

## Findings

### 1. The extension is never loaded into a browser by CI — `medium`

- **Where:** `blueprints/browser-extension/setup.md:1103` to `:1125`, steps
  28–35; disclosed in `overview.md:96` ("What CI cannot prove") and
  `AGENTS.md:126`
- **Standard:** NIST SSDF v1.1, PW.8 (test executable code to identify
  vulnerabilities and verify compliance with requirements); OWASP Top 10:2025
  A02 Security Misconfiguration
- **What:** the recipe proves the logic against `@webext-core/fake-browser`, and
  the manifests as JSON. Nothing proves that Chrome accepts the CSP, that the
  service worker's listener receives a real `MessageSender`, or that Firefox
  loads the event-page background. The five lines in `entrypoints/background.ts`
  that pass the real sender to `handleMessage` run only in a browser.
- **Why it matters:** the sender check is the extension's authorization, and its
  wiring is the one piece of it no test reaches. A reader could take "51 tests
  pass" as "the extension works".
- **Mitigating, and why this is `medium` rather than `high`:** the gap is
  disclosed where a reader looks — `overview.md` has a section for it with the
  exact manual steps to load the build in both browsers, `AGENTS.md` says it
  under "What this does not do", and `CHANGELOG.md` lists a browser test as
  planned. The handler that makes the decision is tested with each kind of
  sender; the untested part is the call that hands it the sender. No browser is
  downloaded because the recipe rules allow only package registries.
- **Fix:** when a browser can be fetched within the recipe rules, add a step that
  loads `.output/chrome-mv3` in a headless Chromium and asserts one counted page
  on a local fixture served from `localhost`.

### 2. "Only the background writes `stats`" is a rule, not a platform guarantee — `low`

- **Where:** `setup.md:144` (`statsItem` in `storage.local`), `AGENTS.md:59`
  (rule 6)
- **Standard:** OWASP ASVS 5.0.0, V8 Authorization (enforce access decisions
  at a trusted layer); OWASP Top 10:2025 A01 Broken Access Control
- **What:** `storage.local` is readable and writable from content scripts in
  both browsers; nothing in the platform stops a future edit to the content
  script from writing `stats` directly.
- **Why it matters:** the popup trusts `stats`. Today the only code in the
  least-trusted context sends two numbers and a string through a validated
  message, so there is nothing to exploit; the risk is a later change that
  takes the shortcut.
- **Fix, if it is ever worth it:** keep data a content script must not touch in
  `storage.session` with its access level left at trusted contexts only, or add
  a lint rule refusing `statsItem` imports under `entrypoints/content.ts`. The
  rule is written down with its reason in `AGENTS.md`, which is where an agent
  editing the project reads it; this review leaves it there.

### 3. The standards list has no browser-extension platform guidance — `info`

- **Where:** `docs/review-standards.md`, "Platform guidance"
- **Standard:** ADR 0010 (every checklist item cites a listed reference)
- **What:** the Manifest V3 rules this review leans on — the extension-pages CSP
  and its minimum, and the ban on remotely hosted code — come from Chrome's own
  documentation, read on 2026-09-25, and are cited below next to a listed
  standard rather than on their own.
- **Fix:** at the next re-check (due 2026-12-21), add a platform row for the
  Chrome extensions security and Manifest V3 documentation and Mozilla's
  Extension Workshop, with versions and dates.

## Fixed before merge

- **A content script that threw into the page.** `reportPage` let a rejected
  `runtime.sendMessage` escape when the background could not be reached (an
  extension being updated or reloaded), and `document.body.innerText` threw on
  a document with no body. Now `reportPage` returns `false` and the content
  script reads `document.body?.innerText ?? ''` (`setup.md:368`, `:493`), with a
  test for the unreachable background. OWASP Top 10:2025 A10 Mishandling of
  Exceptional Conditions.
- **A popup that failed silently.** The same rejection left the popup blank; it
  now says "The extension is not answering." in its status line, with a test.
  Same standard.

## What was checked and found sound

- **Least privilege** (ASVS V8; A01). `permissions: ["storage"]`, no host
  permissions, one content-script site (`setup.md:62`). The manifest check
  (`setup.md:551`) refuses anything the policy does not list, and refuses
  `<all_urls>` or any every-host pattern even if the policy lists it. Step 31
  proves it fails on a manifest widened with `tabs`, and ten unit cases prove
  each other way of asking for more. A WXT dev build's extra `tabs`,
  `scripting` and localhost permissions would fail the same check.
- **Content-script injection surface** (ASVS V1 Encoding and Sanitization; A05
  Injection). The content script runs in the default isolated world (a `MAIN`
  world script fails the check), only on the declared site, top frame only, at
  `document_idle`. It reads text and the title and writes nothing into the
  page. The one page-controlled value that reaches a privileged context, the
  title, is length-capped on both sides and rendered with `textContent`
  (`setup.md:432`); a test renders `<img src=x onerror=…>` and asserts no
  element is created. The popup builds its DOM with `createElement`, and no
  code in the project assigns `innerHTML` or `outerHTML` or calls
  `insertAdjacentHTML`.
- **Message validation between contexts** (ASVS V2 Validation and Business
  Logic; ASVS V8; A01). `parseMessage` (`setup.md:206`) accepts exactly three
  shapes, refuses extra keys, non-integer and out-of-range counts and oversized
  titles; twelve refusal cases are tested. The background checks the sender,
  not the message: extension id first (`setup.md:295`), then a tab inside the
  declared matches for `page-seen` (`:302`), and an extension page with no tab
  for `get-stats` and `reset-stats` (`:316`, `:321`). Tests cover a content
  script out of scope, a content script trying to read or reset, a report that
  is not from a tab, and another extension's id. No `externally_connectable`, so
  web pages and other extensions cannot message it at all, and the check keeps
  it that way.
- **Integrity of shared state** (A10). Writes to `stats` are serialized
  (`setup.md:283`); 25 concurrent reports all count, in a test.
- **Remote code** (A08 Software or Data Integrity Failures; Chrome's Manifest V3
  remotely-hosted-code rule). Everything executed is bundled. Step 32 greps both
  builds for `eval(`, `new Function(` and `importScripts(`, and the build has no
  URL other than error-message links and the placeholder site. No source maps
  ship (step 33).
- **Extension CSP** (A02 Security Misconfiguration). `script-src 'self';
object-src 'self';` (`setup.md:65`) is Chrome's documented Manifest V3
  default, written out explicitly; WXT's own default would add
  `'wasm-unsafe-eval'`, which nothing here needs. The check holds both builds to
  the exact string.
- **Supply chain** (A03; SLSA v1.2 build track; SSDF PS.1/PW.4). Every direct
  dependency is exact; the lock file is committed and CI installs with
  `npm ci --ignore-scripts` (`setup.md:1071`) — no package in the tree has an
  install script, verified during authoring. Actions are pinned by commit SHA,
  the workflow token is `contents: read` (`:1056`), and checkout does not persist
  credentials (`:1064`). The recipe itself scaffolds without `wxt init`, which
  would fetch templates from GitHub.
- **Secrets and privacy** (CLAUDE.md §5b; ASVS V14 Data Protection). There is no
  secret to keep and `AGENTS.md` rule 14 says why there never can be one in an
  extension. The Firefox sources archive excludes dotfiles (WXT's default,
  checked in its source), so a `.env` would not ship in it; `.gitignore` covers
  `.env*`. The only personal data is page titles, kept in local extension
  storage and never transmitted, which is what the Firefox
  `data_collection_permissions: { required: ['none'] }` declaration
  (`setup.md:95`) promises.
- **Configuration** (Twelve-Factor III, adapted). An extension has no runtime
  environment; its configuration is the policy file, in one place, read by the
  config, the content script and the background alike.
- **Service-worker lifecycle** (A10). The listener is registered synchronously
  and answers with `sendResponse` plus `return true`, the pattern both browsers
  support; nothing that must survive lives in worker memory.
- **Telemetry.** WXT 0.21.4's published code makes no network request outside
  `wxt init`, an opt-in zip option and two helpers that fetch the extension's
  own files; there is nothing to switch off, and the CHANGELOG says so.

## Not applicable

- **Authentication, sessions, tokens** (ASVS V6, V7, V9, V10). There are no users
  and no server; `overview.md` does not claim `auth`.
- **OWASP API Security Top 10.** `project_type` is `extension`, and the
  extension exposes no API: no `externally_connectable`, no
  `onMessageExternal`.
- **CIS Docker Benchmark.** No container.
- **WCAG 2.2.** `accessibility` is not claimed. The popup uses a real `<button>`,
  a labelled checkbox and a `role="status"` line, but nothing measures it and
  nothing here says otherwise.
- **Agent and MCP standards.** Not an agent.
