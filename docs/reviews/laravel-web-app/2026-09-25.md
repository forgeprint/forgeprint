# laravel-web-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21). ASVS requirement texts were read from the OWASP ASVS 5.0
  repository on the day of this review.
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first PHP blueprint: Laravel 13 on SQLite, with login,
registration and logout through Fortify, a dashboard behind the `auth`
middleware, and Blade views built by Vite.

It claims `auth`, so the review is dominated by OWASP ASVS 5.0 chapters V6
(authentication), V7 (session management) and V3 (cookies). The authentication
it builds is sound and tested at the HTTP level, including a rate limit proved
by a test. What a reader most needs to know is what it does **not** build: no
password change or reset, no rate limit on registration, and a `.env.example`
that describes a laptop — all three declared in `overview.md` and `AGENTS.md`,
none of them hidden.

One finding was `high` in the draft and was fixed before the pull request
opened (finding 1).

## Findings

### 1. Passwords were not checked against a breached or common list — `high`, fixed before the pull request

- **Where:** `blueprints/laravel-web-app/setup.md:106` (step 9,
  `CreateNewUser`) and `setup.md:120` (step 10, `AppServiceProvider`)
- **Standard:** OWASP ASVS 5.0 **6.2.4** (level 1) — passwords submitted at
  registration are checked against at least the top 3000 passwords
- **What:** the draft validated registration with `Password::min(12)` and
  nothing else, so `password1234` was accepted.
- **Why it matters:** a level 1 control, missing, in a blueprint that claims
  `auth` — and nothing in the draft said so.
- **Resolution:** `AppServiceProvider` now sets `Password::defaults()` to twelve
  characters plus Laravel's `uncompromised()` rule in production, and
  `CreateNewUser` validates with `Password::default()`, so a password form
  added later inherits the same rule. The breach corpus behind `uncompromised()`
  is a superset of any top-3000 list. What remains is finding 5.

### 2. No password change and no password reset — `medium`

- **Where:** `blueprints/laravel-web-app/setup.md:67` (step 8,
  `config/fortify.php` enables `Features::registration()` only)
- **Standard:** OWASP ASVS 5.0 **6.2.2** (level 1) — users can change their
  password
- **What:** Fortify's `updatePasswords` and `resetPasswords` features are off,
  and there are no views for them.
- **Why it matters:** a user who suspects their password has leaked cannot
  change it, and one who forgets it cannot recover the account.
- **Mitigating:** declared in `overview.md` under "What it is NOT for" and
  under "Cons", and in `AGENTS.md` under "What this does not do", with the
  reason: each feature needs views and a mailer, and a feature turned on
  without its views is a route that answers with an error page. Listed under
  "Planned" in `CHANGELOG.md`.
- **Fix:** turn on `Features::updatePasswords()` and
  `Features::resetPasswords()`, add their views in `FortifyServiceProvider`,
  and validate with `Password::default()`.

### 3. Registration has no rate limit and no email verification — `medium`

- **Where:** `blueprints/laravel-web-app/setup.md:67` (step 8); Fortify's
  `POST /register` route carries only the `guest` middleware
- **Standard:** OWASP ASVS 5.0 **2.4.1** (level 2) — anti-automation against
  garbage-data creation; OWASP Top 10:2025 **A07 Authentication Failures**
- **What:** the login endpoint is throttled; the registration endpoint is not,
  and a new account is signed in without confirming its email address.
- **Why it matters:** anybody can create accounts as fast as they can submit
  the form, with any address. Nothing is gained by it — a new account has no
  privileges — but the table fills.
- **Mitigating:** declared under "Cons" in `overview.md` and in `AGENTS.md`;
  listed under "Planned".
- **Fix:** a named limiter added to the `middleware` list in
  `config/fortify.php`, which applies to every Fortify route including
  registration, with a test like the login one; and `Features::emailVerification()` with `MustVerifyEmail` on `User`
  once a mailer exists.

### 4. `.env.example` describes a laptop: debug on, session cookie not `Secure` — `medium`

- **Where:** `blueprints/laravel-web-app/setup.md:28` (step 5 copies the
  skeleton's `.env.example`); `AGENTS.md:58`
- **Standard:** OWASP ASVS 5.0 **3.3.1** (level 1) — cookies carry the `Secure`
  attribute; **13.4.2** (level 2) — debug modes disabled in production;
  OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** the skeleton's `.env.example` sets `APP_DEBUG=true` and does not
  set `SESSION_SECURE_COOKIE`, so the session cookie is sent without the
  `Secure` attribute unless an operator sets it.
- **Why it matters:** a reader who deploys by copying `.env.example` gets
  stack traces in error pages and a session cookie a browser will send over
  plain HTTP.
- **Mitigating:** `config/app.php` falls back to `debug => false` when the
  variable is absent, and both `AGENTS.md` and `overview.md` ("Deployment")
  now name the three production values — `APP_ENV=production`,
  `APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true` — and say they belong in the
  environment, not in a committed file (Twelve-Factor III). The `__Host-`
  cookie prefix that 3.3.1 also asks for is not set.
- **Fix:** none to the recipe; `.env.example` is right for the laptop it
  describes. A deployment blueprint or option is where production values
  belong.

### 5. The breached-password check is production-only, untested, and fails open — `low`

- **Where:** `blueprints/laravel-web-app/setup.md:144` (step 10)
- **Standard:** OWASP ASVS 5.0 **6.2.4**; OWASP Top 10:2025 **A10 Mishandling
  of Exceptional Conditions**
- **What:** `uncompromised()` runs only when `APP_ENV=production`, so no test
  exercises it; and when the Have I Been Pwned range API cannot be reached,
  the framework accepts the password.
- **Why it matters:** a reader could believe the tests prove the check. And a
  deployment that cannot reach the service has the length rule only, with
  nothing but a log line to say so.
- **Mitigating:** both halves are written in the comment beside the rule and
  in `overview.md` ("Trade-offs"). Production-only is deliberate: the recipe
  and the tests reach package registries and nothing else (CLAUDE.md rule 20).
  The check sends a five-character hash prefix, never the password.
- **Fix:** none required. A reader who wants the check to fail closed can
  catch the failure and refuse; that trades availability of registration for
  strictness and is a product decision.

### 6. `GET /user/confirm-password` is registered with no view behind it — `low`

- **Where:** Fortify registers the password-confirmation page whenever
  `views` is `true` (`setup.md:37`, step 8); `FortifyServiceProvider`
  (`setup.md:152`, step 11) sets only the login and register views
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**
- **What:** a signed-in user who opens `/user/confirm-password` gets a server
  error, because no view is bound for it.
- **Why it matters:** little — the route requires authentication and nothing
  links to it. It becomes real the day somebody adds the `password.confirm`
  middleware to a route and finds it fails.
- **Fix:** add `Fortify::confirmPasswordView(...)` and its view in the same
  change that first uses `password.confirm`. `AGENTS.md` already says features
  and views come together.

### 7. The per-address login limit can affect users behind one address — `info`

- **Where:** `blueprints/laravel-web-app/setup.md:185` (step 11)
- **Standard:** OWASP ASVS 5.0 **6.1.1** — rate limiting is documented,
  including how it avoids malicious account lockout
- **What:** twenty login attempts a minute per address, whatever the account.
  An office or a carrier network behind one address shares that budget.
- **Why it matters:** worth knowing, not a defect. The per-account limit is
  keyed by account **and** address, so an attacker cannot lock a victim out
  from elsewhere — the lockout-abuse half of 6.1.1 holds. The limits and their
  reasoning are documented in the code comment and in `overview.md`.

## What was checked and found sound

- **Login rate limit, proved.** Five attempts a minute per account and address,
  twenty per address; `AuthenticationTest` sends five wrong passwords and then
  the right one and asserts 429 and a guest (ASVS 6.1.1, 6.3.1).
- **The protected route is protected, and a test says so.** `/dashboard` sits
  in an `auth` group; `DashboardTest` asserts a guest is redirected to
  `route('login')`, and the recipe's verification reads the middleware back
  from `route:list` (OWASP Top 10:2025 A01).
- **Session handling is Fortify's, and it is right.** The login pipeline
  regenerates the session on authentication and logout invalidates it and
  regenerates the CSRF token (ASVS 7.2.4, 7.4.1). `test_users_can_log_out`
  asserts the guest state afterwards.
- **Registration is an allow-list.** `CreateNewUser` validates and copies three
  named fields; `User` keeps its `#[Fillable]` list; `AGENTS.md` forbids
  `$guarded = []` and passing `$request->all()` to `create()`.
- **Password minimum above the floor.** Twelve characters against ASVS 6.2.1's
  eight, defined once in `Password::defaults()` so a later form cannot be
  weaker.
- **Output encoding and CSRF.** Every view uses `{{ }}`; every form carries
  `@csrf`; `AGENTS.md` states both as rules with their failure modes.
- **Configuration from the environment, in one place.** The recipe runs
  `config:cache` and greps that nothing outside `config/` calls `env()`
  (Twelve-Factor III), then `route:cache`, then clears both so the tests do not
  inherit a cached configuration. `AGENTS.md` explains that trap.
- **`APP_KEY` generated, never committed.** `key:generate` writes it into a
  git-ignored `.env`; `.env.example` keeps `APP_KEY=` empty; the SQLite file is
  ignored by `database/.gitignore` (CLAUDE.md §5b).
- **Supply chain.** The skeleton, the framework and Fortify are pinned exactly,
  and the npm packages by exact version; the recipe runs `composer audit`, and
  so does the generated CI, which installs from the lock files
  (`composer install`, `npm ci`), pins every action by commit and grants
  `contents: read` only (OWASP Top 10:2025 A03; SSDF; SLSA v1.2 build track).
- **No third-party host at build time.** The skeleton's Vite configuration
  downloads a web font during the build; the recipe removes it, so the build
  reaches nothing but what npm installed.
- **Fortify's defaults are narrowed, not inherited.** Its package configuration
  turns on password reset, email verification, two-factor authentication and
  passkeys; `config/fortify.php` lists only what has views, so no feature is
  half-present.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The only credentials in the recipe are the factory's `password` and the
  test's `correct-horse-battery`, both inside tests against an in-memory
  database.

## Not applicable

- **Object-level authorization (ASVS 8.2.2, API1:2023).** No record in this
  blueprint belongs to a user, and `rbac` is not claimed. `AGENTS.md` says how
  to add a policy and the cross-user test that proves it, which is where this
  control starts to apply.
- **Multi-factor authentication (ASVS 6.3.3).** Not claimed; two-factor
  authentication and passkeys are declared off.
- **Rate limiting of an API (API4:2023).** `project_type: web`; there are no
  API routes.
- **CIS Docker.** No container is built or run.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: web`.
- **WCAG 2.2.** `accessibility` is not claimed. The forms label every input,
  the layout sets `lang`, and nothing is a `<div>` doing a button's job — a
  floor, not a claim.
- **Observability beyond the defaults.** Not claimed. The skeleton's `/up`
  health route and log channel are left as they are.

---

## Verdict

**MERGE.** One `high` fixed before the pull request, three `medium`, two
`low`, one `info`.

The three `medium` findings are omissions, each declared where a reader looks
and each listed under "Planned": no password change or reset, no registration
limit, and production values that live in the environment rather than in the
committed example. None is a control the blueprint claims and gets wrong.

`tier: official` is not available while `provenance: generated` (ADR 0011).
