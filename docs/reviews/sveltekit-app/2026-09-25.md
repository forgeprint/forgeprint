# sveltekit-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 and 2026-09-23
  (next re-check due 2026-12-21)
- Reviewer: Claude Code agent, `skills/blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
A server-rendered SvelteKit application on adapter-node: one page with a
server `load` and a form action validated in `$lib/server`, a root layout that
writes the head, a Content Security Policy, and a production server that
refuses to start without `ORIGIN`.

The manifest claims `project_type: web` and `requirements: [seo, testing, ci]`,
so the checklist was built from those: what reaches the browser, whether the
SEO claim is tested against built output, what the tests prove, and SSDF and
SLSA for the workflow. It does not claim `auth`, `accessibility` or
persistence, and `overview.md` says so under "What it is NOT for".

The single most important thing to know before building on it: the canonical
link and SvelteKit's cross-origin form check both depend on `ORIGIN`, and the
blueprint makes the server refuse to start without it. Removing that check to
"make deployment easier" reopens a Host-header problem the rest of the design
assumes is closed.

No `critical` or `high` findings. Four `low` and two `info`.

## Findings

### 1. `style-src` allows `'unsafe-inline'` — `low`

- **Where:** `blueprints/sveltekit-app/setup.md:102`, step 4
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**; OWASP ASVS
  5.0 **V3.4** (browser security mechanism headers)
- **What:** the policy gives scripts a per-response nonce and no
  `'unsafe-inline'`, but lets any inline style through.
- **Why it matters:** an injected `<style>` can restyle the page or exfiltrate
  attribute values through CSS selectors. It cannot run script, which is why
  this is `low`.
- **Mitigating:** Vite injects styles as `<style>` elements in development and
  Svelte transitions do at run time, so a nonce-only `style-src` breaks both.
  The comment in `vite.config.ts` and "Trade-offs made on your behalf" in
  `overview.md` say so.
- **Fix:** none now. A project that uses no transitions can drop
  `'unsafe-inline'` for production builds and let SvelteKit add style nonces.

### 2. Nothing limits how often the form can be posted — `low`

- **Where:** `blueprints/sveltekit-app/setup.md:336`, step 10
- **Standard:** OWASP ASVS 5.0 **V2.4.1** (anti-automation)
- **What:** the action accepts any number of posts from anybody.
- **Why it matters:** today nothing is stored or sent, so a flood costs a
  validation call. The first change a reader makes is to store the signup or
  email it, and at that moment the form becomes a spam and cost vector.
- **Mitigating:** disclosed in `overview.md` ("Abuse protection") and in
  `AGENTS.md` under "Adding persistence", at the place the reader will be when
  it starts to matter.
- **Fix:** none to the recipe. Add a limit when the action gains a side effect.

### 3. The id-only error response is not exercised by a test — `low`

- **Where:** `blueprints/sveltekit-app/setup.md:184`, step 6 (`handleError`)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**; OWASP ASVS 5.0 **V16** (security logging and error handling)
- **What:** `handleError` logs the full error with a random id and returns only
  `Internal error` and the id. The built-server tests cover a 404, not a thrown
  error.
- **Why it matters:** a later edit that returns `error.message` to the browser
  would pass every test.
- **Fix:** when the first route that can fail unexpectedly exists, add a
  built-server test that triggers it and asserts the body carries an id and no
  message.

### 4. The generated CI follows the Node 22 line rather than one release — `low`

- **Where:** `blueprints/sveltekit-app/setup.md:710`, step 17
- **Standard:** NIST SSDF SP 800-218 v1.1 **PO.3** (supporting toolchains); SLSA v1.2
  build track
- **What:** `node-version: '22'` resolves to the newest 22.x at run time.
- **Why it matters:** the runtime that builds the project can change between
  two runs of the same commit.
- **Mitigating:** the actions themselves are pinned by commit, every package is
  pinned by `package-lock.json` and installed with `npm ci`, and `engines`
  plus `engine-strict` refuse a Node older than 22.13. Following the minor line
  keeps security releases arriving, which a pinned patch would not.
- **Fix:** none required. A project that needs reproducible builds pins an
  exact version and updates it deliberately.

### 5. `npm audit` in the generated CI can fail on news, not on a change — `info`

- **Where:** `blueprints/sveltekit-app/setup.md:713`, step 17
- **Standard:** NIST SSDF SP 800-218 v1.1 **RV.1** (identify vulnerabilities)
- **What:** `npm audit --audit-level=high` fails the build when a high advisory
  is published against a locked dependency, even if the commit did not touch
  dependencies.
- **Why it is right anyway:** that is the point of the check. Recorded so a
  reader who sees a red build with no code change knows where to look.

### 6. `vite preview` needs `ORIGIN` too — `info`

- **Where:** `blueprints/sveltekit-app/setup.md:151`, step 6
- **Standard:** The Twelve-Factor App **III** (config)
- **What:** the start-up check applies to every non-development, non-build run,
  including `vite preview`.
- **Why it is right anyway:** one required setting, read from the environment
  in one place, with no production default. `README.md` and `AGENTS.md` name
  it.

## What was checked and found sound

- **Host header and origin (OWASP Top 10:2025 A01, A02; Twelve-Factor III).**
  `init` in `hooks.server.ts` refuses to start without `ORIGIN` and refuses one
  that is not a bare origin. The canonical link is built from `page.url.origin`,
  which adapter-node takes from `ORIGIN`. A test proves the refusal and another
  proves the canonical link comes from `ORIGIN` with the query string dropped.
- **Cross-site form posts (OWASP Top 10:2025 A01; ASVS 5.0 V3.5, browser origin separation).** SvelteKit's
  origin check is on, `AGENTS.md` rule 4 says not to widen it, and a
  built-server test proves a post with `Origin: https://example.com` gets 403.
- **Server-side validation (ASVS 5.0 V2.2).** Validation is in `$lib/server`,
  which SvelteKit refuses to bundle for the browser. The accepted topics are the
  same list the page renders, so a value the page never offered is refused;
  unit tests and a built-server test both prove it. A file sent in place of a
  text field is treated as empty. The length bound runs before the pattern, so
  the pattern never sees more than 254 characters.
- **Output encoding (ASVS 5.0 V1).** The only user input rendered back is the
  address, through Svelte's escaping; there is no `{@html}`.
- **What reaches the browser (OWASP Top 10:2025 A02; ASVS 5.0 V3.4).** No third-party script,
  font or stylesheet. The CSP is `default-src 'self'`, scripts need the
  response's nonce, `object-src 'none'`, `base-uri 'self'`, `form-action
'self'` and `frame-ancestors 'none'`; a test reads the header off the built
  server. `nosniff` and a referrer policy are set in `handle`.
- **Error handling (A10; ASVS V16).** Unexpected errors are logged in full
  with an id and the browser gets the id only (finding 3 is about the test, not
  the code). `App.Error` is typed to that shape.
- **SEO claimed and tested against the built output.** One title, a
  description, an absolute canonical link, Open Graph tags and `lang` are
  asserted on HTML fetched from `node build`, not on templates. The absence of
  a sitemap is disclosed.
- **Supply chain (OWASP Top 10:2025 A03; SSDF PS.3; SLSA v1.2).** The
  generator is `sv@0.17.1`, whose only dependency is pinned exactly and has
  none of its own; it reaches the network only for community add-ons, which the
  recipe does not use. Every project dependency is an exact version, the lock
  file is committed, CI installs with `npm ci`. The one advised transitive
  dependency (`cookie`, GHSA-pxg6-pf52-xh8x) is overridden to a fixed release,
  and the reason and the removal condition are written down. Vitest's
  component mode, which downloads a browser from outside the npm registry, is
  deliberately not set up.
- **The workflow (SSDF PO.3; SLSA v1.2).** Actions pinned by commit with the
  version in a comment, `permissions: contents: read`, `persist-credentials:
false`, a timeout, no secrets, and the same commands a developer runs
  locally.
- **Configuration (Twelve-Factor III).** One required setting, from the
  environment, checked once at start-up. No `.env` file is written and none is
  needed.
- **Observability (OWASP Top 10:2025 A09).** A liveness endpoint that depends
  on nothing, and error ids that join a browser report to a server log line.
  `AGENTS.md` says a readiness check goes beside it rather than into it.
- **Boundaries (hexagonal architecture; Clean Architecture's dependency
  rule).** Routes depend on `$lib/server`; `$lib/server` depends on nothing in
  `src/routes`. The framework enforces the browser/server line at build time.
- **Test strategy.** The tests prove the claims the blueprint makes: the head
  in the served HTML, the headers, the action's refusals over HTTP as a
  JavaScript-off browser sends them, the cross-origin refusal, and the
  missing-`ORIGIN` refusal. `requireAssertions` makes an empty test fail. The
  built-server tests ask the operating system for a free port and then start
  the server on it; if another process takes the port in between, the health
  wait or the content assertions fail loudly rather than passing.
- **Telemetry.** None to disable: `sv`, SvelteKit, Vite, Vitest, ESLint,
  Prettier and Tailwind collect none, and `overview.md` says so.

## Not applicable

- **Authentication, sessions and authorization (ASVS 5.0 V6, V7, V8).** Not
  claimed; "What it is NOT for" leads with it.
- **OWASP API Security Top 10.** `project_type` is `web`, and the only
  endpoint besides the page is a liveness check that returns a constant.
- **CIS Docker Benchmark.** No image is built and no container is run.
- **WCAG 2.2.** `accessibility` is not claimed. The form's labels, legend,
  `aria-invalid`, `aria-describedby` and skip link are good practice that no
  test verifies, and `overview.md` says exactly that.
- **Data protection and cryptography (ASVS 5.0 V11, V14).** Nothing is stored
  and no secret is used. The addresses submitted are held in memory for one
  request.
- **LLM, agentic and MCP references.** Not an agent.
