# ts-library — architecture and security review

- Date: 2026-09-23

- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first `lib`, and the first to carry `cd`.

A library has almost no runtime attack surface — no network, no storage, no
requests — so the review is really a supply-chain review, and that is the axis
on which this blueprint is the strongest in the catalog: it publishes from a
tag with provenance and no stored token, and it proves what the tarball
contains rather than assuming it.

The one thing worth arguing about is the example itself, and the argument is in
its favour.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. The transliteration map is a partial answer presented as a complete one — `low`

- **Where:** `blueprints/ts-library/setup.md:82` (step 4)
- **Standard:** the catalog's own rule that a claim must not be wider than
  what it does; ASVS 5.0, Validation (canonicalisation)
- **What:** fifteen characters are mapped — Turkish, German, Nordic, Polish.
  Greek, Cyrillic, Arabic, Han and everything else still fall through to the
  separator.
- **Why it matters:** the library will silently produce `''` for a title in a
  script it does not know, and an empty slug is a bug that surfaces as a
  routing error much later.
- **Mitigating:** both `README.md` and `AGENTS.md` state exactly which groups
  are handled and say the general answer is a transliteration library. The
  test `returns an empty string when nothing survives` documents the behaviour
  rather than hiding it.
- **Fix:** none required. A caller that cannot accept an empty slug should
  check for one, and that belongs in the caller. Recorded because the next
  person to extend this will reach for more characters rather than for the
  right abstraction.

### 2. `npm pack --dry-run --json` output is read with `grep` — `low`

- **Where:** `blueprints/ts-library/setup.md:314` (step 13) and `:317`
  (step 14)
- **Standard:** NIST SSDF, verification practices
- **What:** the two assertions that decide what ships match strings in npm's
  JSON output.
- **Why it matters:** these are the most valuable checks in the blueprint, and
  they depend on a format npm does not promise. If the key name changes, both
  assertions pass vacuously — `grep -c` returning 0 for sources would still
  satisfy step 14 when the field is simply absent.
- **Fix:** step 14 is the weaker of the two: it asserts an absence, so it
  cannot distinguish "no sources in the tarball" from "no such field". Reading
  the JSON with `node -e` and asserting on a parsed array would close it. Worth
  doing; not a blocker, because step 13 asserts a presence and would fail
  loudly if the shape changed.

### 3. Provenance requires the package to be published from this workflow, and nothing checks that — `info`

- **Where:** `blueprints/ts-library/setup.md:276` (step 10)
- **Standard:** SLSA v1.2, provenance; OWASP Top 10:2025 **A03**
- **What:** `npm publish --provenance` with `id-token: write` produces a signed
  statement about which commit and workflow built the package. If somebody
  publishes the same name from a laptop instead, npm accepts it — provenance is
  a property of a version, not a policy on the package.
- **Why it matters:** the blueprint teaches the right thing and cannot enforce
  it. npm's own trusted-publishing settings can, and that is a registry setting
  rather than a repository one.
- **Fix:** a sentence in `AGENTS.md` pointing at npm's trusted publishing
  configuration would complete the story. Recorded rather than added, because
  it is a claim about a registry UI that should be checked before it is
  written down.

## What was checked and found sound

- **No npm token is stored anywhere.** The release workflow uses OIDC
  (`id-token: write`), so the credential is minted per run and scoped to the
  workflow. This is the strongest supply-chain posture in the catalog, and it
  is the thing this project's own maintainer learned the hard way while
  releasing it by hand (SLSA v1.2; OWASP A03).
- **`prepublishOnly` builds and tests**, so a broken tag cannot publish.
- **What ships is asserted.** `npm pack --dry-run` runs in the recipe and the
  type declarations are checked for by name. A library whose `exports` map
  points at a `.d.ts` that `files` excludes is a package that type-checks for
  nobody, and it is invisible until a consumer reports it.
- **The tests run against `dist/`**, which is what a consumer receives — a
  suite that runs against sources can pass while the build is broken.
- **CI runs the floor and the current Node**, so `engines: >=20` means
  something rather than being a hope.
- **`exports` rather than `main`**, with `types` first in the condition order,
  and `sideEffects: false`.
- **Actions pinned by commit SHA** with the version in a comment; the release
  workflow's permissions are the two it needs and nothing more (least
  privilege).
- **Three tests guard the decision the code exists to make.** If somebody
  replaces the explicit map with normalise-and-strip — which looks equivalent
  — they fail. That is a test suite doing the job a comment cannot.
- **No runtime dependencies at all**, which is the smallest possible
  dependency surface for a consumer.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The package name is `@example/slugify`, a scope reserved for documentation.

## Not applicable

- **Authentication, authorization, session management (ASVS 5.0).** No server,
  no users, no requests.
- **OWASP API Security Top 10.** No API.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: lib`; nothing is exposed
  to a model.
- **CIS Docker.** No container.
- **Rate limiting, caching, migrations, transport security.** Nothing opens a
  socket or stores anything.

---

## Verdict

**MERGE.** Two `low`, one `info`, none blocking.

Worth saying plainly, because a review that only finds fault is not a review:
this blueprint is the best supply-chain story in the catalog. Publishing from a
tag with provenance and no stored token is what the rest of this project is
still working towards, and it arrived here first.

The action worth taking is step 14 — an absence asserted with `grep` is an
assertion that can pass for the wrong reason, and that is exactly the failure
mode this catalog spends most of its review effort on.

`tier: official` is not available while `provenance: generated` (ADR 0011).
