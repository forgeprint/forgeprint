# godot-game — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 and 2026-09-23
  (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is a 2D desktop game on Godot 4.7.2 in C#, with the rules in a plain .NET
library and no network access, user data or server anywhere in it.

The manifest claims `requirements: [testing, ci]`, so this is mostly a
test-strategy review — does what is tested match what `overview.md` says is
tested — plus the supply-chain questions a CI workflow and an MSBuild SDK from
NuGet raise. The single most important thing for a reader: **nothing in the
recipe or in CI has ever started the engine.** The game assembly compiles
against the real Godot API, the rules are tested, and the project files are
checked against the code; whether the scene loads and the game plays is
unproven. The blueprint says so in `overview.md`, `AGENTS.md`, the CI
workflow's header and `CHANGELOG.md`, which is why that is a `medium` finding
rather than a blocker.

No critical or high findings.

## Findings

### 1. The engine never runs, so the scene and the game are unproven — `medium`

- **Where:** `blueprints/godot-game/setup.md:550` (step 15, `scenes/Main.tscn`)
  and `:480` (step 14, `scripts/Main.cs`)
- **Standard:** NIST SSDF SP 800-218 v1.1, PW.8 (test executable code to
  verify it meets its requirements) — the skill's "do the tests prove the
  claim the blueprint makes"
- **What:** the scene file is written by hand in Godot's text format and the
  node scripts are compiled, but no step loads the scene or calls `_Ready`. The
  engine binary is distributed from GitHub releases and godotengine.org, which
  a recipe may not download from.
- **Why it matters:** a malformed line in `Main.tscn`, a node path that
  `GetNode` cannot find, or a runtime-only failure would pass every check here
  and appear the first time somebody presses F5.
- **Fix:** none within the catalog's registry-only rule. What can be checked
  without the engine is: `ProjectFileTests` (step 19) verifies the main scene
  exists, every attached script exists and declares its `partial` class under
  its file name, and the input actions in `project.godot` equal the ones the
  code reads, in both directions. The rest is disclosed in `overview.md` under
  "What CI can prove, and what it cannot". Recorded so the disclosure survives
  the first extension of the tests.

### 2. The game targets .NET 8, whose support ends on 2026-11-10 — `medium`

- **Where:** `blueprints/godot-game/setup.md:388` (step 11, `Game.csproj`) and
  `:80` (step 5, `Game.Rules.csproj`)
- **Standard:** OWASP Top 10:2025 A03 Software Supply Chain Failures (a
  component past its support window gets no security fixes)
- **What:** `GodotSharp` 4.7.2 targets `net8.0`, and the game and the rules
  follow it. Seven weeks after this review the framework is out of support.
- **Why it matters:** a shipped game would run on an unpatched runtime, and a
  later .NET SDK may report the end-of-life framework as a warning, which
  `TreatWarningsAsErrors` turns into a failed build — the weekly recipe run
  would then go red without anything in the blueprint changing.
- **Fix:** move the game and the rules to the framework Godot's own packages
  target once they move; not earlier, because a newer framework than the
  engine's is a reported source of load failures at run time that no test here
  would catch. `AGENTS.md` ("Versions move together") and `overview.md` say
  both. The weekly `setup-test` run is the alarm.

### 3. Build logic and packages come from NuGet without a lock file — `low`

- **Where:** `blueprints/godot-game/setup.md:388` (step 11,
  `Sdk="Godot.NET.Sdk/4.7.2"`) and `:586` (step 17)
- **Standard:** OWASP Top 10:2025 A03; SLSA v1.2
- **What:** every direct package and the MSBuild SDK are pinned exactly, and
  NuGet verifies each package's repository signature. There is no
  `packages.lock.json`, so the transitive set is whatever nuget.org serves at
  the first restore. `Godot.NET.Sdk` is an MSBuild SDK: its targets run at
  build time with the developer's permissions.
- **Why it matters:** the same trade-off as the other .NET blueprints, with one
  addition — an MSBuild SDK is code that runs, not only a library that links.
  It is published by the Godot project (MIT, repository and commit in its
  nuspec).
- **Fix:** none now. A lock file was left out because `Godot.NET.Sdk` adds
  `GodotSharpEditor` only in the `Debug` configuration, which makes what a
  lock records depend on the configuration restored; `overview.md` states the
  trade-off. Worth revisiting if the SDK stops conditioning references on the
  configuration.

### 4. The boundary test reads the rules project file, not the evaluated project — `info`

- **Where:** `blueprints/godot-game/setup.md:922` (step 20, `BoundaryTests.cs`)
- **Standard:** Clean Architecture (the dependency rule); hexagonal
  architecture (ports and adapters)
- **What:** one test reads `Game.Rules.csproj` for Godot package or project
  references; the other checks the compiled assembly's references. A
  `PackageReference` added through `Directory.Build.props`, or through a new
  intermediate project, would not appear in the first, and an unused reference
  does not appear in the second.
- **Why it matters:** it is a way round the boundary, though not one anybody
  takes by accident: a Godot type actually used in the rules does appear in
  the assembly's references and fails the second test. A mutation run while
  writing the blueprint (a `GodotSharp` reference added to the rules project)
  failed the first test as intended.
- **Fix:** none needed at this scope. If the solution grows more projects,
  check `project.assets.json` of the rules project instead of its file.

## What was checked and found sound

- **The boundary is real and points one way** (Clean Architecture's dependency
  rule; ports and adapters). `src/Game.Rules` has no Godot reference; the
  scripts depend on it and never the reverse; `System.Numerics.Vector2` is
  converted to `Godot.Vector2` in one place, `Main.Present`. Two tests hold the
  line (finding 4 notes their edge).
- **The rules are deterministic.** `System.Random` and the frame's seconds are
  arguments; a test replays 600 frames twice from the same seed and requires
  the same state.
- **Exceptional conditions are handled where they occur** (OWASP Top 10:2025
  A10). A long frame is clamped to `MaxStepSeconds` (step 9, line 221) so the
  player cannot pass through a coin; a `NaN`, infinite or negative frame time
  moves nothing (line 248); `Settings` refuses an arena smaller than the
  player and a game that cannot be won (step 6, line 125). Each has a test. A
  renamed node makes `GetNode` throw in `_Ready`, which fails loudly at
  startup rather than silently in `_Process`.
- **Warnings are errors in all three projects**, with nullable reference types
  on (step 2). Godot's own source generators already refuse a missing
  `partial` (GD0001, checked by a mutation while writing the blueprint); the
  class-name-equals-file-name rule, which compiles when broken, is tested.
- **The export configuration is exercised** as far as it can be without the
  engine: step 26 builds `ExportRelease` and asserts the editor-only
  `GodotSharpEditor.dll` is not in its output.
- **CI** (SLSA v1.2, OWASP Top 10:2025 A03): actions pinned by commit SHA with
  the version in a comment, `permissions: contents: read`,
  `persist-credentials: false` (step 22, line 1028). The SHAs are the ones
  this repository's own `setup-test` workflow uses. It runs the same format,
  build, test and export-configuration build as the recipe.
- **Secrets** (CLAUDE.md §5b): the game reads no configuration and holds none.
  `.gitignore` excludes `.godot/`, where the editor keeps export credentials
  such as keystore passwords, and the "After setup" note in `setup.md` says which
  export file is safe to commit.
- **Nothing downloaded outside NuGet.** No engine, no export templates, no art.
  The nodes draw themselves.
- **No secrets, no personal data, no employer information** in the blueprint.

## Not applicable

- **Authentication, session management, access control** (ASVS 5.0 V6–V8):
  no users, no server, no network.
- **OWASP API Security Top 10:** not an API.
- **Containers** (CIS Docker Benchmark): no image.
- **Data protection, cryptography** (ASVS 5.0): nothing is stored or sent.
  `System.Random` places coins; it is not used where guessing the next number
  would matter.
- **Accessibility** (WCAG 2.2): not claimed; `overview.md` says keyboard-only
  play is the whole claim.
- **What reaches the browser:** Godot 4 cannot export C# to the web, and
  `platforms` does not list `web`.
