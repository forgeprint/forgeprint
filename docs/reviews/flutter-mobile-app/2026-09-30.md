# flutter-mobile-app — architecture and security review

- Date: 2026-09-30
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check
  due 2026-12-21), plus OWASP MASVS and MASTG, which that list still does not
  carry — see "Standards used that the list lacks" below
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011,
CLAUDE.md §5c). The catalog's first Dart blueprint and its third `mobile`
one: a Flutter 3.47.5 app with state in a Riverpod 3 `Notifier`, navigation
through `go_router` 18 behind typed route objects, the app's rules in plain
Dart with a test that keeps the framework out of them, 36 tests including
Flutter's accessibility guideline matchers, `very_good_analysis` 11.0.0 with
infos fatal, and `flutter build web --release` as the build proof.

The most important thing to know before building on it: every test runs on
the Dart VM against a fake window, and the only artifact the recipe produces
is a web bundle. Nothing here compiles, signs or runs a mobile package.
`overview.md:49` says so under "What CI cannot prove".

The manifest claims `tier: community` and `provenance: generated`. No
`critical` or `high` finding is open.

## Findings

### 1. The generated Android project signs release builds with the debug key — `medium`

- **Where:** `blueprints/flutter-mobile-app/setup.md:19` (step 1,
  `flutter create`); the file it generates,
  `android/app/build.gradle.kts`, gives the `release` build type
  `signingConfig = signingConfigs.getByName("debug")`
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**; OWASP
  MASVS **MASVS-RESILIENCE-1** (the app verifies the integrity of its own
  code and signing is the platform mechanism for it)
- **What:** the recipe scaffolds with `flutter create` and does not touch the
  Android module. Flutter's template wires the release build type to the
  debug keystore so that `flutter run --release` works on a connected device.
  A reader who runs `flutter build apk --release` therefore gets an APK
  signed with a key that ships with every Android SDK, whose password is
  published.
- **Why it matters:** such an APK is authenticated by nothing. Anybody can
  produce an update that the platform accepts as the same app, and Play will
  not take it at all — the failure the reader sees is a rejection, and the
  failure they do not see is a sideloaded build nobody can trust.
- **Mitigating, and why this is `medium` rather than `high`:** the recipe
  never builds an Android package, the blueprint does not claim it does, and
  the gap is now stated where a reader looks — `overview.md:63` names the
  line and says the key is public, `overview.md:83` makes replacing it step
  one of an Android build, and `AGENTS.md:172` repeats it as a rule. The
  generated `android/.gitignore` already refuses `key.properties`,
  `**/*.keystore` and `**/*.jks`, so the safe path does not also require
  remembering to ignore the key.
- **Fix (before any Android artifact leaves a machine):** replace the release
  `signingConfig` with one loaded from a `key.properties` outside version
  control. Not done in the recipe because removing the template's line breaks
  `flutter run --release`, and supplying a keystore would mean generating key
  material inside a setup recipe.

### 2. `testing` is proved on the Dart VM only; nothing runs on a device, and there are no goldens — `medium`

- **Where:** `blueprints/flutter-mobile-app/setup.md:1152` (step 28,
  `flutter test --coverage`); no `integration_test/` directory and no
  `matchesGoldenFile` anywhere
- **Standard:** OWASP MASTG v2.0.0, whose testing techniques for Android and
  iOS rest on dynamic analysis against a device or emulator; and the review
  skill's rule that a claim wider than its verification is a finding
- **What:** `requirements: [testing]` is backed by 36 tests that all run in
  `flutter test`. The widget tests drive the real screens, the real router
  and the real notifier, but through Flutter's test binding: no platform
  channels, no real fonts, no compositor, no input method, no frame budget.
- **Why it matters:** `resolve` matches on the word. A reader expecting
  device coverage gets VM coverage.
- **Mitigating:** the gap is disclosed at `overview.md:49` ("On-device
  behaviour", "iOS", "Android packaging", "What it looks like") and again in
  `AGENTS.md` under what the project does not do, with the next step named in
  both. What the tests do assert is behaviour rather than compilation: a
  refused blank title, a trimmed title, a toggled row, a count that follows
  it, four kinds of bad link, and four accessibility guidelines against the
  rendered tree.
- **Fix (when the app has device-only behaviour):** `integration_test` run
  with `flutter test integration_test` on an emulator, on a runner that has
  the Android SDK and a system image; a tool that can drive native dialogs
  for any flow that meets one. Recorded under "Planned" in the CHANGELOG.

### 3. `flutter.minSdkVersion` is 24, so the app would install on Android 7 — `low`

- **Where:** `blueprints/flutter-mobile-app/setup.md:19` (step 1); the
  generated `android/app/build.gradle.kts` reads `minSdk =
flutter.minSdkVersion`, which is 24 in Flutter 3.47.5
- **Standard:** OWASP MASVS **MASVS-CODE-1** — "The app requires an
  up-to-date platform version."
- **What:** the floor is inherited from the toolchain rather than decided.
  Android 7.0 stopped receiving security patches years ago.
- **Why it matters:** for an app that stores nothing and reaches no network,
  very little. For the app this becomes — a token, a name, a photo — an
  unpatched platform undermines every storage and transport control above it.
- **Mitigating:** `overview.md:63` says `minSdk` is a template default and
  not a decision, and lists deciding it as part of the first Android build.
  The app today has nothing to protect.
- **Fix:** set `minSdk` explicitly the moment the app stores or transmits
  anything; MASVS-CODE-1 is the argument to cite in that discussion.

### 4. The web build has no content security policy, and a reader may deploy it — `low`

- **Where:** `blueprints/flutter-mobile-app/setup.md:1155` (step 29,
  `flutter build web --release`); the generated `web/index.html` loads
  `flutter_bootstrap.js` and declares no CSP
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** `flutter build web` produces a deployable directory. It carries
  Flutter's default `index.html`, which sets no `Content-Security-Policy` and
  registers a service worker.
- **Why it matters:** the blueprint calls this a build proof, but the output
  is a static site somebody can upload. Served without a policy and without
  the usual response headers, it is one third-party script away from being
  somebody else's page.
- **Mitigating:** `overview.md` states plainly that the web build is a
  compile proof and not a product, and names `nextjs-fullstack-app`,
  `sveltekit-app` and `astro-content-site` for readers whose users are on the
  web. Headers are the server's job, not the bundle's, which is why this is
  `low` and not higher.
- **Fix:** if the web target becomes a product, add a CSP and the rest of the
  response headers at the host, and re-review — Flutter Web's CanvasKit
  renderer needs its WebAssembly and font sources allowed explicitly.

### 5. Android backup is on by default, and the app will not always store nothing — `low`

- **Where:** `blueprints/flutter-mobile-app/setup.md:19` (step 1); the
  generated `AndroidManifest.xml` sets no `android:allowBackup`, so the
  platform default of `true` applies
- **Standard:** OWASP MASVS **MASVS-STORAGE-2** (no sensitive data leaves the
  app unintentionally)
- **What:** anything the app writes to its private storage would be copied to
  the user's cloud backup and restored onto another device.
- **Why it matters:** today the app writes nothing, so there is nothing to
  copy. The first feature that adds `shared_preferences` or a database
  changes that silently, because the manifest does not have to be touched for
  it to happen.
- **Mitigating:** `AGENTS.md:105` makes this one of the two storage rules and
  names the decision as part of adding storage, and `overview.md:63` lists
  the manifest defaults as defaults rather than decisions.
- **Fix:** decide `allowBackup` and `dataExtractionRules` in the same change
  that introduces storage, not after.

### 6. `riverpod_lint` is not enabled, so two of the state rules are unenforced — `info`

- **Where:** `blueprints/flutter-mobile-app/setup.md:156` (step 7,
  `analysis_options.yaml`)
- **Standard:** the catalog's own
  `experts/flutter-mobile-engineer/checklists/analysis-gate.md` AG7
- **What:** the expert asks for the chosen state library's lint.
  `riverpod_lint` 3.1.9 is published and depends on `analysis_server_plugin`,
  the newer analyzer plugin mechanism; `dart.dev`'s analysis page still
  documents only the legacy `analyzer: plugins:` form and calls it legacy.
- **Why it is `info`:** the blueprint states the omission and its reason in
  `overview.md` under the trade-offs, and the rules the plugin would enforce
  — providers not created inside `build`, `ref.watch` in `build` and
  `ref.read` in callbacks — are written as rules in `AGENTS.md` instead. A
  plugin that silently does not run would be worse, because it would read as
  coverage.

### 7. CI restores a dependency cache on pull requests — `info`

- **Where:** `blueprints/flutter-mobile-app/setup.md:1065` (step 24,
  `cache: true` on `subosito/flutter-action`)
- **Standard:** SLSA v1.2 build track (what the build trusts)
- **What:** the action restores the Flutter SDK and the pub cache from
  GitHub's cache. GitHub scopes cache writes by branch, so a pull request
  cannot write a cache the default branch reads. Nothing to fix; recorded
  because a cache is an input to the build.

## What was checked and found sound

- **Supply chain (A03, SSDF, SLSA):** every direct dependency is pinned to an
  exact version with no caret — `flutter_riverpod: 3.4.3`, `go_router:
18.0.2`, `intl: 0.20.3`, `very_good_analysis: 11.0.0`
  (`setup.md:22`) — and `pubspec.lock` is committed (`setup.md:150`), which
  for pub means a `sha256` per resolved package, direct and transitive. That
  is per-artifact integrity, not only a coordinate. The Flutter SDK itself is
  pinned in the workflow (`setup.md:1065`), and Dependabot proposes moves for
  both ecosystems (`setup.md:1125`).
- **CI trust boundary (SSDF PO.3, SLSA):** actions pinned by commit SHA and
  checked against their tags on 2026-09-30, `permissions: contents: read`,
  `persist-credentials: false`, a concurrency group and a timeout.
- **Secrets (CLAUDE.md §5b, MASVS-STORAGE-1):** no key, token, password or
  connection string anywhere in the recipe; nothing is read from
  `--dart-define` or `String.fromEnvironment`; `AGENTS.md:112` states that
  the app bundle is not a place for a secret and that `--obfuscate` renames
  rather than encrypts.
- **Untrusted input (MASVS-CODE-4, MASVS-PLATFORM-1):** a route parameter is
  the app's only external input, and it is parsed in exactly one place
  (`setup.md:302`, `parseTaskDetailRoute`) with `int.tryParse` and a range
  check, never `int.parse` on a `!`-asserted value. Unparseable and unmatched
  locations both reach `MissingScreen` through `errorBuilder`
  (`setup.md:565`), and four tests cover `/tasks/abc`, `/tasks/-1`,
  `/tasks/9999` and `/nowhere`, two of them asserting that no exception was
  thrown. This is the control the `state-and-routing` checklist's SR6 and
  SR7 ask for.
- **Error handling (A10):** the two failures the app has are values, not
  exceptions — a refused title is a `TitleProblem` shown from a localised
  string, and a missing task is a `null` from `findTask` shown as a sentence.
  Both are tested.
- **Boundaries (Clean Architecture, hexagonal):** `lib/src/rules` imports
  nothing from the framework, and `setup.md:794` is the test that enforces
  it by reading every file in the folder — and fails rather than passes when
  the folder is empty, which is the failure mode that makes most such tests
  worthless. Dependency direction runs one way: `ui` → `state` → `rules`,
  and `rules` depends on nothing.
- **Configuration (Twelve-Factor III):** there is none to get wrong. The app
  reads no environment, and the one generated artifact — the localisations —
  is regenerated and diffed in CI (`setup.md:1065`) so a stale copy fails.
- **Test strategy:** the tests prove the claims rather than the compile. The
  notifier is exercised through `ProviderContainer.test()` with no widget
  tree; the screens are driven through the real router and the real provider
  scope; coverage is asserted against a named source file
  (`setup.md:1152`), so a run that tested nothing would fail the
  verification rather than pass it.
- **Accessibility, as far as a test can assert it:** `setup.md:912` runs
  `labeledTapTargetGuideline`, `androidTapTargetGuideline`,
  `iOSTapTargetGuideline` and `textContrastGuideline` against the rendered
  screen, and the theme (`setup.md:606`) raises Material 3's 40-pixel button
  to 48 because the matcher refused the smaller one. The blueprint does not
  claim `requirements: accessibility`, so this is not scored against WCAG
  2.2 — it is recorded because the claim that is _absent_ is nonetheless
  partly backed, which is the safe direction for the mismatch to run.
- **Localisation claim:** `requirements` does not list `i18n`, and
  `overview.md` says why — one locale proves no translation. The
  infrastructure is there; the word is not claimed. That is the correct way
  round.
- **Recipe safety (rule 20):** `forgeprint lint-setup` is clean. No pipe from
  a download, no privilege escalation, no recursive delete, no write outside
  the project, and the only network host any step reaches is `pub.dev`.
- **Analyzer as a gate:** `flutter analyze` with infos fatal and no
  `--no-fatal-infos` (`setup.md:1149`), on `very_good_analysis` 11.0.0 pinned
  to the exact version, with `strict-casts`, `strict-inference` and
  `strict-raw-types` on — the `analysis-gate` checklist's AG1, AG3, AG4 and
  AG8. No `// ignore:` and no `ignore_for_file` in any hand-written file
  (AG6). `dart format --set-exit-if-changed` is a separate gate
  (`setup.md:1146`), and it is a check rather than a reformat.

## Not applicable

- **OWASP API Security Top 10, ASVS V2/V3:** no API, no authentication, no
  session, no token. `overview.md` says so under "What it is NOT for".
- **MASVS-AUTH, MASVS-CRYPTO, MASVS-NETWORK:** no credentials, no keys, no
  cryptography, and no network call at all — the app requests no Android
  permission, including `INTERNET`.
- **MASVS-PRIVACY:** nothing is collected, stored or sent.
- **MASVS-RESILIENCE beyond finding 1:** no anti-tampering claim is made, and
  none is expected of a blueprint.
- **CIS Docker Benchmark:** no container.
- **OWASP LLM / Agentic Top 10, MCP guidance:** not an agent.
- **WCAG 2.2 / EN 301 549:** `requirements` does not claim `accessibility`,
  so the guideline matchers above are a bonus rather than a verification
  target.

## Standards used that the list lacks

`docs/review-standards.md` still has no mobile row — the same gap the
`android-compose-app` review of 2026-09-25 recorded, and it is now the second
review to need it. This review cites two, read on 2026-09-30, and the
2026-12-21 re-check should add them:

- **OWASP MASVS** — the control set used above (MASVS-CODE, -STORAGE,
  -PLATFORM, -NETWORK, -PRIVACY, -RESILIENCE). Latest tagged release v2.1.0
  (2024-01-18); the control text cited is the current `controls/` directory
  of `OWASP/owasp-masvs`.
- **OWASP MASTG** — v2.0.0 (2026-06-30), the first stable release of the
  refactored testing guide.

A Dart or Flutter platform row would help too, in the way the list already
carries one for ASP.NET Core: the analyzer's strict modes, the formatter and
the accessibility guideline matchers are all vendor documentation this review
leaned on, and none of them has a citable row today.

## For the linter

Nothing this review found could have been found by a rule.
`forgeprint lint-setup` reports no problem on this recipe, and the two
configuration defects in findings 1 and 3 live in files `flutter create`
generates rather than in `setup.md`, so no rule reading the recipe could see
them. If that class of finding recurs, the rule worth writing is one that
reads the _generated_ tree after `test-setup`, which is a change to
`test-setup` and belongs in its own pull request.
