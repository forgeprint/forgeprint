# nuxt-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `skills/blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is the catalog's first Vue blueprint: a server-rendered Nuxt 4 application
with one public Nitro route and no users, no database and no state.

The attack surface is one POST endpoint and the server-rendered HTML. Both are
handled with more care than a starter usually gets — the route refuses an
oversized or length-less body before reading it, validates with a schema, and
the canonical URL is built from configuration and tested against a forged
`Host` header. What a reader should know before building on it is what it does
not do: no authentication, no security headers, and `seo` means the tags the
tests assert, not a sitemap.

The manifest claims `tier: community` and `provenance: generated`. No
`critical` or `high` findings are open.

## Findings

### 1. No security response headers — `low`

- **Where:** `blueprints/nuxt-app/setup.md:68` (step 2, `nuxt.config.ts`)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** nothing sets `Content-Security-Policy`, `X-Frame-Options` or
  `Referrer-Policy`; Nuxt sends none by default.
- **Why it matters:** `project_type: web` — the page can be framed, and
  nothing limits what scripts it may load if one is ever injected. Today there
  is no third-party script and all interpolation is Vue text binding, which
  escapes, so there is nothing to inject into.
- **Mitigating:** disclosed in `overview.md` under "What it is NOT for", with
  the reason a CSP is not a one-liner here: Nuxt inlines
  `window.__NUXT__.config` as a script, so a real policy needs nonces or
  hashes.
- **Fix:** `routeRules: { '/**': { headers: { ... } } }` for the static
  headers, and a nonce-based CSP once the project knows its third parties. A
  follow-up, not a blocker.

### 2. `seo` is narrower than the word — `low`

- **Where:** `blueprints/nuxt-app/manifest.yaml:15` against
  `setup.md:488` (step 17)
- **Standard:** the review-standards rule for `requirements: [seo]` — whether
  the claim is tested against the built output rather than the templates
- **What:** the tests assert one title, a description of twenty or more
  characters, an absolute canonical URL and the Open Graph tags, in the HTML
  the production build sends. There is no sitemap, no `robots.txt`, no
  structured data.
- **Why it matters:** `resolve` matches on `requirements`.
- **Mitigating, and why this is `low`:** what is claimed is tested against the
  built server's output, which is the bar the standards set; and the gap is
  disclosed in `overview.md` ("All of SEO"). With one page there is nothing
  for a sitemap to list.
- **Fix:** none now. Add a sitemap when a second page arrives.

### 3. `siteUrl` defaults to a domain nobody owns — `low`

- **Where:** `blueprints/nuxt-app/setup.md:91` (step 2)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**;
  Twelve-Factor III
- **What:** `runtimeConfig.public.siteUrl: 'https://example.com'`, from which
  every canonical URL is built.
- **Why it matters:** deployed unchanged, every page tells crawlers its
  canonical home is a domain it does not control.
- **Mitigating:** it is overridable from the environment
  (`NUXT_PUBLIC_SITE_URL`), which the generated `README.md` and `AGENTS.md`
  both say to set; `example.com` is reserved by RFC 2606. The same finding and
  the same resolution as `astro-content-site`.
- **Fix:** none; a check that fails on the placeholder would fail the
  blueprint's own CI.

### 4. The route has a size limit and no rate limit — `info`

- **Where:** `blueprints/nuxt-app/setup.md:232` (step 8)
- **Standard:** OWASP API Security Top 10 2023 **API4 Unrestricted Resource
  Consumption**
- **What:** a body over 1024 bytes is refused with 413, and a request with no
  `Content-Length` with 411, both before h3 buffers anything. Nothing limits
  how often the route may be called.
- **Why it matters:** the route is stateless and does constant work, so the
  missing rate limit costs nothing today. A route that calls a paid upstream
  or writes to storage would need one.
- **Fix:** none in the code. `AGENTS.md`'s checklist for a new API route says
  that a route that costs something per call needs a rate limit this
  blueprint does not provide.

### 5. Validation errors are returned to the caller — `info`

- **Where:** `blueprints/nuxt-app/setup.md:255` (step 8)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**
- **What:** h3 turns the thrown `ZodError` into a 400 whose body carries the
  issue list (path, code, limit). In production Nitro sends no stack trace.
- **Why it matters:** it reveals the schema's shape, which the form already
  reveals. Nothing else leaks. The form shows a fixed message rather than the
  server's.
- **Fix:** none.

### 6. The build pins its direct dependencies, not what they fetch — `info`

- **Where:** `blueprints/nuxt-app/setup.md:25` (step 1)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** every direct dependency is an exact version and there is no
  lockfile, so transitive dependencies resolve at install time; the generated
  CI uses `npm install` accordingly. `postinstall` runs `nuxt prepare`, which
  is Nuxt's own code from a pinned version.
- **Why it matters:** the same trade-off every blueprint here carries.
- **Fix:** none. Recorded so the next reviewer does not raise it again. The
  `h3@1.15.11` pin is part of this story and is explained in `AGENTS.md`: it
  keeps npm from hoisting the h3 2 that `@nuxt/eslint` pulls in, which
  otherwise breaks `@nuxt/test-utils`.

## What was checked and found sound

- **Input validation happens on the server, before use** (OWASP Top 10:2025
  A05 Injection; ASVS 5.0 validation chapter). `readValidatedBody` with a zod
  schema; the handler body cannot see an unvalidated value. The e2e suite
  proves 200, 400 for an empty name, 400 for a body that is not JSON, and 413.
- **The size check precedes the read.** Checking `Content-Length` is enough
  because Node's HTTP parser holds a request to the length it declares; a
  chunked request without one is refused (411) — checked by hand against the
  built server during authoring.
- **The canonical URL cannot be steered by the request** (A02 Security
  Misconfiguration: trusting the `Host` header is how a cached page ends up
  advertising somebody else's origin). It is
  built from configuration; an e2e test sends a forged `Host` over `node:http`
  — deliberately not `fetch`, which silently replaces the header — and the
  recipe repeats the check with `curl` against the production build. A unit
  test proves a `//host` path cannot change the host.
- **One place writes SEO tags, and its type requires both fields**, so a page
  without a description fails `nuxt typecheck` — verified during authoring by
  deleting one.
- **The SEO claim is tested against output, not templates**: the e2e suite
  reads the HTML the production build sends, and the recipe reads it again
  from `node .output/server/index.mjs`.
- **Nothing reaches a third party.** No analytics, fonts, CDNs or tag
  managers; `telemetry: false` keeps Nuxt from loading its telemetry module at
  all (confirmed in `nuxt`'s source: the module is only added when the option
  is not `false`), and the CI workflow also sets `NUXT_TELEMETRY_DISABLED`.
  Devtools are off.
- **The recipe's server listens on loopback, on a port the OS chose**, and is
  stopped by process id. The built server treats port 0 as unset and falls
  back to 3000; the recipe asks for a free port instead of trusting it.
- **The generated CI** pins `actions/checkout` and `actions/setup-node` by
  commit SHA (the current v7.0.1 and v7.0.0 releases, checked against their
  tags), grants `contents: read` only, and sets `persist-credentials: false`
  (SLSA v1.2 build track; A03).
- **Configuration from the environment** (Twelve-Factor III): the one setting
  that must change per deployment is a runtime config key with an environment
  override; there is no secret anywhere, so there is nowhere to put one.
- **Boundaries hold at the size this is.** `app/` and `server/` do not import
  each other; the shared schema and `canonicalUrl` live in `shared/`, which
  uses no framework auto-imports and is unit-tested in plain Node (hexagonal
  ports and adapters, in its smallest form: the pure function is separate from
  the composable that feeds it request state).
- **Error handling fails safe** (A10). Invalid input is a 400 before the
  handler runs; the form catches a failed request and shows a fixed message;
  production errors carry no stack.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The only hosts named are `example.com`, `attacker.invalid` and loopback.

## Not applicable

- **Authentication, session management, access control (ASVS 5.0).** No
  users; `overview.md` says so first.
- **Database, migrations, multi-tenancy.** None claimed, none present.
- **OWASP LLM 2025, Agentic 2026, MCP guidance.** No model, no tools.
- **CIS Docker.** No container.
- **WCAG 2.2.** `accessibility` is not claimed, and `overview.md` says so. The
  form's input has a label and results are announced through `role="status"`
  and `role="alert"`, but none of that is a claim.
- **Observability (A09).** Not claimed. Nitro logs unhandled errors to the
  console; there is no health endpoint, and the home page serves as one.

---

## Verdict

**MERGE.** Three `low`, three `info`, nothing above. The two worth carrying
forward are the missing security headers — disclosed, and not a one-liner in
Nuxt because of the inline config script — and the rate limit a second,
costlier route would need.

`tier: official` is not available while `provenance: generated` (ADR 0011).
`tier: verified` is available the day a maintainer runs the setup themselves.
