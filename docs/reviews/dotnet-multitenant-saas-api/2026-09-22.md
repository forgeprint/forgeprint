# dotnet-multitenant-saas-api — architecture and security review

- Date: 2026-09-22
- Blueprint version: 1.0.4
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **CHANGES** — findings closed the same day; see _Resolution_

## Summary

An ASP.NET Core 10 SaaS API whose tenant isolation lives in the data layer: the
tenant comes from a `tenant_id` claim on a validated token and from nowhere
else, a global query filter scopes every read, and `SaveChanges` stamps writes
and refuses one carrying somebody else's tenant. That design is right, and the
tests prove the parts that matter.

The two findings are both in the layer **above** that design — the layer that
decides who gets to reach it. One of them is the same fault
`dotnet-web-api` had, and the other is a near-miss that looks correct in a
diff: the blueprint sets the _default_ authorization policy where it means the
_fallback_ policy, so an endpoint that declares no authorization at all is
public. `/customers` declares none.

The manifest claims `tier: official`. Two `high` findings are open, so
**rule 23 blocks that tier** until they are closed.

## Findings

### 1. `SetDefaultPolicy` does not cover an endpoint that declares nothing — `high`

- **Where:** `blueprints/dotnet-multitenant-saas-api/setup.md:496` (step 20,
  `Program.cs`), and the endpoint at `setup.md:523`
- **Standard:** OWASP API Security Top 10 2023, **API5:2023 Broken Function
  Level Authorization**; OWASP Top 10:2025 **A01 Broken Access Control**
- **What:** the recipe writes

  ```csharp
  builder.Services
      .AddAuthorizationBuilder()
      .SetDefaultPolicy(new AuthorizationPolicyBuilder()
          .RequireAuthenticatedUser()
          .RequireClaim(TenantResolutionMiddleware.ClaimType)
          .Build());
  ```

  with the comment _"A request without a tenant claim is rejected before it
  reaches an endpoint, so no endpoint has to remember to check."_ That is what
  `SetFallbackPolicy` does. `SetDefaultPolicy` sets the policy used by
  `[Authorize]` and `.RequireAuthorization()` **when they are present without a
  named policy**; it does nothing for an endpoint that carries no authorization
  metadata at all. `/customers` carries none.

- **Why it matters:** the blueprint's central claim — that tenancy is enforced
  rather than remembered — is not implemented at the point where it is claimed.
  Today the damage is limited: an anonymous request to `/customers` reaches the
  data layer, `TenantContext.TenantId` throws because nothing resolved a
  tenant, and the caller gets a 500 rather than another tenant's rows. That is
  luck, not design — it depends on every future endpoint touching
  `AppDbContext`. The first status, config or metrics endpoint somebody adds
  will be genuinely public, and `AGENTS.md` and the 1.0.0 CHANGELOG both tell
  them it will not be.
- **Fix:** `SetFallbackPolicy(...)` with the same policy, and keep
  `SetDefaultPolicy` too so that a bare `.RequireAuthorization()` means the
  same thing. Then make `/customers` prove it by leaving it unmarked, and add a
  test that an anonymous request to it is **401** — which today it is not.

### 2. An unset audience turns audience validation off — `high`

- **Where:** `blueprints/dotnet-multitenant-saas-api/setup.md:487` (step 20)
- **Standard:** OWASP API Security Top 10 2023, **API2:2023 Broken
  Authentication**; OWASP ASVS 5.0, Self-contained Tokens chapter
- **What:**

  ```csharp
  options.Audience = builder.Configuration["Oidc:Audience"];
  options.TokenValidationParameters.ValidateAudience =
      !string.IsNullOrEmpty(options.Audience);
  ```

  `Oidc:Audience` has no default and is not checked. Missing means audience
  validation is off.

- **Why it matters:** identical code to `dotnet-web-api` 1.0.4, and worse in
  this context. This service derives _which tenant's data you see_ from a claim
  inside the token. With audience validation off, any token that authority
  issued is accepted — including one minted for a different application, by a
  different team, with a `tenant_id` claim of its own. The isolation that the
  whole blueprint is built to guarantee then depends on a token the service
  never verified was meant for it.
- **Fix:** the same as `dotnet-web-api` 1.0.5. Read `Oidc:Authority` and
  `Oidc:Audience` **before** registration, throw if either is missing, and
  leave `ValidateAudience` at its default. Reading them inside the
  `AddJwtBearer` delegate is not equivalent: that delegate runs on the first
  request, so a missing setting becomes a 500 per call instead of a service
  that refuses to start. The container check and the test host then have to
  supply the settings, which is the correct consequence.

### 3. The recipe's own claim is not tested — `medium`

- **Where:** `blueprints/dotnet-multitenant-saas-api/setup.md:537` onwards
  (step 21, the isolation tests)
- **Standard:** OWASP ASVS 5.0, Access Control chapter (verification); OWASP
  API5:2023
- **What:** the isolation tests are good and they test the data layer — one
  tenant cannot read another's rows, the query filter is not baked into the
  cached model, a write is stamped, a foreign tenant's row is refused. None of
  them goes through the HTTP pipeline, so nothing tests that a request without
  a token is refused.
- **Why it matters:** finding 1 would have been caught by a single test
  asserting `/customers` answers 401 to an anonymous caller. The blueprint has
  a test project and a test host available, and the gap is exactly where the
  claim lives.
- **Fix:** add an integration test with `WebApplicationFactory<Program>`: an
  anonymous `GET /customers` is 401, and `/health` is 200. Two assertions, and
  they guard the control that the data-layer tests assume is already in place.

### 4. `tenant_id` is trusted as a string without shape — `low`

- **Where:** `blueprints/dotnet-multitenant-saas-api/setup.md:114` (step 14)
- **Standard:** OWASP ASVS 5.0, Validation chapter
- **What:** `TenantResolutionMiddleware` accepts any non-whitespace claim value
  as a tenant identifier. Under `db-per-tenant` that value is validated by
  `TenantDatabaseName.For` against `^[a-z0-9][a-z0-9-]{0,50}$` before it
  reaches a connection string — good, and tested. Under
  `shared-db-tenant-column` it is never checked; it goes into a query
  parameter, so it is not injectable, but a 400-character claim becomes a
  400-character `TenantId` on every row it writes and the column is
  `HasMaxLength(64)`.
- **Why it matters:** a malformed claim produces a database error at write time
  rather than a rejected request. Low, because the token was signed by an
  authority you trust.
- **Fix:** validate in the middleware for both tenancy options, using the
  pattern `db-per-tenant` already defines, and reject with 401 rather than
  resolving.

## What was checked and found sound

- **The tenant comes from the token and nowhere else.** No header, route value,
  query string or subdomain can select a tenant. The middleware says so in a
  comment, and it is true of the code (OWASP API1:2023).
- **The filter is not bakeable into the model.** `tenantId` is a per-instance
  field that EF lifts into a query parameter, and there is a test asserting the
  compiled model is not poisoned by the first tenant that used it — the
  failure mode that makes naive multi-tenancy leak.
- **Writes are stamped, not trusted.** `SaveChanges` sets the tenant on added
  entities and throws when a modified entity carries another tenant's
  identifier, with a test for each.
- **Ordering is correct and explained.** Authentication, then tenant
  resolution, then authorization — the tenant is read from an authenticated
  principal, never before it exists.
- **`db-per-tenant` validates the identifier before it reaches a connection
  string**, with a regex and a test that a hostile identifier is refused
  (OWASP A03 injection surface).
- **`TenantContext` fails loudly.** Using a tenant-scoped service outside a
  tenant request throws rather than returning a default — which is why
  finding 1 is a 500 today instead of a leak.
- **Container.** Non-root runtime stage, no SDK in the final image, health
  endpoint that touches nothing (CIS Docker, image scope).
- **Supply chain.** Actions pinned to SHAs, read-only workflow permissions, SDK
  pinned through `global.json`, every package version explicit (SSDF, SLSA).
- **Compose binds to loopback and the images are pinned** — fixed in 1.0.4 by
  the review of `dotnet-web-api`.

## Not applicable

- **OWASP LLM 2025 and Agentic 2026.** `project_type: api`; no model, no agent
  surface.
- **CIS Docker host and daemon controls.** A blueprint does not configure the
  reader's daemon.
- **Migrations and schema deployment.** The blueprint ships none and
  `overview.md` says so; how schema changes reach an environment is the
  reader's decision.
- **Rate limiting (API4:2023).** Not claimed. Unlike `dotnet-web-api` before
  1.0.5, this blueprint's "What it is NOT for" already names billing, quotas
  and per-user rules as out of scope — but it does not name rate limiting
  either. One line, same as the fix applied there.

## Resolution

Closed in **1.1.0**, on the day of the review.

| #   | Severity | Closed by                                                                                                                                                                                                                                                    |
| --- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `high`   | `SetFallbackPolicy` alongside `SetDefaultPolicy`, both built from the same tenant policy, **and an integration test that a request to `/customers` with no token is 401** — the endpoint still declares nothing, so that 401 can only come from the fallback |
| 2   | `high`   | `Oidc:Authority` and `Oidc:Audience` are required and read before registration, so a missing one stops the service starting rather than answering 500 per request; `ValidateAudience` stays at its default                                                   |
| 3   | `medium` | The integration test in finding 1 is this finding's fix: the blueprint's claim is now tested through the HTTP pipeline                                                                                                                                       |
| 4   | `low`    | Open. Validating the shape of `tenant_id` in the middleware is worth doing and is not urgent: the claim arrives on a token this service verified                                                                                                             |

**`tier: official` is no longer blocked.** One `low` finding remains open.

Verified locally: 34 steps green on `postgres` + `shared-db-tenant-column`,
including the new authorization test and the container check, which now
supplies the authentication settings the service demands.
