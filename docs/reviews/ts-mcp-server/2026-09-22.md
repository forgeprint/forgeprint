# ts-mcp-server — architecture and security review

- Date: 2026-09-22
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **CHANGES** — findings closed the same day; see _Resolution_

## Summary

An MCP server on the official TypeScript SDK. The separation is right —
`createServer()` holds the tools and knows nothing about bytes, the entry point
holds the transport and nothing else — and the tests speak the real protocol
rather than calling the handler, which is the distinction that catches schema
mistakes.

Two findings. The `http` transport ships a server with no access control at
all, and the specification names that exact shape as an attack surface on the
machine it runs on, not only beyond it. And the CI workflow the blueprint
writes cannot run on a fresh clone, because it uses `npm ci` and the recipe
never commits a lockfile.

The manifest claims `tier: official`. One `high` finding is open, so **rule 23
blocks that tier** until it is closed.

## Findings

### 1. The HTTP transport has no access control, and localhost is not a boundary — `high`

- **Where:** `blueprints/ts-mcp-server/setup.md:140` (step 5, the `http`
  branch)
- **Standard:** MCP specification 2026-07-28, _Security Best Practices_ —
  "Local MCP Server Compromise". The specification says a server intended to
  run locally **SHOULD** prevent unauthorized use by malicious processes:
  _"Use the `stdio` transport to limit access to just the MCP client"_, or
  _"Restrict access if using an HTTP transport, such as: Require an
  authorization token; Use unix domain sockets or other IPC mechanisms with
  restricted access."_ It names the attack directly: _"An attacker accesses an
  insecure local server that's left running on localhost via DNS rebinding."_
  Also OWASP Top 10 for Agentic Applications 2026, and OWASP LLM 2025 excessive
  permissions.
- **What:** the `http` entry point binds `127.0.0.1` on a port the operating
  system picks and serves the MCP endpoint to anything that connects. No token,
  no `Origin` check, no socket permissions.
- **Why it matters:** `overview.md` says the HTTP option is not for a hosted
  service and that authentication is absent — which frames the risk as
  beginning outside the machine. The specification frames it as beginning
  inside: every other process on the host can call these tools, and a web page
  the user visits can reach the port through DNS rebinding, which sidesteps the
  same-origin protections that would otherwise apply. For an `echo` tool that
  is harmless. The blueprint exists to be extended with tools that are not.
- **Fix:** one of, in the order the specification lists them:
  1. Require a bearer token on the HTTP transport, read from the environment
     and compared in constant time; refuse to start without it.
  2. Validate the `Origin` header and reject anything unexpected, which is the
     direct answer to DNS rebinding.
  3. State in `AGENTS.md` and `overview.md` that the `http` option is for a
     trusted single-user machine and nothing else, and that adding a tool which
     touches the filesystem, the network or a credential means adding
     authentication first.

  (3) alone is the minimum. (1) or (2) is what makes the option safe to extend,
  and (2) is a dozen lines.

### 2. The CI workflow cannot run on a fresh clone — `medium`

- **Where:** `blueprints/ts-mcp-server/setup.md:227` (step 8, `ci.yml`) against
  `setup.md:199` (step 7, `.gitignore`) and step 3
- **Standard:** NIST SSDF (PS.3, archive and protect each release); SLSA v1.2
  build track — the dependency graph a build resolves has to be the one that
  was reviewed
- **What:** the workflow runs `npm ci`, which fails without
  `package-lock.json`. The recipe runs `npm install`, which writes that file,
  but never says to commit it and never mentions it again. A reader who commits
  what the recipe told them to create has a repository whose first CI run
  fails.
- **Why it matters:** worse than the inconvenience, the lockfile _is_ the
  supply-chain artefact. `package.json` pins exact versions of direct
  dependencies; only the lockfile pins what those pull in. Losing it means the
  build resolves a different transitive graph than the one that was tested.
- **Fix:** add a step that commits the lockfile, or at minimum name it in
  "After setup" as the file that must be committed. A `.gitignore` entry
  excluding it would be the wrong fix and is worth saying so.

### 3. `SERVER_VERSION` will drift from `package.json` — `low`

- **Where:** `blueprints/ts-mcp-server/setup.md:81` (step 4) and `setup.md:20`
  (step 1)
- **Standard:** Twelve-Factor I (one codebase, one build)
- **What:** `0.1.0` is written twice, in `package.json` and in `server.ts`. The
  version the client sees in the handshake is the second one.
- **Why it matters:** Forgeprint's own MCP server shipped exactly this bug —
  `--version` and the handshake reported `0.1.0` for three releases. It is the
  kind of drift nobody notices because nothing reads it until a bug report
  quotes it.
- **Fix:** a note in `AGENTS.md` that the two move together, or a test that
  asserts they match. Forgeprint uses the test.

## What was checked and found sound

- **Tool surface is minimal and the boundary is right.** One tool, no
  filesystem, no network, no process spawning — OWASP LLM 2025 excessive
  functionality does not apply to what ships.
- **Arguments are validated in the schema.** `z.string().min(1)` reaches the
  client as JSON Schema, so the constraint is enforced before the handler runs
  and is visible to the model before it calls. A test asserts an empty message
  is refused.
- **The tool description says when to use it**, which is the only thing a model
  has when deciding whether to call it.
- **stdout discipline is stated as a rule, with the reason.** Under stdio,
  stdout is the protocol; `AGENTS.md` says a stray `console.log` is a malformed
  message, and the HTTP entry point logs to stderr.
- **The tests speak the protocol.** `InMemoryTransport` drives a real client
  against a real server, and `scripts/probe.mjs` drives the built executable —
  which is what catches a wrong entry point or anything written to stdout.
- **Statelessness is a decision, not an accident.** No session identifiers, and
  `overview.md` says why. State handle hijacking (MCP spec) does not apply to a
  server that mints no handles.
- **No token handling at all**, so token passthrough — which the specification
  forbids outright — cannot occur.
- **Supply chain in CI.** Actions pinned to commit SHAs, `permissions:
contents: read`, dependency versions exact in `package.json`.
- **Port 0.** The HTTP option asks the operating system for a port and prints
  it, so a health check is never answered by a different process.

## Not applicable

- **OAuth, consent, confused deputy, scope minimisation (MCP spec).** The
  server implements no authorization flow and proxies no third-party API.
- **SSRF (MCP spec).** The server fetches nothing.
- **CIS Docker.** No container; `platforms` does not claim one.
- **OWASP API Security Top 10.** `project_type: agent`, not an HTTP API in the
  resource sense.
- **NIST SP 800-218A.** It applies to developing generative AI models, not to
  serving tools to one.

## Resolution

Closed in **1.1.0**, on the day of the review.

| #   | Severity | Closed by                                                                                                                                                                                                                                                                                                                                                                                           |
| --- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `high`   | The HTTP entry point refuses an unexpected `Origin`, which is the direct answer to DNS rebinding; `ALLOWED_ORIGINS` is empty by default, so every request carrying the header is refused. `overview.md` and `AGENTS.md` now say localhost is not a boundary and that `stdio` is the safer default. **The recipe proves the guard**: a request with `Origin: https://example.com` must come back 403 |
| 2   | `medium` | "After setup" names `package-lock.json` as a file that must be committed, says why `npm ci` needs it, and says not to gitignore it                                                                                                                                                                                                                                                                  |
| 3   | `low`    | A note where `SERVER_VERSION` is written                                                                                                                                                                                                                                                                                                                                                            |

**`tier: official` is no longer blocked.**

The `Origin` step exposed a false positive in `lint-setup`: `example.com` in a
header value was read as a host being contacted. Documentation domains reserved
by RFC 2606 and RFC 6761 are now allowed, with a test.

It also exposed a flaky verification. The step that reads the server's address
out of its log waited thirty seconds, and the first run of a freshly built
binary on Windows exceeded it once. Sixty now: a verification that fails
intermittently is worse than a slow one.
