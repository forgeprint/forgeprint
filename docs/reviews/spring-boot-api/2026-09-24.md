# spring-boot-api — architecture and security review

- Date: 2026-09-24
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first Java blueprint and its first `api` with object-level
authorization: every row carries an owner, the owner is the token's subject,
and every repository query filters on it.

The single thing a reader should know before building on it: authorization is
"any valid token, for its own rows". There are no scopes or roles, and nothing
bounds how often a caller may hit a route. Both are declared under "What it is
NOT for", and both are the next thing a real service needs.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Any valid token may call any endpoint — `low`

- **Where:** `blueprints/spring-boot-api/setup.md:274` (step 11)
- **Standard:** OWASP API Security Top 10 2023, **API5:2023 Broken Function
  Level Authorization**
- **What:** the filter chain requires an authenticated caller and nothing more.
  Scopes and roles in the token are not read.
- **Why it matters:** object-level authorization is enforced (see "What was
  checked"), so one caller cannot reach another's rows. But a token minted for a
  read-only client can still `POST`. The moment an administrative endpoint is
  added, "authenticated" is not enough.
- **Fix:** declared in `overview.md` ("Role or scope based authorization").
  When the first endpoint needs more than ownership, add
  `.requestMatchers(HttpMethod.POST, "/api/**").hasAuthority("SCOPE_...")` and
  a test beside `aRequestWithNoTokenIsRefused`. Recorded as `low` because the
  claim is `auth`, not `rbac`, and the gap is disclosed.

### 2. Nothing bounds how often a route can be called — `low`

- **Where:** `blueprints/spring-boot-api/overview.md`, "What it is NOT for"
- **Standard:** OWASP API Security Top 10 2023, **API4:2023 Unrestricted
  Resource Consumption**
- **What:** no rate limiting. The list query is capped at 100 rows
  (`setup.md:415`), which bounds the cost of one request, not the number of
  them.
- **Why it matters:** a legitimate scope decision behind a gateway, a gap when
  exposed directly.
- **Fix:** already declared, with that distinction. Left open because the
  declaration is the mitigation, not the control.

### 3. The JWK Set address is not required to be HTTPS — `low`

- **Where:** `blueprints/spring-boot-api/setup.md:167` (step 9, `TokenSettings`)
  and `:293` (step 11)
- **Standard:** OWASP ASVS 5.0, Cryptography and communications chapters;
  OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** `APP_TOKEN_JWKS` is any `URI`. The keys that decide who is
  authenticated are fetched from it.
- **Why it matters:** a reader who points it at a plain-HTTP address lets
  anyone on that network path substitute the signing keys. Inside a cluster
  this is common and sometimes acceptable; across a network it is not.
- **Fix:** a one-line check in `TokenSettings` (reject a scheme other than
  `https` unless an explicit flag allows it) would make the unsafe choice
  deliberate. Not done in 1.0.0 because it breaks the in-cluster case without a
  second setting, and the trade-off deserves its own change.

### 4. No per-artifact lock for Maven dependencies — `low`

- **Where:** `blueprints/spring-boot-api/setup.md:44` (step 7) and `:923`
  (step 25)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2 build track; NIST SSDF PS.3
- **What:** versions are pinned through the Spring Boot parent and one
  explicit property, but Maven has no lock file, so nothing records the hash
  of each artifact the way `go.sum` does.
- **Why it matters:** a republished artifact under the same coordinates would
  be accepted if its repository checksum matched.
- **Fix:** already mitigated as far as Maven allows without a plugin: the
  wrapper archive is checked against a recorded SHA-256 (step 2), the wrapper
  checks Maven's SHA-256 (step 6), and the build runs with `--strict-checksums`
  so a download that does not match its published checksum fails. The gap is
  stated in `overview.md`. A dependency-verification plugin is a dependency
  decision for the reader.

### 5. Base images are pinned by tag, not by digest — `low`

- **Where:** `blueprints/spring-boot-api/setup.md:872` and `:877` (step 24)
- **Standard:** CIS Docker Benchmark v1.8.0, image and Dockerfile scope (use
  trusted, pinned base images); OWASP Top 10:2025 A03
- **What:** `eclipse-temurin:25.0.4_7-jre-noble` is a specific patch tag, but
  a tag can be re-pointed.
- **Why it matters:** the same tag can resolve to a rebuilt image. Temurin
  rebuilds tags for OS security updates, which is usually what a reader wants
  and occasionally not.
- **Fix:** consistent with every other container in the catalog. A reader who
  needs reproducible images adds `@sha256:` and takes on updating it.

### 6. The JWK Set fetch path is not exercised by the tests — `info`

- **Where:** `blueprints/spring-boot-api/setup.md:581` (step 20, `TestTokens`)
- **Standard:** OWASP ASVS 5.0, token verification
- **What:** the tests replace the production `JwtDecoder` with one that trusts
  a generated public key, and apply the production `TokenRules`. The
  signature, issuer, audience, expiry and subject rules are tested; fetching
  and caching the JWK Set is not.
- **Why it matters:** a wrong `APP_TOKEN_JWKS` shows up as every request
  answering 401, not as a failed test.
- **Fix:** none needed for a template: the fetch is Spring Security's
  `NimbusJwtDecoder`, not code this blueprint writes. Recorded so the next
  reviewer does not raise it as an oversight.

### 7. No `HEALTHCHECK` in the image — `info`

- **Where:** `blueprints/spring-boot-api/setup.md:864` (step 24)
- **Standard:** CIS Docker Benchmark v1.8.0, image and Dockerfile scope
- **What:** the image declares no health check. Liveness and readiness are
  HTTP endpoints for an orchestrator to probe.
- **Fix:** none; the JRE image has no HTTP client to run one with, and adding
  one to the image would add attack surface to satisfy a control that
  orchestrators replace.

## What was checked and found sound

- **Deny by default.** `.anyRequest().authenticated()` after an explicit list
  of two public groups (health, the OpenAPI document). A route added later is
  protected without touching the file, and `aPathNobodyMappedIsRefusedRatherThanFound`
  fails if the default is loosened (OWASP API5:2023, Top 10:2025 A01).
- **Object-level authorization in the data layer.** No repository method reads
  a row without the owner; another caller's item is a 404 rather than a 403,
  and `anotherCallerCannotReadOrListIt` proves both the read and the list
  (OWASP API1:2023).
- **Token validation is complete and shared.** RS256 only (algorithm confusion
  and `none` refused by the decoder), issuer, audience, expiry required,
  subject required. Spring Security's defaults check neither audience nor the
  presence of `exp`; both are added, and the tests build their decoder with
  the same `TokenRules`. A forged signature, a wrong audience and an expired
  token each have a test (OWASP API2:2023, ASVS 5.0 token chapter).
- **Unauthenticated is 401 with `WWW-Authenticate: Bearer`**, asserted in a
  test and again against the running image.
- **Configuration fails closed.** No default for the datasource or the token
  settings; `TokenSettings` is `@Validated`. Starting the image with no
  environment was tried and it exits with status 1 before listening
  (Twelve-Factor III; OWASP Top 10:2025 A10).
- **Validation at the boundary, errors as RFC 9457 problem details.** The
  `@Size` on the request record matches the `CHECK` constraint in V1, so a
  refusal is a 400 and never reaches the database as a 500. No exception
  message or SQL reaches a response (OWASP A10).
- **Parameterised SQL only.** `JdbcClient` with named parameters throughout;
  no string concatenation into a query (ASVS 5.0 injection requirements).
- **Migrations are the schema.** Flyway at startup, no ORM schema generation,
  and `AGENTS.md` states that applied migrations are never edited.
- **Actuator exposes `health` only**, with `show-details: never`; liveness
  touches nothing and readiness includes the database (OWASP A09, A02).
- **The OpenAPI inventory is off by default** and declares the bearer scheme
  when on (OWASP API9:2023).
- **CSRF is disabled for a reason that holds**: stateless sessions and no
  cookies. `AGENTS.md` says adding a cookie login means turning it back on.
- **Container:** multi-stage, layered, built from the tested jar, a fixed
  numeric non-root user (`10001:10001`, asserted by step 29), a build context
  of exactly one file, and the recipe runs the image against a real
  PostgreSQL on a private network with no published database port (CIS Docker
  image scope).
- **CI:** actions pinned by commit SHA, `permissions: contents: read`,
  `persist-credentials: false`, a pinned runner image, `--strict-checksums`
  (SLSA v1.2, OWASP A03).
- **Build tool integrity:** the wrapper scripts and Maven itself are both
  verified against recorded SHA-256 values before they run.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The only credential-shaped value is `local-development-only-not-a-real-secret`,
  used for a throwaway check database; test keys are generated in memory per
  run and never written.

## How the recipe was exercised

Java is not installed on the review machine, so every step was run in an
`eclipse-temurin:25.0.4_7-jdk-noble` container with the host's Docker socket:
the wrapper and Maven checksums verified, all 11 tests passed against
Testcontainers PostgreSQL 18.6, and the image built. The container-check steps
(29–42) were then run against that image from the host: liveness and readiness
answered `UP`, the unauthenticated request answered 401, and the containers
and network were removed. CI's `setup-test` is the run of record.

---

## Verdict

**MERGE.** Five `low`, two `info`, nothing `medium` or above.

The design holds where API starters usually fail — ownership in the query,
deny by default, a token validator that checks the audience, and a service
that will not start half-configured. The open findings are the next
capabilities a real service needs (scopes, rate limiting) and two
supply-chain limits that Maven and tagged images share with the rest of the
catalog.

`tier: official` is not available while `provenance: generated` (ADR 0011).
