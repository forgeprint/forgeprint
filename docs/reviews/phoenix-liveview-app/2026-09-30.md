# phoenix-liveview-app — architecture and security review

- Date: 2026-09-30
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21); OWASP ASVS 5.0 requirement texts read from the OWASP/ASVS
  repository on 2026-09-30
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first Elixir blueprint: Phoenix 1.8.15 and LiveView 1.2.12 on
Postgres, with `mix phx.gen.auth` in its 1.8 magic-link shape and one LiveView
page behind it.

Most of the design is Phoenix's own, so the review concentrates on three
questions: whether the `realtime` claim is verified as widely as the word, what
the generated authentication leaves open, and whether the production
configuration is honest about what it refuses. Five gaps were found while
drafting and closed before this review; they are recorded below so the next
reviewer does not re-derive them. No `critical` or `high` finding is open.

The single most important thing for a reader: **the only way into this
application is a link sent by email, and nothing rate-limits the endpoint that
sends it.** Both are disclosed in `overview.md`, and both are work the reader
has to do before launch.

The manifest claims `tier: community` and `provenance: generated`.

## Found while drafting, fixed before review

These were in the generated code or in the first draft, would have been
findings here, and are closed in 1.0.0.

- **No content security policy — would have been `medium`.** The router
  `mix phx.new` writes calls `put_secure_browser_headers` with no policy, and
  Sobelow 0.15.0 reports `Config.CSP` at high confidence. OWASP Top 10:2025
  **A02 Security Misconfiguration**. Fixed: a policy on the browser pipeline at
  `blueprints/phoenix-liveview-app/setup.md`, step 16, and `--exit Low` in the
  `precommit` alias and in CI so that removing it fails the build rather than
  printing a warning.
- **`force_ssl` set in `config/runtime.exs` — would have been `high`.** The
  first draft put it there, which Phoenix accepts and silently ignores because
  it reads the option at compile time; the site would have served plain http
  for ever while the configuration said otherwise. OWASP Top 10:2025 **A02**.
  Fixed: it stays in the generated `config/prod.exs`, `runtime.exs` carries a
  comment saying why, and `runtime_config_test.exs` asserts against the file
  that works.
- **A production host defaulting to `example.com` — would have been `medium`.**
  The generated `runtime.exs` falls back to that string for `PHX_HOST`, and the
  host is what builds the magic link in the sign-in email. Twelve-Factor III,
  and OWASP Top 10:2025 **A02**. Fixed: no default, a `raise` naming the
  variable, and a test.
- **A production secret with no floor — would have been `medium`.** The
  generated `runtime.exs` accepts any non-empty `SECRET_KEY_BASE`, including
  the one printed in `config/dev.exs`. It signs session cookies and LiveView
  socket tokens. ASVS 5.0 **11.4.2** is about password storage rather than this
  key, so the citation here is OWASP Top 10:2025 **A02** together with
  CLAUDE.md §5b. Fixed: the development value is refused by name, anything
  under 64 bytes is refused by length, and both are tested — plus a recipe step
  that runs a production command with no secret at all and records the refusal.
- **The development server bound to `0.0.0.0` — would have been `low`.** The
  generated `config/dev.exs` binds every interface, with code reloading,
  readable stack traces, the LiveDashboard and a mailbox preview behind it.
  OWASP Top 10:2025 **A02**. Fixed: `ip: {127, 0, 0, 1}`.

## Findings

### 1. The magic-link lifetime is longer than the out-of-band maximum — `medium`

- **Where:** the generated `lib/liveview_app/accounts/user_token.ex`,
  `@magic_link_validity_in_minutes 15`; disclosed at
  `blueprints/phoenix-liveview-app/overview.md`, "The security posture you
  inherit"
- **Standard:** OWASP ASVS 5.0 **6.5.5** (Level 2): "Out of band requests must
  have a maximum lifetime of 10 minutes."
- **What:** a sign-in link works for fifteen minutes after it is sent. That is
  the `phx.gen.auth` default in Phoenix 1.8.15 and the blueprint does not
  change it.
- **Why it matters:** the window in which a link found in a mailbox, a proxy
  log or a shared screen still opens the account is half again as long as the
  standard allows at Level 2. Nothing else compensates: the link is the whole
  credential.
- **Fix:** set `@magic_link_validity_in_minutes 10` in
  `lib/liveview_app/accounts/user_token.ex`, and update the paragraph in
  `overview.md` in the same change. It is left open here rather than patched
  because changing a generated module inside a recipe step means rewriting the
  whole file, and that trade is the maintainer's to make.

### 2. Nothing rate-limits the endpoint that sends sign-in mail — `medium`

- **Where:** `blueprints/phoenix-liveview-app/setup.md`, step 16 — the routes
  `post "/users/log-in"` and `live "/users/register"` have no limiter in front
  of them
- **Standard:** OWASP ASVS 5.0 **6.3.1** and **6.1.1** (both Level 1)
- **What:** `phx.gen.auth` generates no anti-automation control, and the
  blueprint adds none. Anyone can ask for sign-in mail to any address as often
  as they like.
- **Why it matters:** the token entropy makes guessing a link pointless, so the
  exposure is not the credential — it is unbounded mail sent in the
  application's name to an address its owner did not ask about, and the sender
  reputation that goes with it. 6.3.1 is a Level 1 requirement, which is the
  bar this blueprint's audience sits at.
- **Fix:** put a limiter (`Hammer`, `PlugAttack`, or the edge in front of the
  application) on `POST /users/log-in` and on the registration LiveView's
  submit, keyed by address and by source, and write what it allows into
  `overview.md` as 6.1.1 asks. Disclosed today; disclosure is not the control.

### 3. `connect-src` names bare websocket schemes — `low`

- **Where:** `blueprints/phoenix-liveview-app/setup.md`, step 16,
  `@content_security_policy`
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** the policy is `connect-src 'self' ws: wss:`. A bare scheme-source
  matches any host, so the policy permits a websocket to anywhere.
- **Why it matters:** as a channel out of the page it is real, but it is second
  in line: `default-src 'self'` has to fail first for anything to be running
  that could use it. It is defence in depth that is wider than it needs to be.
- **Fix:** replace the two schemes with the deployment's own origin
  (`wss://app.example.com`). It is not done here because `'self'` does not
  reliably cover a plain-`ws` socket on an http page, which is what development
  serves, and no check in this catalog opens a browser to find out. The comment
  in the router and `overview.md` both say so.

### 4. Transitive dependency versions are resolved at generation time — `low`

- **Where:** `blueprints/phoenix-liveview-app/setup.md`, step 8
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF SP 800-218
- **What:** every direct dependency is pinned to an exact version in `mix.exs`,
  and `mix.lock` is written by the resolver during the recipe. Two people
  running the recipe months apart get the same direct versions and possibly
  different transitive ones.
- **Why it matters:** the recipe is reproducible in the sense that matters most
  — the same direct tree — but not byte-for-byte. It is the same trade
  `rails-web-app` makes with `Gemfile.lock`, and it ends the moment `mix.lock`
  is committed.
- **Fix:** none in the recipe. `overview.md` says to commit `mix.lock` on the
  first day, and CI already runs `mix deps.get --check-locked`, which makes the
  tree fixed for everyone afterwards.

### 5. `realtime` is proved between processes, not between browsers — `info`

- **Where:** `blueprints/phoenix-liveview-app/setup.md`, step 17
- **Standard:** the skill's own rule that a claim wider than its verification is
  a finding (`skills/blueprint-arch-review/SKILL.md`, §2)
- **What:** `counter_live_test.exs` increments from the test process and asserts
  the mounted LiveView re-rendered, which exercises the whole
  PubSub-to-`handle_info`-to-diff path. It does not open two sockets, and
  `Phoenix.LiveViewTest` never loads `app.js`.
- **Why it matters:** the mechanism is genuinely tested; the last hop, a real
  browser applying a diff, is not, and a content security policy too tight for
  one would pass every check here.
- **Fix:** nothing now. It is disclosed in `overview.md` under "What CI cannot
  prove", which is what turns it from a defect into a decision. A browser check
  is in the CHANGELOG's Planned section.

## What was checked and found sound

- **Authentication, both doors.** `/counter` sits inside
  `live_session :require_authenticated_user` with the `on_mount` hook _and_
  behind the `:require_authenticated_user` plug, and the test asserts the
  redirect for the ordinary HTTP request and for the websocket mount
  separately. ASVS 5.0 **7.2.1** (verification in a trusted backend service)
  and **8.x** access control. A `live` route added to the scope but to a
  session without the hook would be open, and `AGENTS.md` says so in those
  words.
- **Password storage.** `pbkdf2_elixir` 2.3.1 through the Comeonin interface,
  which is a computationally intensive key derivation function with per-user
  salt — ASVS 5.0 **11.4.2** (Level 2). Argon2id would be stronger; the
  trade-off (a C toolchain the recipe would have to declare) is recorded in
  `overview.md` and in `mix.exs`. Test configuration lowers the rounds, in
  `config/test.exs` only.
- **Session tokens.** Reference tokens rather than static secrets, 32 bytes
  from `:crypto.strong_rand_bytes/1` — 256 bits, against the 128 that ASVS 5.0
  **7.2.3** asks for — looked up in Postgres on every request, which is
  **7.2.1**. A fresh token is issued and the session renewed on sign-in and
  the row is deleted on sign-out, which is **7.2.2** and **7.2.4**. Note what
  is and is not hashed: the emailed tokens (magic link, email change) are
  stored as SHA-256 digests, the session token is stored as it is, because it
  only ever travels inside a cookie signed with `secret_key_base` — which is
  the second reason that key is now refused when it is short or copied from
  development. Sudo mode re-checks recency before an email or password change.
- **Configuration.** One place per environment, everything production needs
  read from the environment with no default, and the boot stops naming the
  missing variable. Twelve-Factor **III**. Six tests read `config/runtime.exs`
  the way a boot reads it, and step 36 runs a production command with no secret
  and records the refusal, which is the same claim proved from outside the
  suite.
- **Secrets.** The development value is labelled
  `local-development-only-not-a-real-secret-…` and refused by name in
  production; the test value says `test-only`; the recipe's throwaway secret is
  written to `prod-secret.txt`, which step 21 adds to `.gitignore` before it
  exists. Nothing secret-shaped is committed. CLAUDE.md §5b.
- **Transport.** `force_ssl` with `rewrite_on: [:x_forwarded_proto]` in
  `config/prod.exs` (HSTS is Plug.SSL's default), the endpoint URL fixed to
  `https` on port 443, and a test asserting it is in the compile-time file.
  ASVS 5.0 **V12**.
- **Supply chain.** Every direct dependency pinned exactly; `phx_new` installed
  from Hex at 1.8.15 rather than from a script; `mix deps.get --check-locked`
  and `mix deps.unlock --check-unused` in CI; `mix_audit` against the Elixir
  Security Advisories; both GitHub Actions pinned by commit SHA with the tag in
  a comment; `permissions: contents: read`; `persist-credentials: false` on
  checkout. OWASP Top 10:2025 **A03**, NIST SSDF, SLSA v1.2 build track.
- **Static analysis as a gate, not a report.** `sobelow --exit Low --private`
  in `precommit` and in CI. `--private` also keeps the scan from calling out to
  check its own version, which is what makes it run the same way offline.
- **Development surface.** The LiveDashboard and the Swoosh mailbox preview are
  behind `Application.compile_env(:liveview_app, :dev_routes)`, set in
  `config/dev.exs` and nowhere else, so they are not merely unrouted in
  production — they are not compiled into it. The development server binds
  loopback.
- **Boundaries and dependency direction.** `LiveviewApp` holds the contexts and
  `LiveviewAppWeb` the delivery mechanism; `CounterLive` calls
  `LiveviewApp.Counter` and the context names no web module. The one rule that
  keeps it honest — a LiveView never assigns its own answer in
  `handle_event/3` — is stated in `AGENTS.md` with the failure it prevents, and
  the tests enforce it. Clean Architecture's dependency rule; hexagonal ports
  and adapters.
- **Test strategy against the claims.** `auth`: anonymous refused over HTTP and
  over the socket. `realtime`: three assertions, one of them from a different
  process. `migrations`: applied against a real `postgres:18.6-alpine`, in test
  and again with the production configuration. `ci`: the workflow runs the same
  list `mix precommit` runs. 123 tests, all passing on Elixir 1.20.4 / OTP 29.
- **The recipe itself.** 43 steps, each one action with a verification;
  `forgeprint lint-setup` clean; no privileged command, no pipe from a
  download, no fixed port — the database port comes from
  `docker compose port db 5432` and the production server's from the operating
  system. Every download is from hex.pm, repo.hex.pm, builds.hex.pm,
  registry.npmjs.org or Docker Hub, which is why Tailwind, daisyUI and
  heroicons are absent; `overview.md` says so under trade-offs rather than
  leaving it to be discovered.
- **Error handling.** Phoenix's generated `ErrorHTML`/`ErrorJSON` return status
  text and nothing else, `debug_errors` is true only in `config/dev.exs`, and
  the two generated tests for them still run. OWASP Top 10:2025 **A10**.

## Not applicable

- **CIS Docker Benchmark.** The blueprint builds no image. `stack: [docker]`
  names the `postgres:18.6-alpine` container the recipe runs for local
  development and stops again; the tag is pinned, no Dockerfile exists, and
  nothing is published. The image-and-Dockerfile scope has nothing to review.
  When a Dockerfile arrives — `overview.md` and the CHANGELOG both say it has
  not — this section becomes a checklist.
- **OWASP API Security Top 10.** `project_type: web`; there is no API. The
  `:api` pipeline the generator writes is left in place and routed to nothing.
- **OWASP Top 10 for LLM Applications and for Agentic Applications, SP
  800-218A, the MCP specification.** No model, no tools, no agent surface.
- **WCAG 2.2 and EN 301 549.** `requirements` does not claim `accessibility`,
  and `overview.md` does not imply it. The one thing the blueprint does do —
  `aria-live="polite"` on the element that changes without a page load — is
  there because a live region is the difference between a working page and a
  silent one for a screen reader, not as a claim of conformance.
- **Observability (OWASP A09).** Not claimed. Worth knowing rather than fixing:
  there is no health endpoint and no structured logging beyond Phoenix's
  defaults, so the first deployment will need both. The LiveDashboard exists
  but only in development.
- **ASVS V10 OAuth and OIDC, V9 self-contained tokens.** No identity provider,
  no JWT; sessions are reference tokens in Postgres.
