# phaser-web-game — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 and 2026-09-23
  (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is the catalog's first `game` blueprint: a 2D browser game on Phaser 4.2.1
and Vite 8.3.1, static files, no server, no network access at run time, no
user data.

The manifest claims `requirements: [testing, ci]`, so the review is mostly a
test-strategy review (does the testing prove what `overview.md` says it
proves?) plus the supply-chain questions CI raises and the `web`-type question
of what reaches the browser. The single most important thing for a reader:
**the tests prove the rules, the scene wiring and the build; they prove
nothing about what is drawn.** The blueprint says so in `overview.md`, in
`AGENTS.md` and in the test's own stub, which is why that is a `medium`
finding rather than the finding.

No critical or high findings.

## Findings

### 1. Nothing drawn is ever checked — `medium`

- **Where:** `blueprints/phaser-web-game/setup.md:929` (step 20,
  `src/test/canvas-2d.ts`) and `:980` (step 21, `src/game.test.ts`)
- **Standard:** NIST SSDF SP 800-218 v1.1, PW.8 (test executable code to
  identify vulnerabilities and verify compliance with security requirements) — the
  question the skill asks as "do the tests prove the claim the blueprint
  makes"
- **What:** the headless test runs under Phaser's HEADLESS renderer with a 2D
  canvas context that answers every call with nothing. Scenes, loading,
  keyboard input and rules run for real; no pixel is produced.
- **Why it matters:** a sprite drawn off screen, in the wrong colour, or behind
  the background passes every test. `testing` in the manifest could be read as
  wider than that.
- **Fix:** none possible within the catalog's rule that recipes download
  nothing from outside a package registry (a real browser would be such a
  download). The gap is disclosed in `overview.md` ("What CI can prove, and
  what it cannot"), in `AGENTS.md`, and in the stub's comment, and the
  Playwright test the research proposed is named as the thing left out.
  Recorded so the disclosure is kept when the test is extended.

### 2. No Content-Security-Policy — `low`

- **Where:** `blueprints/phaser-web-game/setup.md:106` (step 5, `index.html`)
- **Standard:** OWASP ASVS 5.0 V3.4.3 (a Content-Security-Policy response
  header with at least `object-src 'none'` and `base-uri 'none'`)
- **What:** the page ships no policy, and a static host adds none by default.
- **Why it matters:** the game loads no third-party script, renders no user
  content and makes no request at run time, so there is little for a policy to
  stop today. The first analytics snippet or ad script somebody adds would run
  with the page's full authority.
- **Fix:** set the header at the host when the game is deployed. A `<meta>`
  policy in `index.html` was not added, because a policy that breaks Phaser's
  WebGL or inline style use can only be caught in a real browser, which CI
  here does not have. Worth adding once a browser check exists.

### 3. Transitive dependencies resolve at first install — `info`

- **Where:** `blueprints/phaser-web-game/setup.md:17` (step 1) and `:49`
  (step 2)
- **Standard:** OWASP Top 10:2025 A03 Software Supply Chain Failures; SLSA v1.2
- **What:** the five direct dependencies are pinned exactly; the recipe's
  `npm install` writes `package-lock.json`, and the generated CI installs with
  `npm ci` from it. The lock is therefore frozen at the reader's first install,
  not at the blueprint's.
- **Why it matters:** the same trade-off every npm blueprint in the catalog
  carries. `npm audit` against the resolved tree reported 0 vulnerabilities on
  2026-09-25.
- **Fix:** none. Recorded so the next reviewer does not re-derive it.

### 4. The rules boundary is a text check — `info`

- **Where:** `blueprints/phaser-web-game/setup.md:596` (step 12,
  `src/rules/boundary.test.ts`)
- **Standard:** Clean Architecture (the dependency rule); hexagonal
  architecture (ports and adapters)
- **What:** the test reads each module in `src/rules/` as text and allows only
  `./` import specifiers. A `require()` would not match its pattern.
- **Why it matters:** it would be a way round the boundary.
- **Fix:** none needed: `tsconfig.json` loads only `vite/client` types, so
  `require` does not type-check and `npm run typecheck` refuses it. The two
  checks together close it. A mutation run while writing the blueprint
  (adding `import Phaser from 'phaser'` to `geometry.ts`) failed the test as
  intended.

## What was checked and found sound

- **The boundary is real and enforced.** `src/rules/` is a pure function from
  state, input, milliseconds and a seeded random source to the next state. The
  scenes only translate keys and copy positions. The dependency points one way,
  scenes to rules, and a test fails the other direction (Clean Architecture's
  dependency rule).
- **Determinism is enforced, not hoped for.** `Math.random`, `Date.now` and
  `performance.now` are refused in the rules by the same test; randomness is a
  seeded `Random` argument. The only `Math.random` call is the scene choosing
  a seed, which is outside the rules and harmless.
- **Exceptional conditions are handled where they occur** (OWASP Top 10:2025
  A10). A long frame is clamped to `MAX_STEP_MS` (step 9) so a background tab
  cannot tunnel the player through the hazard; a negative frame time is
  ignored; a failed asset load stops at the preload scene with the file named
  on screen instead of starting with a missing texture; a disabled keyboard
  throws at scene creation rather than failing silently in `update`. The first
  two have tests.
- **The tests drive the real game.** `src/game.test.ts` boots the same
  `gameConfig()` the page uses, holds a key through a real `KeyboardEvent`,
  runs the clock out, and restarts with Space. A mutation that unwired the
  right arrow key failed it.
- **The budget has teeth.** `npm run build` runs the size check after
  `vite build`, and steps 31–32 build an over-budget stand-in and assert the
  check exits non-zero. A check that only printed would fail those steps.
- **No source maps** in the build (`vite.config.ts`, the budget script, and
  step 30 all check it).
- **What reaches the browser** (`project_type: game` on `platforms: [web]`,
  read against the skill's `web` row): one HTML file and one script. No
  third-party script, no font or asset CDN, no request at run time; the one
  asset is inlined, and step 29 asserts it.
- **CI** (SLSA v1.2, OWASP Top 10:2025 A03): actions pinned by commit SHA with
  the version in a comment, `permissions: contents: read`,
  `persist-credentials: false`, `npm ci` from the committed lock file. The
  SHAs are the ones this repository's own `setup-test` workflow uses.
- **Configuration** (Twelve-Factor III): the game reads none, and `.gitignore`
  keeps `.env*` out, with a comment on why a `VITE_` variable is public.
- **Nothing downloaded outside the npm registry.** No browser, no native canvas
  binary, no asset site. The coin is a 142-byte original PNG written from
  base64 in the recipe, and its step verifies the signature and dimensions.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).

## Not applicable

- **Authentication, session management, access control** (ASVS 5.0 V6–V8):
  no users, no server.
- **OWASP API Security Top 10:** not an API.
- **Data protection, cryptography** (ASVS 5.0): nothing is stored or sent;
  the seeded generator is documented as unsuitable where guessing the next
  number matters, and nothing here depends on that.
- **CIS Docker Benchmark:** no container.
- **Observability** (OWASP Top 10:2025 A09): a client-only game with no
  backend has nothing to log to. A game that later reports errors to a service
  should be reviewed for what it sends.
- **Accessibility** (WCAG 2.2): not claimed. `overview.md` says under "What it
  is NOT for" that the canvas is invisible to a screen reader and that
  keyboard-only play is the whole claim.
