# ai-chat-web-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is the catalog's first application that puts a model behind a public HTTP
route, which makes it the first where the OWASP Top 10 for LLM Applications
applies to a request somebody else sends rather than to a program the reader
runs themselves.

The manifest claims `project_type: agent` and `requirements: [realtime,
testing, ci]`, so the checklist came from OWASP LLM 2025 (prompt injection,
sensitive information disclosure, system prompt leakage, improper output
handling, excessive agency, unbounded consumption), the web references for
what reaches the browser, and SSDF and SLSA for the workflow. It does not
claim `auth` or `rate-limiting`, and the single most important thing a reader
should know is that it has neither: the route is safe per request and
unbounded in aggregate, and `overview.md`, `AGENTS.md` and the generated
README each say so before anything else.

One finding was fixed before the pull request opened: the draft logged the
provider's error object whole, and that object carries the request body —
the user's conversation. The shipped version logs the error's name and
message only, and a test asserts the conversation is not in the log.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Nothing bounds what the route costs in aggregate — `medium`

- **Where:** `blueprints/ai-chat-web-app/setup.md:369` (step 10,
  `handleChat`), and the absence of authentication or a rate limit anywhere
- **Standard:** OWASP Top 10 for LLM Applications 2025, **LLM10 Unbounded
  Consumption**; OWASP API Security Top 10 2023, **API4:2023 Unrestricted
  Resource Consumption**
- **What:** every request is bounded — 20 messages, 4,000 characters per user
  message, 12,000 per assistant message, 256 KB per body counted while
  reading, 2,048 output tokens, a 60-second timeout, and generation aborted
  when the client disconnects. Nothing limits how many requests arrive, or who
  sends them.
- **Why it matters:** deployed as shipped, anybody who finds `/api/chat` can
  spend the key's money one bounded request at a time, and the model id is an
  Opus-tier model.
- **Mitigating, and why this is `medium` rather than `high`:** neither `auth`
  nor `rate-limiting` is in `requirements`, so the resolver never offers this
  to somebody who asked for them; the omission is the first item under "What
  it is NOT for", the last section of `AGENTS.md`, and the first section of
  the generated README, each naming the three controls to add (authentication,
  a rate limit in front of the route, a provider-side spend limit). A reader
  would notice. The part of the control that belongs to one request is
  present and tested.
- **Fix:** none at this scope. A per-process in-memory limiter would be
  misleading on any multi-instance host, which is why the blueprint leaves
  the control to the platform in front of it rather than half-doing it.

### 2. The conversation history is client-supplied, including the assistant's turns — `low`

- **Where:** `blueprints/ai-chat-web-app/setup.md:270` (step 10, the request
  schema)
- **Standard:** OWASP Top 10 for LLM Applications 2025, **LLM01 Prompt
  Injection**
- **What:** the route is stateless, so the browser sends the whole history
  with every request, and a caller can write the assistant's side too.
- **Why it matters:** a forged assistant turn is a stronger injection than a
  user message, because models weigh their own prior output. Today the model
  has no tools and no data, so the only thing a caller can steer is the text
  of their own reply — the same thing they could steer by typing.
- **Mitigating:** the schema refuses a `system` message outright, allows only
  text, bounds every turn, and the code comment and `overview.md` (Cons) both
  say that this stops being harmless the day the model gets a tool or data.
- **Fix:** none now. When the first tool or data source arrives, keep the
  history on the server and accept only the new user message from the client.
  `AGENTS.md` ("add a tool", "keep chat history") points there.

### 3. No Content Security Policy — `low`

- **Where:** `blueprints/ai-chat-web-app/setup.md:91` (step 4,
  `next.config.ts`)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** the app sets `X-Content-Type-Options`, `Referrer-Policy` and
  `X-Frame-Options` and turns off `X-Powered-By`; it sets no CSP.
- **Why it matters:** a CSP is the second line behind the first, which here
  is that model output is rendered as React text and never as HTML
  (`chat.tsx`, step 12). If somebody later adds a Markdown renderer that
  passes raw HTML, nothing catches it.
- **Fix:** declared under Cons in `overview.md`. A nonce-based CSP in Next.js
  needs middleware and changes how pages render, which is a larger change than
  this blueprint's scope; `AGENTS.md` names the Markdown renderer as the point
  to be careful.

### 4. The limits count characters, not tokens — `info`

- **Where:** `blueprints/ai-chat-web-app/setup.md:142` (step 7, `limits.ts`)
- **Standard:** OWASP Top 10 for LLM Applications 2025, **LLM10 Unbounded
  Consumption**
- **What:** input bounds are character counts. A token count would need a
  provider-specific tokenizer in the request path.
- **Why it matters:** the ceiling per request is real but approximate; text
  in scripts that tokenize densely costs more than its length suggests.
- **Fix:** none; declared under Cons. The body limit in bytes is the hard
  backstop.

### 5. The mock model proves the plumbing and not the replies — `info`

- **Where:** `blueprints/ai-chat-web-app/setup.md:611` (step 16,
  `tests/mock-model.ts`)
- **Standard:** the catalog's rule that a verification must prove what a
  reader thinks it proves
- **What:** `MockLanguageModelV4` from `ai/test` streams fixed deltas. The
  suite proves validation, streaming, the hook, the transport and rendering —
  including a second turn, which is where a schema too strict for what
  `useChat` really sends would break.
- **Why it matters:** a green suite says nothing about whether a real model
  honours the system prompt. `realtime` is verified at the protocol level
  (each delta is asserted separately in the route test) and at the rendered
  result, not frame by frame in the UI.
- **Fix:** already stated in `overview.md` and in the mock's own comment.

## What was checked and found sound

- **The key stays on the server, and two checks prove it.** It is read in one
  file, at call time, with no default and no fallback provider (Twelve-Factor
  III). `tests/boundaries.test.ts` refuses a `'use client'` file importing
  from `src/server/` and a second file reading the key; the build check greps
  everything under `.next/static` for the key's value, its name and the
  system prompt after a build made with a sentinel key, both in the recipe
  (step 26) and in the generated CI (OWASP LLM 2025, LLM02 Sensitive
  Information Disclosure).
- **A missing key fails clearly.** `MissingApiKeyError` becomes a 503 naming
  the variable, before any stream starts; a test asserts it, and the recipe
  asserts it again against the running app with the variable unset
  (steps 27–30). OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**.
- **Provider errors stay on the server.** `onError` returns a fixed sentence
  to the browser, and — after the fix recorded in the summary — logs the
  error's name and message rather than the object that carries the
  conversation. Both halves are tested (LLM02; A09 Security Logging and
  Monitoring Failures).
- **The system prompt is server-side and holds nothing worth stealing.** The
  file says to assume it leaks, and the bundle check keeps it out of the
  client (LLM07 System Prompt Leakage).
- **A client-supplied system message is refused, not filtered.** The request
  schema is an allow-list of two roles and two part types (LLM01).
- **A refused request costs nothing.** Content type, body size, schema and
  limits are checked before the model factory is called, and every refusal
  test asserts the factory was never called (LLM10).
- **The body is bounded while it is read**, via the stream reader, so an
  oversized body is refused without being buffered (API4:2023).
- **Cross-site requests are refused by content type.** The route answers only
  `application/json`, which a cross-origin page cannot send without a
  preflight the route never answers; a test covers the `text/plain` case
  (A01 Broken Access Control, cross-site request forgery).
- **Model output is rendered as text** inside React elements, never as HTML
  (LLM05 Improper Output Handling).
- **No tools, so no agency to be excessive.** The model can produce text and
  nothing else, and `AGENTS.md` sets out what the first tool must bring with
  it — a narrow argument, a check in code, a misuse test, and a human approval
  for side effects (LLM06 Excessive Agency; Agentic 2026).
- **Supply chain.** Every npm dependency is pinned exactly, including the
  `vite` peer that would otherwise float; the generated CI installs with
  `npm ci`, has `contents: read` only, pins both actions by commit SHA and
  checks out without persisting credentials (SSDF PS.1, PW.4; SLSA v1.2;
  A03 Software Supply Chain Failures; LLM03 Supply Chain).
- **The recipe's own checks are honest about ports and processes.** The app
  binds to loopback on a port the operating system chooses, the recipe reads
  the port back from the log, and stops the process it started.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The only credential-shaped value is the sentinel
  `local-development-only-not-a-real-secret`, which names itself, and `.env*`
  is git-ignored before any environment file exists.

## Not applicable

- **Authentication, session management, access control (ASVS 5.0 V6–V8).**
  Not claimed; declared as absent (finding 1).
- **OWASP API Security Top 10 beyond API4.** One route, no objects, no
  identifiers, no authorization decisions to get wrong.
- **LLM04 Data and Model Poisoning, LLM08 Vector and Embedding Weaknesses.**
  No training, no fine-tuning, no retrieval.
- **LLM09 Misinformation.** A property of the model and the product around
  it, not of this scaffold; nothing here presents output as authoritative.
- **MCP specification and the MCP server guide.** No MCP surface.
- **CIS Docker.** No container.
- **NIST SP 800-218A.** It profiles the development of models themselves;
  this blueprint consumes one through an API.

---

## Verdict

**MERGE.** One `medium`, two `low`, two `info`; nothing `critical` or `high`.

The design choice everything rests on is right: the model is a parameter of
the route, which is what lets a mock drive the whole path — hook, transport,
route, stream, render — with no key, and what keeps the provider in one file.
The two claims a chat app most often gets wrong are both proved rather than
asserted: the key does not reach the browser, and a missing key fails with a
sentence.

The `medium` is the one to read before deploying. Per-request bounds are not
a budget, and the blueprint says so where a reader looks.

`tier: official` is not available while `provenance: generated` (ADR 0011).
