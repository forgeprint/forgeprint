# dotnet-web-api — architecture and security review

- Date: 2026-09-22
- Blueprint version: 1.0.4
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **CHANGES**

## Summary

An ASP.NET Core 10 minimal API with EF Core, bearer token validation, a
container image and CI. The structure is sound — the provider is named in one
file, configuration carries no secrets, the container runs as a non-root user,
and the health endpoint deliberately touches nothing.

The two findings that matter are both about **failing open where the blueprint
says it fails closed**. `AGENTS.md` tells the reader that endpoints require
authorization by default; `Program.cs` has no policy that makes that true. And
under the `oidc` option, leaving the audience unconfigured silently switches
audience validation off rather than refusing to start. In both cases a reader
following the blueprint's own documentation ends up with less protection than
the documentation promises, and nothing tells them.

The manifest claims `tier: official`. Two `high` findings are open, so
**rule 23 blocks that tier** until they are closed.

## Findings

### 1. `AGENTS.md` promises authorization by default; the code has no default — `high`

- **Where:** `blueprints/dotnet-web-api/setup.md:249` (step 17, `Program.cs`),
  against `blueprints/dotnet-web-api/AGENTS.md:55-59`
- **Standard:** OWASP API Security Top 10 2023, **API5:2023 Broken Function
  Level Authorization**; OWASP Top 10:2025 **A01 Broken Access Control**; OWASP
  ASVS 5.0, Authorization chapter (secure defaults)
- **What:** `AGENTS.md` says _"Endpoints require authorization by default. If
  an endpoint is public, say so in code with `.AllowAnonymous()`… `/health` is
  the one exception and is already mapped that way."_ None of that is
  implemented. `Program.cs` registers `AddAuthorization()` with no fallback
  policy, protects `/items` with an explicit `.RequireAuthorization()`, and maps
  `/health` with no `.AllowAnonymous()` — because nothing needs one when
  nothing is protected by default.
- **Why it matters:** this is the instruction file an agent reads before adding
  an endpoint. It will believe the new endpoint is protected and will not write
  `.RequireAuthorization()`, and the endpoint will be public. The failure is
  silent, it is in the direction of less security, and the document is what
  caused it. `dotnet-multitenant-saas-api` already does this correctly, so the
  fix is proven inside this catalog.
- **Fix:** make the document true. In `AddApiAuthentication`, set a fallback
  policy that requires an authenticated user:

  ```csharp
  services.AddAuthorization(options =>
      options.FallbackPolicy = new AuthorizationPolicyBuilder()
          .RequireAuthenticatedUser()
          .Build());
  ```

  Then mark `/health` `.AllowAnonymous()` explicitly, and drop the now-redundant
  `.RequireAuthorization()` on `/items` or keep it as documentation. Add a test
  that a new unmarked endpoint is refused — otherwise the next change silently
  undoes this.

### 2. Under `oidc`, an unset audience turns audience validation off — `high`

- **Where:** `blueprints/dotnet-web-api/setup.md:236` (step 16, `oidc` branch)
- **Standard:** OWASP API Security Top 10 2023, **API2:2023 Broken
  Authentication**; OWASP ASVS 5.0, Self-contained Tokens chapter; MCP-adjacent
  guidance does not apply here
- **What:**

  ```csharp
  options.Audience = configuration["Oidc:Audience"];
  options.TokenValidationParameters.ValidateAudience =
      !string.IsNullOrEmpty(options.Audience);
  ```

  `Oidc:Audience` has no default and is not checked at startup. If it is
  missing, the expression evaluates to `false` and the service accepts **any**
  token the configured authority issued — including one minted for a different
  application in the same tenant.

- **Why it matters:** misconfiguration is the normal case, not the exceptional
  one: a reader who has not registered an API identifier yet gets a service
  that appears to work and validates less than they think. Compare the `jwt`
  branch, which fails closed — a missing `ValidAudiences` leaves validation on
  with nothing to match, so every token is refused. The two branches of the
  same option disagree about what to do when configuration is incomplete, and
  only one of them is safe.
- **Fix:** fail closed. Require the value and refuse to start without it:

  ```csharp
  options.Audience = configuration["Oidc:Audience"]
      ?? throw new InvalidOperationException("Oidc:Audience is required.");
  ```

  Leave `ValidateAudience` at its default of `true`. If a deployment genuinely
  has no audience, that is a deliberate configuration switch with a name, not
  the consequence of an empty string.

### 3. The local database is published on every interface — `medium`

- **Where:** `blueprints/dotnet-web-api/setup.md:387` (`postgres`) and
  `setup.md:411` (`sqlserver`)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**; CIS Docker
  Benchmark, container networking scope
- **What:** `ports: - '5432:5432'` and `'1433:1433'` bind to `0.0.0.0`. The
  database is reachable from anything that can reach the machine, with the
  password that is written three lines above it in the same file.
- **Why it matters:** a developer on a shared or public network is exposing a
  database with a known password. It is local-development configuration, which
  is exactly the configuration nobody reviews.
- **Fix:** bind to the loopback interface — `'127.0.0.1:5432:5432'` and
  `'127.0.0.1:1433:1433'`. `ts-mcp-server` and `fastapi-service` already do
  this, so the catalog is inconsistent with itself today.

### 4. `mssql/server:2025-latest` is a moving tag — `medium`

- **Where:** `blueprints/dotnet-web-api/setup.md:407`
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; CIS
  Docker Benchmark, image scope
- **What:** `2025-latest` is a floating tag: the same recipe pulls different
  bytes on different days.
- **Why it matters:** the catalog's central claim is that a recipe is
  reproducible. A moving tag is the one thing that makes it not.
- **Fix:** pin to a released tag, and say in `overview.md` that the reader
  should update it deliberately.
- **This should not have needed a human.** `pin-image` only rejects the exact
  tag `latest`, so `2025-latest` passed. **Proposed rule change:** reject any
  tag containing `latest` as a word — `latest`, `2025-latest`, `stable-latest`.
  Not made in this pass; the review does not change code.

### 5. Base images are pinned to a minor, not a digest — `low`

- **Where:** `blueprints/dotnet-web-api/setup.md:335` and `setup.md:346`
- **Standard:** CIS Docker Benchmark, image scope (pin by digest)
- **What:** `mcr.microsoft.com/dotnet/sdk:10.0` and `aspnet:10.0` move as
  patches are published.
- **Why it matters:** less serious than finding 4 — the tag stays within a
  supported minor — but it is still not byte-reproducible.
- **Fix:** none required. This is a real trade-off: a digest pin is
  reproducible and stops security patches arriving silently, which for a base
  image is usually the wrong side to be on. Worth one sentence in
  `overview.md` saying the choice was made and why.

### 6. Rate limiting is absent and not declared absent — `low`

- **Where:** `blueprints/dotnet-web-api/overview.md`, "What it is NOT for"
- **Standard:** OWASP API Security Top 10 2023, **API4:2023 Unrestricted
  Resource Consumption**
- **What:** there is no rate limiting, which is a legitimate scope decision —
  `requirements` does not claim `rate-limiting`. But the "What it is NOT for"
  list does not mention it, and that list is what a reader uses to find out.
- **Why it matters:** an undocumented omission reads as an oversight. A
  documented one is a design decision the reader can act on.
- **Fix:** one line in "What it is NOT for", pointing at
  `AddRateLimiter` as the place to start.

## What was checked and found sound

- **Non-root container.** `USER $APP_UID` in the runtime stage, no SDK and no
  source in the final image (CIS Docker, image scope).
- **Health endpoint.** Liveness only, touching no dependency, with the reason
  written in a comment — a health check that queries the database turns a slow
  database into an outage (OWASP A09; Twelve-Factor IX).
- **No secrets in source.** Token validation settings and connection strings
  come from configuration; `AGENTS.md` names every key and says the environment
  is the source. The only committed credential is in
  `appsettings.Development.json` and is self-evidently local
  (`local-development-only`) — CLAUDE.md §5b, and it is Development-scoped.
- **Dependency direction and boundaries.** `DatabaseRegistration.cs` is the one
  file that names a provider, and `AuthenticationRegistration.cs` the one that
  configures the scheme. Switching either is a one-file change (hexagonal ports
  and adapters).
- **Supply chain in CI.** Actions pinned to full commit SHAs,
  `permissions: contents: read`, and the SDK pinned through `global.json`
  (SSDF; SLSA build track).
- **Known advisory handled deliberately.** Step 5 replaces the template's
  OpenAPI package to avoid GHSA-v5pm-xwqc-g5wc, and says so (OWASP A06).
- **Error handling.** `AddProblemDetails` and `UseExceptionHandler` are
  registered, so a failure returns a structured response rather than a stack
  trace (OWASP A10, new in the 2025 edition).
- **OpenAPI is Development-only.** `MapOpenApi` is inside an
  `IsDevelopment()` guard, so the schema is not published in production
  (OWASP A02).
- **The tests test the claim.** One asserts `/health` answers with no database;
  the other asserts `/items` refuses an unauthenticated caller. The second is
  the one that would catch finding 1 regressing — for that endpoint only.

## Not applicable

- **Multi-tenancy controls (OWASP API1 BOLA, tenant isolation).** The blueprint
  does not claim `multi-tenant` and `overview.md` says plainly that it is not
  for multi-tenant SaaS, naming the blueprint that is.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: api`, no model and no
  agent surface.
- **CIS Docker host and daemon controls.** A blueprint does not configure the
  reader's daemon; only the image and Dockerfile scope applies.
- **Session management (ASVS).** Bearer tokens only; no cookies, no server-side
  session.
- **NIST SP 800-218A.** Applies to generative AI development; not this.
