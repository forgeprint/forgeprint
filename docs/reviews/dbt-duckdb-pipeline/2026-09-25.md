## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first `languages: [sql]` blueprint and its second `data` one: a
dbt Core 1.12 project on a local DuckDB file, with raw CSV read in place as a
source, a seed, staging views, a contracted mart, four kinds of test and a CI
workflow.

The most important thing a reader should know: the project's correctness
rests on its tests, and the recipe shows them failing as well as passing —
two deliberately broken builds are required to fail on the right test with
the mart left unbuilt. That was not true of the first draft; see "Found while
writing it" below.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Transitive dependencies resolve at install time — `low`

- **Where:** `blueprints/dbt-duckdb-pipeline/setup.md:27` (step 3) and `:46`
  (step 5)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** the four direct dependencies are pinned with `==`. dbt-core 1.12.5
  itself declares ranges — `dbt-adapters>=1.24.5,<2.0`, `protobuf>=6.0,<8.0`,
  `metricflow>=0.213.0,<1.0` among some twenty-five — and about eighty packages
  install.
- **Why it matters:** the surface is larger than in the other Python
  blueprints here, and dbt's own adapter layer is one of the ranged packages. A
  release of any of them can change what `dbt build` does without a change in
  the repository, and the weekly setup-test is what would notice.
- **Fix:** a constraints file generated from the tested environment
  (`pip freeze > constraints.txt`, installed with `-c constraints.txt`), or a
  hashed lock. Recorded rather than fixed, consistent with the catalog's other
  pip-based blueprints (`python-cli` review, finding 3); the gap is wider here,
  hence `low` rather than `info`.

### 2. `DBT_RAW_DIR` is placed inside a SQL string literal unescaped — `low`

- **Where:** `blueprints/dbt-duckdb-pipeline/setup.md:193` (step 13)
- **Standard:** OWASP Top 10:2025 **A05 Injection**; Twelve-Factor III
- **What:** the source renders
  `read_csv('{{ env_var('DBT_RAW_DIR', 'data') }}/raw_{name}.csv', …)`. A value
  containing a single quote ends the literal.
- **Why it matters:** in the shipped design the environment belongs to the
  operator, so this is a broken query rather than an exploit. It becomes one
  if a later orchestrator builds the variable from something a user typed.
- **Fix:** none at this scope. `AGENTS.md:47` names it as configuration; a
  reader who wires it to input needs to validate it first. Reading
  configuration from the environment is itself correct (Twelve-Factor III).

### 3. The committed `profiles.yml` is where a warehouse credential would land — `info`

- **Where:** `blueprints/dbt-duckdb-pipeline/setup.md:83` (step 8)
- **Standard:** Twelve-Factor III; CLAUDE.md §5b
- **What:** the profile is committed, which is right for DuckDB — it holds a
  relative path and nothing secret.
- **Why it matters:** "Moving to a warehouse" means adding a target to this
  same file. The recipe leads the reader somewhere safe: `AGENTS.md:129` and
  `overview.md` both say every credential comes from `env_var('…')` with no
  default, so a missing variable fails instead of connecting as somebody else.
  Recorded so the next reviewer does not re-derive it.

### 4. sqlfluff lints a rendering, not the project — `info`

- **Where:** `blueprints/dbt-duckdb-pipeline/setup.md:441` (step 22)
- **Standard:** NIST SSDF v1.1, PW.7 (review and analyse code)
- **What:** the jinja templater renders `ref()` and `source()` from stand-ins.
  A macro or `var()` it does not know is linted as a guess.
- **Why it matters:** the trade is deliberate — no profile, no connection, no
  warehouse credentials in a lint job — and disclosed at `overview.md:143`.

## Found while writing it, and fixed before this review

Recorded because they are what the review would otherwise have raised, and
because each fix is now something the recipe proves.

- **A fractional amount was rounded silently** — would have been `medium`,
  OWASP Top 10:2025 **A10 Mishandling of Exceptional Conditions**. DuckDB casts
  the text `1850.5` to the integer `1851` without an error, in the model, with
  a declared `read_csv` type, and with an inferred one alike. Fixed by reading
  the source as text (`all_varchar = true`) and testing the text with a
  generic test, `whole_number`, before staging casts it. Proved by steps 36–39.
- **No step showed that a test could fail** — would have been `medium`,
  architecture question 6. A suite that has only been seen passing may be
  vacuous. Fixed with two broken copies of the data under `target/`, each of
  which must produce a non-zero exit, the named failing test, and a skipped
  mart (steps 32–39).
- **DuckDB downloads extensions at run time by default** — would have been
  `low`, **A03 Software Supply Chain Failures**. A query that touches an
  `https://` or `s3://` path makes DuckDB fetch `httpfs` from its own
  extension server, unpinned, in the middle of a build — a host no recipe here
  may reach. Fixed with `autoinstall_known_extensions` and
  `autoload_known_extensions` off in the profile (`setup.md:102`); checked by
  hand that an `https` read is then refused rather than fetched.
- **The mart's sum was `hugeint`, not the promised `bigint`** — not a security
  finding. The enforced contract refused the table on the first build, which
  is the contract doing its job.

## What was checked and found sound

- **Boundaries hold.** Raw data enters only through `_sources.yml`; staging
  casts and renames and does nothing else; business rules live in the mart.
  The one file that knows the data is CSV on disk is the one a warehouse move
  edits (hexagonal architecture — the source is the adapter).
- **The mart's shape is enforced, not described.** `contract: enforced: true`
  compares names and types before building, and has already caught one drift.
- **Every claimed test kind exists and runs:** `unique`, `not_null`,
  `relationships`, `accepted_values`, a singular reconciliation test, a unit
  test, and the project's own generic test. Step 29 asserts all 28 nodes
  succeeded and that the unit test was among them; step 30 reads the mart back
  and checks the numbers.
- **Errors stop the build (A10).** An unknown status fails a `relationships`
  test; a fractional integer fails `whole_number`; a malformed date fails the
  cast; a type change fails the contract; a missing file fails the read. In
  each case `dbt build` skips everything downstream, so a bad row never
  reaches the mart.
- **Configuration from the environment (Twelve-Factor III):** the database
  path and the raw directory, each with a local default that is not a
  production value.
- **Telemetry off (A02 Security Misconfiguration).** dbt Core sends anonymous
  usage events by default; `flags: send_anonymous_usage_stats: false` in
  `dbt_project.yml` turns them off for every command. Read in dbt's source
  (`dbt/tracking.py`, `initialize_from_flags`): the `.user.yml` id is written
  only when tracking is on, which is why step 40 checking for its absence is a
  meaningful check. `DO_NOT_TRACK` is also honoured (`dbt/cli/flags.py`).
- **No home-directory writes.** `DBT_PROFILES_DIR=.` on every command; a
  container run confirmed nothing was created under the home directory.
- **No dbt packages**, so nothing is fetched from hub.getdbt.com or git
  (A03). `AGENTS.md:117` says how to add one deliberately.
- **CI (SSDF, SLSA v1.2, A03):** actions pinned by commit SHA with the
  version in a comment — both SHAs checked against the tags on 2026-09-25;
  `permissions: contents: read`; `persist-credentials: false`; a timeout; no
  secrets; no `pull_request_target`. It installs from the same requirements
  file the recipe does.
- **Every version pinned with `==`** and read from PyPI on 2026-09-25.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The sample customers are single invented first names.
- **What it does not do is said plainly** — warehouses, orchestration,
  ingestion, concurrent writers, Python models, packages, dbt 2.0 — under
  "What it is NOT for", with "What CI cannot prove" beside it
  (`overview.md:160`).

## Verdict

**MERGE.** Two `low` findings and two `info`, none blocking. The three issues
that would have been `medium` or `low` were found while writing it and each is
now proved by a step of the recipe rather than asserted.

Finding 1 is the one worth acting on next: a constraints file would make the
weekly setup-test a check on the pins rather than on whatever PyPI resolved
that Monday.

`tier: official` is not available while `provenance: generated` (ADR 0011).
