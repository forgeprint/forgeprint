# astro-content-site — architecture and security review

- Date: 2026-09-23
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is the catalog's first `web` blueprint and the first to claim `seo` or
`accessibility`.

It is also the first blueprint here with almost no attack surface: a static
build, no server, no database, no user input, nothing loaded from a third
party. Most of the security checklist does not apply, and the review is
correspondingly short — but the two findings it does have are both about the
same thing, which is whether the blueprint's claims are as large as the words
it uses.

The manifest claims `tier: community` and `provenance: generated`. No
`critical` or `high` findings are open.

## Findings

### 1. `accessibility` is claimed, and what is tested is a subset of it — `medium`

- **Where:** `blueprints/astro-content-site/manifest.yaml:16` against
  `setup.md:300` (step 10)
- **Standard:** the catalog's own rule that a verification has to prove what a
  reader thinks it proves; WCAG 2.2 is the reference the word invokes and is
  not on `docs/review-standards.md`
- **What:** the requirement `accessibility` appears in the manifest, and the
  tests assert four things: `lang` on `<html>`, exactly one `h1`, a skip link
  pointing at the `main` landmark, and `alt` on every `<img>`. Real work, and
  four regexes.
- **Why it matters:** `resolve` matches on `requirements`. Somebody who asks
  for an accessible site gets this one, and the word promises more than static
  assertions can deliver — contrast, focus order, keyboard traps, and whether
  any alt text describes anything are all invisible here. The gap between the
  claim and the check is the kind that stops being noticed.
- **Mitigating, and the reason this is `medium` rather than `high`:** the
  blueprint says so itself, three times — in `overview.md` under "What it is
  NOT for", in `AGENTS.md` under what the tests check, and in a comment inside
  the test file. It is disclosed, prominently, in the places a reader looks.
- **Fix:** either add WCAG 2.2 to `docs/review-standards.md` and review against
  it properly, or narrow the claim. A follow-up, not a blocker: the disclosure
  is what makes the claim honest today, and removing the requirement would make
  the blueprint harder to find for the readers it does help.

### 2. `site` defaults to a domain nobody owns — `low`

- **Where:** `blueprints/astro-content-site/setup.md:104` (step 3)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**
- **What:** `site: 'https://example.com'`, which every canonical URL and every
  sitemap entry is built from.
- **Why it matters:** shipped unchanged, the site tells crawlers its canonical
  location is a domain it does not control. A sitemap full of `example.com` is
  worse than no sitemap, because a crawler believes it.
- **Mitigating:** `example.com` is the correct placeholder — RFC 2606 reserves
  it precisely so documentation cannot accidentally name a real host — and both
  the config comment and the generated `README.md` say to change it before the
  first deploy.
- **Fix:** a step that fails when `site` is still the placeholder would catch
  it, but it would also fail every CI run of the blueprint itself. Left as a
  documented placeholder, which is what it is.

### 3. The build pins Astro but not what Astro fetches — `info`

- **Where:** `blueprints/astro-content-site/setup.md:20` (step 1)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** every direct dependency is pinned to an exact version and there is
  no lockfile in the recipe, so transitive dependencies resolve at install
  time.
- **Why it matters:** identical to the trade-off the other blueprints carry.
  A committed lockfile is byte-exact and also freezes security patches; the
  catalog's position so far has been to pin direct dependencies and let the
  reader decide about a lockfile.
- **Fix:** none. Recorded so the next reviewer does not raise it again.

## What was checked and found sound

- **Nothing runs at request time.** A static build with no adapter: no server,
  no database, no sessions, no request handling. The whole of ASVS chapters on
  authentication, session management and access control is not merely
  unimplemented, it is inapplicable, and `overview.md` says so plainly rather
  than leaving a reader to infer it.
- **No third-party scripts.** Nothing loads analytics, fonts, comments or
  tag managers, so there is no supply chain in the browser and no data leaving
  the reader's machine (OWASP Top 10:2025 A03; the catalog's own PRIVACY.md
  position).
- **No JavaScript is shipped at all** for these pages — Astro sends none when
  no component is interactive, and none here is.
- **The frontmatter schema is enforced at build time.** A post missing a
  description fails the build rather than shipping an empty meta tag
  (OWASP Top 10:2025 A10 Mishandling of Exceptional Conditions — failing at the
  moment somebody is watching).
- **One `<head>`, and both props are required.** `Page.astro` is the only place
  that writes it, so a page with no description does not type-check. This is
  the structural reason the SEO claim holds rather than a convention somebody
  has to remember.
- **The tests read the build output, not the templates.** A template can be
  right while the output is wrong — a missing `site`, an integration that did
  not run — and the output is what a crawler and a screen reader actually get.
- **The canonical URL is absolute and asserted to be.** The test requires
  `https://`, which is exactly the failure a missing `site` produces.
- **Actions pinned by commit SHA** with the version in a comment (A03).
- **`npm test` builds first**, so the assertions cannot silently check a stale
  `dist/`. That is a one-word decision in `package.json` that makes the
  difference between a test suite and a habit.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  The only host named anywhere is `example.com`.

## Not applicable

- **Authentication, authorization, session management (ASVS 5.0).** No users,
  no server.
- **OWASP API Security Top 10.** No API.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: web`, no tools, no model.
- **CIS Docker.** No container.
- **Rate limiting (API4:2023).** Static files; whatever serves them decides.
- **Migrations, multi-tenancy, observability.** None claimed, none implied.

---

## Verdict

**MERGE.** One `medium`, one `low`, one `info`. The `medium` is worth stating
clearly because it will come up again: this blueprint claims a word —
`accessibility` — that is bigger than what it verifies, and it is honest about
that in the three places a reader looks. That honesty is what makes it
mergeable; the same blueprint with the same tests and no disclosure would be
`CHANGES`.

The follow-up worth doing is not to this blueprint: it is to add WCAG 2.2 to
`docs/review-standards.md`, so the next reviewer of anything claiming
`accessibility` has a reference to cite instead of a judgement to make.

`tier: official` is not available while `provenance: generated` (ADR 0011).
`tier: verified` is available the day a maintainer runs the setup themselves.
