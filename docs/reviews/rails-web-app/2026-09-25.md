# rails-web-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21); OWASP ASVS 5.0 requirement texts read from the OWASP/ASVS
  repository on 2026-09-24
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first Ruby blueprint: Rails 8.1.4 on SQLite with the Rails 8
defaults and the built-in authentication generator.

Most of the design is Rails' own, and the review therefore concentrates on two
questions: what the generated authentication leaves open, and whether the
blueprint's additions close it without opening something else. Three gaps in
the generated code were found while drafting and fixed before this review —
recorded under _Found while drafting_ so the next reviewer knows they were
looked at. No `critical` or `high` finding is open.

The single most important thing for a reader: **this is a one-machine design.**
SQLite on the container's disk, and Solid Queue only running when somebody
starts it. Both are disclosed; both are where a first deployment goes wrong.

The manifest claims `tier: community` and `provenance: generated`.

## Found while drafting, fixed before review

These were in the generated code, would have been findings here, and are
closed in 1.0.0. Recorded so they are not re-derived.

- **No password minimum — would have been `high`.** `has_secure_password` caps
  a password at 72 bytes and sets no floor, and the generated reset tests set a
  three-character password. OWASP ASVS 5.0 **6.2.1** (Level 1) requires at
  least 8. Fixed: `validates :password, length: { minimum: 15 }` at
  `blueprints/rails-web-app/setup.md:84`, with a model test and a controller
  test that a short password is refused on reset.
- **Sessions never expire — would have been `medium`.** The generated session
  lives until sign-out, behind a cookie set with `permanent` (twenty years).
  ASVS 5.0 **7.3.2** (absolute maximum session lifetime) and **7.1.1**
  (documented). Fixed: `Session::MAX_AGE` (`setup.md:101`), lookups through
  `Session.active` (`setup.md:145`), the cookie expiring with the session
  (`setup.md:160`), and a test that an aged session is redirected.
- **Action Cable authenticated with its own lookup — would have been part of
  the above.** The generator writes `ApplicationCable::Connection` with
  `Session.find_by`, a second path that an expiry check in the concern alone
  would not cover (ASVS 5.0 **7.4.1**: a terminated session must not be
  usable). Fixed at `setup.md:188`.

## Findings

### 1. No Content Security Policy — `medium`

- **Where:** the generated `config/initializers/content_security_policy.rb`,
  left commented out; nothing in `blueprints/rails-web-app/setup.md` enables it
- **Standard:** OWASP ASVS 5.0 **3.4.3** (Level 2); OWASP Top 10:2025 **A02
  Security Misconfiguration**
- **What:** responses carry no `Content-Security-Policy` header.
- **Why it matters:** CSP is the second line behind output encoding. Rails
  escapes ERB output by default, so the first line holds; the first `raw` or
  `html_safe` on user input has nothing behind it.
- **Mitigating:** disclosed in `overview.md` (Cons) and in `AGENTS.md` (What
  this does not do). Import maps with nonces make a strict policy achievable.
- **Fix:** a later version enables the initializer with `default-src 'self'`,
  `object-src 'none'`, `base-uri 'none'` and nonces for the import map, plus a
  request test that asserts the header. Not a blocker: disclosed, and a policy
  somebody has not tested against their pages breaks them.

### 2. SQLite on the container's own disk loses data on restart without a volume — `medium`

- **Where:** the generated `config/database.yml` and `Dockerfile`; started
  without a volume at `blueprints/rails-web-app/setup.md:558` (step 28)
- **Standard:** The Twelve-Factor App **VI** (processes are stateless;
  persistent data lives in a backing service) and **IV** (backing services)
- **What:** users, sessions, the cache and the job queue are four SQLite files
  under `/rails/storage` inside the container.
- **Why it matters:** a reader who deploys the image as built, with no volume,
  loses every account on the next restart — and every queued job.
- **Mitigating:** stated in `overview.md` (Cons and "What it is NOT for") and in
  `AGENTS.md` under its own heading. The check container is disposable on
  purpose.
- **Fix:** none in the blueprint; the disclosure is the right place. A
  Postgres blueprint is listed under Planned in the CHANGELOG.

### 3. No check against common or breached passwords — `medium`

- **Where:** `blueprints/rails-web-app/setup.md:84` (step 6)
- **Standard:** OWASP ASVS 5.0 **6.2.4** (Level 1: at least the top 3000
  passwords) and **6.2.12** (Level 2: breached passwords)
- **What:** the floor is length only.
- **Why it matters:** fifteen characters removes most of the common list, and
  not all of it.
- **Mitigating:** the 15-character floor — chosen over ASVS's minimum of 8 for
  this reason and said so in `overview.md` (Trade-offs); sign-in is
  rate-limited (10 attempts per 3 minutes per IP, ASVS **6.3.1**).
- **Fix:** a local list check in `User` needs a word list in the repository,
  and a breached-password check needs a network service; both are decisions
  for the reader. Recorded, not blocking.

### 4. The job supervisor does not start with the image — `low`

- **Where:** the generated `Dockerfile` `CMD`; `config/recurring.yml` at
  `blueprints/rails-web-app/setup.md:258` (step 14)
- **Standard:** The Twelve-Factor App **VIII** (concurrency: process types are
  declared); OWASP Top 10:2025 **A10 Mishandling of Exceptional Conditions**
- **What:** the image runs the web server only. Jobs run when `bin/jobs` runs
  as a second process or `SOLID_QUEUE_IN_PUMA` is set.
- **Why it matters:** a deployment that does neither accepts jobs and never
  runs them, silently — including the password-reset mail.
- **Mitigating:** session expiry does **not** depend on the job (the lookup
  enforces it), so the security property holds either way. Stated in
  `recurring.yml` itself, in `AGENTS.md` and in `overview.md`. The setup's
  container check sets `SOLID_QUEUE_IN_PUMA=1`, so the supervisor is proved to
  boot.
- **Fix:** none required.

### 5. Password-reset mail is enqueued but has nowhere to go in production — `low`

- **Where:** the generated `config/environments/production.rb` (no SMTP
  settings)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional Conditions**
- **What:** the reset request succeeds and tells the user instructions were
  sent; the delivery job fails in the queue.
- **Fix:** disclosed in `overview.md` (Cons). Configuring delivery needs a
  provider and a credential, which a generic blueprint must not invent.

### 6. Cookies carry no `__Host-` or `__Secure-` prefix — `low`

- **Where:** `blueprints/rails-web-app/setup.md:160` (step 8, `session_id`) and
  the Rails session cookie
- **Standard:** OWASP ASVS 5.0 **3.3.1** (Level 1) and **3.3.3** (Level 2)
- **What:** the `Secure` attribute half of 3.3.1 holds in production, because
  `force_ssl` marks every cookie secure; the prefix half does not.
- **Why it matters:** a prefix stops a sibling subdomain or an insecure origin
  from planting a cookie of the same name. The cookie is signed, so a planted
  value cannot name a session it did not obtain.
- **Fix:** rename to `__Host-session_id` in production only, once the
  development server runs over HTTPS or the name is environment-dependent.
  Not attempted here: a `__Host-` cookie is refused by a browser over plain
  HTTP, which would break sign-in in development.

### 7. The production image carries the development and test tools — `low`

- **Where:** the generated `Dockerfile` (`BUNDLE_WITHOUT="development"`), and
  the `group :development, :test` block at
  `blueprints/rails-web-app/setup.md:22` (step 3)
- **Standard:** CIS Docker Benchmark v1.8.0, image and Dockerfile scope —
  minimal contents (control number to be confirmed at the link, as
  `docs/review-standards.md` requires)
- **What:** Brakeman, RuboCop, bundler-audit and debug are in a group that is
  also `:test`, so Bundler installs them in the image.
- **Fix:** `BUNDLE_WITHOUT="development:test"` in the Dockerfile. Left as
  generated in 1.0.0 because it is Rails' own default and the recipe does not
  rewrite the Dockerfile; worth doing in a reader's first week.

### 8. Transitive gems float until `Gemfile.lock` is committed — `low`

- **Where:** `blueprints/rails-web-app/setup.md:22` and `:67` (steps 3 and 4)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF v1.1 (protect the software)
- **What:** every gem the application names is pinned exactly; what they
  depend on is resolved on the day the recipe runs and then locked.
- **Why it matters:** two runs on different days can produce different
  lockfiles. The lockfile, once committed, is what makes builds reproducible —
  the Docker build already refuses to run without it (`BUNDLE_DEPLOYMENT=1`).
- **Fix:** disclosed in `overview.md` (Cons). Nothing more a recipe can do
  without committing a lockfile to the catalog.

### 9. Gems install into the active Ruby, not the project — `info`

- **Where:** `blueprints/rails-web-app/setup.md:16` (step 1)
- **Standard:** CLAUDE.md rule 20 (no elevated privileges, nothing outside the
  project); a scope observation rather than a control
- **What:** `gem install rails` and `bundle install` write into the Ruby
  installation's gem directory, as every Rails project does.
- **Fix:** the recipe's preamble requires a Ruby from a version manager, so no
  step needs elevated privileges, and `overview.md` says never to use them.
  Recorded so it is not raised again.

## What was checked and found sound

- **Protected by default.** `ApplicationController` includes `Authentication`,
  so every action requires a session unless its controller opts out by name.
  `DashboardController` declares nothing and is protected, and a test proves
  an unauthenticated request is redirected — both in `bin/rails test` and
  against the production container (step 29, a `302` from `/`). OWASP Top
  10:2025 **A01**; ASVS 5.0 chapter **V8** (Authorization).
- **Session handling** (ASVS 5.0 **7.2.1–7.2.4**): reference tokens in the
  database, looked up server-side; a new session row on every sign-in; the
  cookie signed, `HttpOnly` (**3.3.4**) and `SameSite=Lax` (**3.3.2**);
  sign-out destroys the row (**7.4.1**); a password reset destroys every
  session the user had (**7.4.3**).
- **Brute force** (ASVS 5.0 **6.3.1**): `rate_limit` on sign-in and on reset
  requests, backed by Solid Cache in production. Unknown addresses on reset get
  the same response as known ones.
- **Reset tokens** expire after 15 minutes and are bound to the password
  digest, so a used token dies with the old password.
- **CSRF** is on by default for every form, and `button_to` sends the token
  with the sign-out request.
- **Transport** (ASVS 5.0 **3.4.1**): `force_ssl` and `assume_ssl` in
  production — HSTS and secure cookies, behind a TLS-terminating proxy, which
  `overview.md` states as a trade-off.
- **Secrets** (CLAUDE.md §5b; Twelve-Factor **III**): `config/master.key` is
  in `.gitignore` (step 24 checks) and `.dockerignore`, and the image is
  checked to contain the encrypted credentials but not the key (step 26). The
  container check generates its secret key base in a subshell and never prints
  it. No secret-shaped string anywhere in the blueprint; fixture passwords are
  test-only.
- **Container** (CIS Docker, image scope): multi-stage, base image pinned to
  the Ruby patch version, runs as uid 1000 (step 25 asserts `1000:1000`),
  binds to loopback on an operating-system-chosen port in the check.
- **CI** (SLSA v1.2; NIST SSDF; A03): the generated workflow is kept with every
  action pinned by commit SHA, `permissions: contents: read`, and
  `persist-credentials: false`. It runs Brakeman, bundler-audit, importmap
  audit, RuboCop and the tests.
- **Static analysis in the recipe itself.** Brakeman must report zero warnings
  and RuboCop must pass, both at pinned versions; the verification parses
  Brakeman's JSON rather than trusting an exit code.
- **Tests prove the claims.** The dashboard redirect, the expired-session
  refusal, the password floor on the model and on reset, and the job's body and
  enqueueing — each claim in `overview.md` has a test behind it.
- **No personal data, no employer information** (CLAUDE.md §5b).

## Not applicable

- **OWASP API Security Top 10.** `project_type: web`; no API is exposed.
- **OWASP LLM 2025, Agentic 2026, MCP guidance.** No model, no tools.
- **Authorization beyond "signed in"** (ASVS 5.0 V8 object-level checks). The
  blueprint has one page and no per-user records; `overview.md` says there are
  no roles.
- **Password change** (ASVS 5.0 **6.2.3**). There is no change-password flow,
  only reset; the requirement applies when one is added.
- **Multi-tenancy, file upload, OAuth.** Not claimed, and skipped or absent.
- **CIS Docker host and daemon controls.** The reader's environment, not the
  blueprint's.

---

## Verdict

**MERGE.** No `critical` or `high` open. Three `medium` (no CSP, SQLite needs a
volume, no common-password check), five `low`, one `info`, all disclosed where
a reader looks.

The one `high` this review would have raised — no password minimum — was found
while drafting and closed before the pull request, together with the session
lifetime and the second session lookup in Action Cable.

`tier: official` is not available while `provenance: generated` (ADR 0011).
