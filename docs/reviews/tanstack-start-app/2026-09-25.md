# tanstack-start-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, following
  `skills/blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
TanStack Start on Vite with a Nitro Node server, claiming
`requirements: [auth, testing, ci]` for `project_type: web`. The review is
therefore dominated by authentication and session management, and by what the
browser receives.

The authentication is small and honest about it: one account from the
environment, an scrypt hash, a session cookie sealed by the framework, a guard
proved at the HTTP level against the built server. What a reader must know
before building on it is the other half of the risk, which is not in the code:
the framework's API is young and the Node adapter it generates is a beta.

Two findings from the first pass were fixed in the recipe before this report,
and are recorded under "Fixed before merge" so the reasoning survives. No
`critical` or `high` finding is open.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. The sign-in rate limit is per process and keyed on the socket address — `medium`

- **Where:** `blueprints/tanstack-start-app/setup.md:305` (step 11,
  `src/server/rate-limit.ts`) and `:513` (step 15, the call site)
- **Standard:** OWASP ASVS 5.0.0, Authentication chapter (brute-force and
  anti-automation controls); OWASP API Security Top 10 2023 **API4:2023
  Unrestricted Resource Consumption**
- **What:** ten attempts per address per fifteen minutes, counted in a `Map` in
  the server process. The address is the socket's; `X-Forwarded-For` is
  deliberately not read.
- **Why it matters:** two ways the limit stops meaning what it says. Behind a
  reverse proxy every client has the proxy's address, so one person's ten bad
  guesses lock everybody out of sign-in for fifteen minutes. Across several
  instances or a restart, each process counts from zero.
- **Mitigating:** both are stated in `AGENTS.md` and under Cons in
  `overview.md`, with the fix; the default is the safe one (spoofable headers
  are not trusted); and the e2e suite proves the 429 on a single instance.
- **Fix:** before deploying behind a proxy or on more than one instance, move
  the limit to the proxy or to a shared store, or read the client address from
  a header only a proxy you control sets (`getRequestIP({ xForwardedFor: true })`).

### 2. The Content-Security-Policy does not restrict scripts — `medium`

- **Where:** `blueprints/tanstack-start-app/setup.md:600` (step 17,
  `src/server.ts`)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**; OWASP ASVS
  5.0.0, Web Frontend Security chapter
- **What:** the policy is `frame-ancestors 'none'; base-uri 'self';
form-action 'self'; object-src 'none'`. There is no `script-src`.
- **Why it matters:** a CSP's main value is limiting what an injected script can
  do. React escapes output and nothing here renders HTML from input, so there is
  no known injection point; the policy is the second line, and it is missing.
- **Mitigating:** disclosed in `AGENTS.md` and `overview.md`, with the reason:
  Start's server rendering writes inline scripts, so a script policy needs a
  per-request nonce, and proving every inline script carries it needs a
  browser, which this recipe does not download. The parts that need no nonce
  are set and asserted by the e2e suite.
- **Fix:** pass a per-request nonce to Start's handler (its request context
  accepts one) and add `script-src 'self' 'nonce-…'`, with a browser test that
  the page still hydrates. Recorded under "Planned" in the CHANGELOG.

### 3. The production HTTP server is a beta — `medium`

- **Where:** `blueprints/tanstack-start-app/setup.md:44` (step 2,
  `"nitro": "3.0.260903-beta"`), and transitively `h3` 2.0.1-rc.20 under the
  session code
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF SP 800-218 v1.1, PW.4 (reuse well-secured software)
- **What:** the Node server that serves every request, and the library that
  seals the session cookie, are pre-release versions.
- **Why it matters:** a pre-release has no support promise; a security fix may
  arrive only in a later pre-release with other changes attached.
- **Mitigating:** it is what TanStack's own generator emits for
  `--deployment nitro`; the version is pinned exactly and locked by
  `package-lock.json`; `npm audit` was clean on 2026-09-25; the recipe runs
  weekly in CI. `overview.md` states the beta and the young API as the main
  risk, first.
- **Fix:** none now. Move to Nitro 3 stable when it is published, in its own
  version bump.

### 4. Errors during server rendering are serialized into the page — `low`

- **Where:** framework behaviour; observed on the built server while writing
  the recipe (a route error's message appeared in the dehydrated state)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional Conditions**;
  OWASP ASVS 5.0.0, Security Logging and Error Handling chapter
- **What:** when a loader or `beforeLoad` throws during server rendering, Start
  serializes the error, message included, into the HTML for hydration.
- **Why it matters:** an error message that names a file, a query or a
  configuration value is sent to the visitor.
- **Mitigating:** the configuration errors no longer reach this path —
  `src/server.ts` refuses the request first and logs the reason server-side; an
  invalid path parameter throws `notFound()` rather than the validation error.
  Disclosed under Cons.
- **Fix:** keep error messages in route code free of detail, and log detail
  server-side. Worth re-checking when Start offers a production redaction switch.

### 5. A session cannot be revoked individually — `low`

- **Where:** `blueprints/tanstack-start-app/setup.md:379` (step 12,
  `useSession`) and `:535` (sign-out)
- **Standard:** OWASP ASVS 5.0.0, Session Management chapter (session
  termination)
- **What:** the session lives only in the sealed cookie. Sign-out clears the
  browser's copy; a copied cookie remains valid until its eight-hour lifetime
  ends, which is enforced when the cookie is unsealed.
- **Why it matters:** a stolen cookie cannot be killed without rotating
  `SESSION_SECRET`, which ends every session.
- **Mitigating:** the cookie is `HttpOnly`, `Secure` in production and
  `SameSite=Lax`, which makes theft hard; the lifetime is short; the trade-off
  is stated in `AGENTS.md` and `overview.md`.
- **Fix:** if revocation matters, store a session id server-side and check it
  in `getCurrentUser`.

### 6. No `Cache-Control` on authenticated responses — `low`

- **Where:** `blueprints/tanstack-start-app/setup.md:608` (step 17, where
  headers are set) and `:482` (`getCurrentUser`, a GET server function)
- **Standard:** OWASP ASVS 5.0.0, Data Protection chapter (sensitive data in
  caches)
- **What:** `/dashboard` and the `getCurrentUser` response depend on the
  cookie but carry no `Cache-Control: private, no-store`.
- **Why it matters:** a misconfigured shared cache could store one user's page.
  There is one account, so today the exposure is the username.
- **Fix:** set `Cache-Control: no-store` in `src/server.ts` on responses to
  requests that carry the session cookie, and assert it in the e2e suite.

### 7. The scaffolder sends telemetry unless told not to — `info`

- **Where:** `blueprints/tanstack-start-app/setup.md:18` (step 1)
- **Standard:** NIST SSDF SP 800-218 v1.1, PO.3 (toolchain) — what the build
  tools do on the developer's machine
- **What:** `@tanstack/cli` posts usage events to Google Analytics by default
  and writes an identifier under the home directory. The recipe sets
  `TANSTACK_CLI_TELEMETRY_DISABLED=1`, which stops both (read in the CLI's
  source, `telemetry-config.js`), and `AGENTS.md` repeats it for later runs.
  The generated application has no telemetry.

## Fixed before merge

Raised in the first pass of this review and fixed in the recipe; recorded so
the reasoning is not lost.

- **No rate limit on sign-in** (was `high` against the `auth` claim: OWASP ASVS
  5.0.0 Authentication chapter; API4:2023). scrypt at N=2^17 made an unlimited
  endpoint both a guessing oracle and a way to spend the server's CPU. Now
  limited before the hash runs, unit-tested, and proved by the e2e suite (the
  eleventh attempt is a 429 with `Retry-After`).
- **The sign-in page could be framed** (was `medium`: A02; clickjacking). Now
  `frame-ancestors 'none'`, asserted by the e2e suite.

## What was checked and found sound

- **Credential storage** (ASVS 5.0.0 Cryptography and Authentication chapters):
  scrypt from `node:crypto`, N=2^17, r=8, p=1, a random 16-byte salt per hash,
  compared with `timingSafeEqual`. The hash runs whether or not the username
  matched, and one message covers both failures, so neither text nor timing
  says which was wrong. The helper script reads the password from standard
  input, not the command line, and a test holds its parameters to the module's.
- **Session management** (ASVS 5.0.0 Session Management chapter): Start's
  `useSession` seals the cookie (encrypted and integrity-protected) with a
  secret of at least 32 characters; `HttpOnly`, `SameSite=Lax`, `Secure` in
  production; an eight-hour lifetime checked server-side; the session is
  cleared before sign-in writes to it (fixation). A tampered cookie is proved to
  be no session.
- **Access control** (Top 10:2025 A01): the guard is a pathless layout's
  `beforeLoad` that asks a server function, so the decision is the server's on
  the first request and on every client navigation. Proved at two levels: the
  route's own `beforeLoad` in a unit test, and a 307 to
  `/login?redirect=%2Fdashboard` from the built server. `AGENTS.md` says plainly
  that a guard does not protect server functions and each must authorize itself.
- **Open redirect** (A01): `safeRedirect` accepts only a path on this site and
  refuses `//host` and `/\host`; the sign-in function answers such a target with
  400, and the sign-in page drops it from its query string.
- **CSRF** (A01; ASVS Web Frontend Security): `createCsrfMiddleware` on every
  server function, written out in `src/start.ts`; a cross-site post is proved to
  get 403 and no cookie. `SameSite=Lax` is the second layer.
- **Input validation** (ASVS Validation and Business Logic chapter): Zod at every
  boundary — server-function input, search parameters, path parameters. A
  malformed request is a 400, not a 500; a bad search value falls back to a
  default; a bad path segment is a 404.
- **Configuration** (Twelve-Factor III; A02): read in one module, from the
  environment. Development falls back to values that announce themselves as
  fake; the production build refuses them — the development account is
  recognised by its password, not by a string, so re-hashing it does not get it
  past the check. The check runs when the server loads, logs
  `Refusing to serve: …` and answers 503 to everything; the e2e suite starts a
  server with the published secret and with no account to prove both.
  `import.meta.env.PROD` is replaced at build time, so an environment variable
  cannot put the production build into development mode.
- **The server boundary** (A02; ASVS Data Protection): the recipe checks the
  built browser bundle for `scrypt`, `SESSION_SECRET` and the development
  secret, and for source maps. `AGENTS.md` explains why a module-scope secret in
  a route file would ship.
- **Error handling** (A10): a misconfigured server fails closed with a logged
  reason; a failed sign-in is a redirect with a generic message; an unknown
  note is a 404.
- **CI** (SLSA v1.2; SSDF): actions pinned by full commit SHA with the version
  in a comment, `permissions: contents: read`, `persist-credentials: false`,
  `npm ci` from the committed lock file. The workflow runs build, type check,
  unit and e2e tests — the same things the recipe runs.
- **Supply chain** (A03): every version exact, verified against the npm registry
  on 2026-09-25; the generator's `latest` entries replaced; the generator itself
  pinned (`@tanstack/cli@0.71.0`) and fetching only npm packages (read in its
  source: the only non-npm fetch is a template registry that is used only when
  `CTA_REGISTRY` is set). No authentication library: sealing is the framework's,
  hashing is the runtime's.
- **Test strategy:** the tests prove the claims rather than compile them — the
  guard, the cookie attributes, the tampered cookie, CSRF, the rate limit, the
  400s, the headers and the refusals are all asserted against the production
  build, on ports the operating system chooses.
- **What it does not do** is stated: one account, no database, no shared rate
  limit, no script policy, no revocation — in `AGENTS.md` and `overview.md`.

## Not applicable

- **OWASP API Security Top 10 as a whole** — `project_type: web`. The server
  functions are an API surface, so API4 is cited above; object-level
  authorization (API1) has no objects to apply to, since there is one user and
  no per-user data.
- **CIS Docker Benchmark** — no container. The build runs as a plain Node
  process.
- **OWASP LLM / Agentic Top 10, MCP guidance** — not an agent.
- **WCAG 2.2** — `accessibility` is not claimed. The pages use native form
  controls with labels and declare `lang`, but nothing is asserted about
  contrast or focus, and the blueprint makes no claim.
- **Multi-factor authentication, account recovery** — not claimed; one account
  from the environment is the stated user model.
