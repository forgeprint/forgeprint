## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
It is the catalog's first `cli` blueprint.

Most of the security checklist does not apply and says so below: no network, no
database, no user input beyond `argv`, nothing persisted, no container. What is
left is the question a CLI blueprint actually has to answer — **is the thing
testable, and does it behave like a program a script can call** — and on both
it does well enough that the two findings are about scope rather than defects.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. `argv` is input, and nothing here validates it beyond its shape — `low`

- **Where:** `blueprints/node-cli/setup.md:104` (step 5)
- **Standard:** OWASP ASVS 5.0, Validation chapter
- **What:** Commander enforces arity and option types; `greet` then interpolates
  the argument straight into a string. For this example that is the whole
  program and there is nothing to exploit — no shell, no file path, no query.
- **Why it matters:** the next command somebody adds will take a path or a URL,
  and the example sets the pattern. A blueprint teaches by what it shows.
- **Fix:** none required at this scope. `AGENTS.md` tells the reader to put the
  work in its own module with its own types, which is where validation belongs.
  Worth revisiting if a future option value ever reaches a filesystem call.

### 2. No dependency lockfile — `info`

- **Where:** `blueprints/node-cli/setup.md:24` (step 1)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**;
  SLSA v1.2
- **What:** Commander, TypeScript and `@types/node` are pinned exactly; their
  transitive dependencies resolve at install time.
- **Why it matters:** the same trade-off every blueprint in this catalog
  carries. A committed lockfile is byte-exact and also freezes security
  patches.
- **Fix:** none. Recorded so the next reviewer does not raise it again.

## What was checked and found sound

- **The tests drive the parser, not the function.** `createProgram` takes its
  output as a parameter, so a test reads what the tool would have printed. A
  test that called `greet()` directly would pass while the option was
  misspelled in the command definition — which is the failure that actually
  happens in a CLI.
- **`exitOverride` has its own test.** Without it a parse error calls
  `process.exit` and takes the test runner with it, and the failure looks like
  an unrelated crash.
- **The binary translates the override back into exit codes.** This is the part
  worth calling out: `exitOverride` is right for tests and wrong for a program,
  and `bin.ts` catches the thrown error and exits with the code Commander would
  have used. Without it `tool --help` exits 1, and every script that checks the
  status is quietly wrong. **The recipe proves it** — step 14 runs `--help` as
  an action, so a non-zero exit fails the step. It was caught exactly that way
  while building this.
- **Exit codes are treated as the interface**, and step 15 asserts a bad
  invocation is non-zero rather than silently doing nothing.
- **Output goes through one function in one file.** Nothing else touches a
  stream, which is what makes the tool usable as a library and testable without
  capture.
- **Actions pinned by commit SHA** with the version in a comment
  (OWASP Top 10:2025 A03).
- **`private: true`**, deliberately: publishing is a different set of decisions
  and `overview.md` says so rather than half-doing it.
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).

## Verdict

**MERGE.** One `low`, one `info`, neither blocking. The blueprint's whole
argument is testability and it makes that argument structurally rather than by
asserting it — and the one thing that could have been wrong without anyone
noticing, the exit code of `--help`, is a step that fails when it breaks.
