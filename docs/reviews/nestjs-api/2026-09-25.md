# nestjs-api — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 and 2026-09-23
  (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first NestJS blueprint and its second TypeScript `api`, after
`ts-http-service`.

The central difference from `ts-http-service` is the one that review asked
for: authentication is the framework's default rather than a placement
convention. `JwtAuthGuard` is an `APP_GUARD`, the only way past it is
`@Public()`, and the tests prove both halves — a controller declared with no
decorator at all is refused, and the list of `@Public()` handlers is asserted
to be exactly the health check. Ownership is enforced in the data layer and
tested across two subjects, which is what makes `API1` a checked control here
rather than a non-applicable one.

The most important thing a reader should know: there is no rate limiting, no
logging of rejected tokens and no TLS to Postgres. All three are named in
`AGENTS.md` or `overview.md`; none is hidden.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Rejected tokens leave no trace in the log — `medium`

- **Where:** `blueprints/nestjs-api/setup.md:255` (step 7, `jwt-auth.guard.ts`)
- **Standard:** OWASP Top 10:2025 **A09 Security Logging and Alerting
  Failures**; OWASP ASVS 5.0, Security Logging chapter (authentication
  failures are logged)
- **What:** a token that fails verification becomes a 401 and nothing else.
  The problem-details filter logs only 5xx, so a stream of forged or expired
  tokens is invisible to whoever operates the service.
- **Why it matters:** credential stuffing against an issuer, a leaked secret
  being probed, or a client stuck on an expired token all look the same from
  outside — silence. The guard is the one place that knows, and it says
  nothing.
- **Mitigating, and why this is `medium`:** the rejection itself is correct and
  tested, the reason is correctly withheld from the caller, and `AGENTS.md`
  lists structured logging under "What this does not do".
- **Fix:** in the `catch` block, `Logger.warn` the method, the path and the
  error's class name (never the token, never the claims), before throwing.
  Missing tokens are normal traffic and need not be logged; invalid ones are
  not.

### 2. No rate limiting — `low`

- **Where:** `blueprints/nestjs-api/setup.md:660` (step 19, `app.module.ts`)
- **Standard:** OWASP API Security Top 10 2023, **API4:2023 Unrestricted
  Resource Consumption**
- **What:** nothing bounds how often a caller can hit a route. Two partial
  controls exist: `GET /items` returns at most 100 rows, and the JSON body
  parser keeps Nest's default size limit.
- **Why it matters:** exposed directly, every route including the token check
  can be hammered at no cost to the caller.
- **Fix:** disclosed in `overview.md` ("NOT for") and `AGENTS.md`, and
  `@nestjs/throttler` is named as the usual addition. The CHANGELOG carries it
  under Planned. Recorded so it is not raised again.

### 3. The connection to Postgres is not encrypted by default — `low`

- **Where:** `blueprints/nestjs-api/setup.md:608` (step 17, `options.ts`)
- **Standard:** OWASP ASVS 5.0, Secure Communication chapter; OWASP Top
  10:2025 **A02 Security Misconfiguration**
- **What:** the DataSource passes `DATABASE_URL` through unchanged and sets no
  `ssl` option. Locally and in CI the database is on the same host, which is
  correct; in a deployment, whether the connection is encrypted depends on
  what the reader puts in the URL.
- **Why it matters:** a managed Postgres reached over a network with the URL
  copied from this recipe would be unencrypted.
- **Fix:** `pg` reads `sslmode` from the URL, so `?sslmode=verify-full` is a
  configuration change, not a code change. `AGENTS.md` names "no TLS to
  Postgres". Worth a sentence in the generated `README.md` in a later version.

### 4. HMAC means the verifier holds the signing key — `low`

- **Where:** `blueprints/nestjs-api/setup.md:299` (step 8, `auth.module.ts`)
- **Standard:** OWASP ASVS 5.0, Cryptography chapter; OWASP API2:2023
- **What:** HS256 with a shared secret. `algorithms: ['HS256']` prevents
  algorithm confusion and the secret must be 32 characters or more; the secret
  that verifies is the secret that signs.
- **Why it matters:** the same finding as `ts-http-service` and
  `go-http-service`. Fine for one internal issuer, wrong the moment a third
  party issues tokens.
- **Fix:** stated in `overview.md` under "NOT for", with the file that changes.

### 5. The runtime image ships a shell and npm — `low`

- **Where:** `blueprints/nestjs-api/setup.md:1100` (step 25, `Dockerfile`)
- **Standard:** CIS Docker Benchmark v1.8.0, image scope (minimal contents)
- **What:** the final stage is `node:22.23.3-alpine3.24`. It runs as `node`,
  installs from the lockfile with `npm ci` and prunes development dependencies,
  but still contains a shell and `npm`.
- **Why it matters:** less for an attacker to use after a compromise is the
  point of a minimal image.
- **Fix:** not a one-line swap here. The migration container runs
  `npm run migration:run` from the same image, deliberately (step 39), so a
  distroless final stage would need the migration command rewritten as
  `node node_modules/typeorm/cli.js ...`. Worth doing together with a test
  that the migration container still works.

### 6. An unauthenticated caller can tell a real route from a missing one — `info`

- **Where:** `blueprints/nestjs-api/setup.md:314` (step 9) with step 7
- **Standard:** OWASP API Security Top 10 2023, **API9:2023 Improper Inventory
  Management**
- **What:** `/items` answers 401 and `/nope` answers 404 without a token, so
  routes can be enumerated. This is normal behaviour for the framework and for
  almost every API.
- **Fix:** none proposed. The OpenAPI document, when enabled, publishes the
  same list on purpose.

## What was checked and found sound

- **Default-deny is real and tested.** `APP_GUARD` covers routes that did not
  exist when it was written; a probe controller with no decorator is refused
  in the tests (OWASP API5:2023; A01). The allow-list of `@Public()` handlers is
  asserted, and the assertion refuses to pass on an empty controller list.
- **Token verification is complete.** `algorithms`, `audience` and `issuer` in
  `verifyOptions`, plus an explicit `exp` and `sub` check because jsonwebtoken
  accepts a token with no `exp`. Forged, wrong-audience and expiry-less tokens
  each have a test (OWASP API2:2023; ASVS 5.0 self-contained tokens).
- **Object-level authorization in the data layer.** Every `ItemsService`
  method takes the owner; somebody else's item is 404; a test creates as one
  subject and reads as another (OWASP API1:2023).
- **Mass assignment is refused, not trimmed.** `whitelist` and
  `forbidNonWhitelisted` on a global `ValidationPipe`, and a test that sending
  `ownerId` is a 400 (OWASP API3:2023).
- **The pipeline is providers, not `main.ts` calls,** so the tests exercise the
  same guard, pipe and filter production runs.
- **Errors do not leak.** Every error is RFC 9457 `application/problem+json`;
  a non-HTTP exception is a 500 with no detail and its stack goes to the log
  (OWASP Top 10:2025 A10).
- **Configuration fails closed** before anything is constructed, naming the
  settings and never their values; a test checks the secret is not echoed, and
  the recipe starts the image unconfigured and asserts exit code 1 and the
  message (Twelve-Factor III; A10).
- **Migrations are reviewed SQL.** `synchronize: false`, a test that the
  applied migrations equal the entity schema, `migration:check` in the recipe
  and in the generated CI, and migrations listed as classes so the image
  carries them — which the recipe proves by running them from the image.
  The service never migrates on startup.
- **OpenAPI is off by default** because `SwaggerModule` serves outside the
  guard; the recipe enables it explicitly to check it.
- **`/health` touches nothing** (A09; Twelve-Factor IX); shutdown hooks close
  the pool on SIGTERM; `x-powered-by` is disabled.
- **Container:** multi-stage, `npm ci` from the lockfile, development
  dependencies pruned, `USER node` asserted by the recipe, a `HEALTHCHECK`,
  base images pinned to a patch tag (CIS Docker image scope; A03).
- **Local database on loopback with an OS-chosen port** (A02).
- **Generated CI:** `permissions: contents: read`, actions pinned by commit
  SHA with the version in a comment, `npm ci` (SSDF PS; SLSA v1.2 build track;
  A03).
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  Every credential-shaped value reads as `local-development-only`.

## Not applicable

- **Token issuance, password storage, session management and refresh (ASVS
  5.0).** The service verifies only; `overview.md` says so.
- **RBAC and function-level roles beyond authenticated/anonymous.** Not
  claimed; `overview.md` says there is no RBAC.
- **CORS and browser security headers.** Not claimed; no browser is expected
  to call it directly, and `overview.md` says so.
- **Multi-tenancy.** Not claimed. Ownership by `sub` is not tenant isolation.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: api`.
- **CIS Docker host and daemon controls.** A blueprint does not configure the
  reader's daemon.

## Verdict

**MERGE.** No `critical`, no `high`. One `medium`, four `low`, one `info`.

The `medium` is a one-block change to the guard and belongs in the first
revision; it does not change what the blueprint promises and the gap is
disclosed. Nothing here would have been caught by `lint-setup`, so no rule is
proposed.

`tier: official` is not available while `provenance: generated` (ADR 0011).
