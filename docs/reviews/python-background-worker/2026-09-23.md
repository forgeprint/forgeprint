# python-background-worker — architecture and security review

- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first `data` blueprint and the first to carry `background-jobs`.

A worker has a small external surface — it accepts no requests and exposes no
port — so the security questions are about the trust boundary of the queue
itself: who can enqueue, what a task will run, and what happens when one fails.
The blueprint answers the third thoroughly and the first two by omission,
which is defensible for a worker behind a private broker and is the thing a
reader most needs told.

What it does unusually well is make the failure modes explicit: every Celery
setting carries the failure it prevents.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Anything that can reach the broker can run a task — `medium`

- **Where:** `blueprints/python-background-worker/setup.md:80` (step 7); the
  absence of any authentication on Redis
- **Standard:** OWASP Top 10:2025 **A01 Broken Access Control**; ASVS 5.0,
  Access Control
- **What:** Celery's trust boundary is the broker. A client that can write to
  the queue can invoke any registered task with any arguments, and the worker
  will run it. Redis here has no password and no TLS.
- **Why it matters:** it is correct for the development compose file — the port
  is bound to loopback and the blueprint says so. It is wrong the moment the
  broker is shared, and nothing in the blueprint marks that transition. A
  reader who moves the same configuration to a managed Redis has an unprotected
  task-execution endpoint.
- **Mitigating:** the compose file binds to `127.0.0.1` with the reason in a
  comment, and `overview.md` describes Redis as "the common choice and the
  right starting point; not the durable one".
- **Fix:** one paragraph in `AGENTS.md` under a heading of its own — the broker
  is the authentication boundary, so a shared one needs a password and TLS
  (`rediss://`), and the worker should not be reachable from anything that is
  not the producer. Worth adding; not a blocker, because the shipped
  configuration is loopback-only.

### 2. Task arguments are trusted, and the example does not show validation — `low`

- **Where:** `blueprints/python-background-worker/setup.md:118` (step 7)
- **Standard:** OWASP ASVS 5.0, Validation
- **What:** `resize` checks that its arguments are positive and raises
  `ValueError`, which is exactly right and is also the whole of it.
- **Why it matters:** the first real task will take an identifier, and the
  second will take a path. Arguments arrive as JSON from whoever can write to
  the queue, so a task that opens `args[0]` as a file is the shape to avoid.
  `AGENTS.md` says "pass an identifier, not an object", which is about
  serialisation rather than about trust.
- **Fix:** the same paragraph as finding 1 covers it — arguments are input.

### 3. Broker and result backend share one Redis — `low`

- **Where:** `blueprints/python-background-worker/setup.md:301` (step 18)
- **Standard:** Twelve-Factor IV (backing services)
- **What:** database 0 for the broker and 1 for results, on the same instance.
- **Why it matters:** fine to start, and a busy queue competing with a result
  store for the same memory and the same eviction policy is a real problem
  later — particularly since `result_expires` is what keeps the second from
  growing.
- **Fix:** none. `overview.md` states it under Cons, which is the right place.

### 4. `--pool=solo` in the setup is a concession the reader must not copy — `info`

- **Where:** `blueprints/python-background-worker/setup.md:311` (step 19)
- **Standard:** none; a usability observation
- **What:** the check runs the worker with the solo pool because the default
  prefork pool does not fork on Windows.
- **Why it matters:** a reader copying the command into production gets a
  single-threaded worker.
- **Fix:** already stated in `overview.md` under Cons and in the step's own
  sentence. Recorded so it is not raised again.

## What was checked and found sound

- **The queue is actually exercised.** The setup starts a worker, enqueues a
  job and reads the result back. Unit tests on a Celery task prove the function
  works; only this proves the task is registered, reachable and serialisable.
  That distinction is the catalog's own rule about verifications, applied well.
- **The tests are the other half and need no broker**, so the logic runs in
  milliseconds and in CI without a service. Both halves on purpose, and
  `AGENTS.md` explains why either alone is insufficient.
- **Every setting carries the failure it prevents.** `acks_late` with
  `task_reject_on_worker_lost` — either alone still drops a job when the
  process is killed, which is the single most common Celery data-loss bug.
  `worker_prefetch_multiplier=1`. Both time limits. `result_expires`. This is
  the most valuable part of the blueprint (OWASP Top 10:2025 A10, mishandling
  of exceptional conditions).
- **The retry policy is a decision and a test guards it.**
  `autoretry_for=(TransientFailure,)`, with a test asserting the tuple — so
  adding `Exception`, which turns a poison message into four attempts, fails.
- **Tasks have explicit names**, so a rename does not orphan queued jobs. Also
  asserted by a test.
- **The worker refuses to start without a broker**, read at import. A worker
  silently not connected is indistinguishable from an empty queue.
- **Redis binds to loopback on an operating-system-chosen port**, so it neither
  collides with an existing Redis nor listens on the network — the same lesson
  `nextjs-fullstack-app` learned by failing, carried forward rather than
  repeated.
- **Every version pinned with `==`**, CI installs from the same file the recipe
  does, and actions are pinned by commit SHA (SSDF; SLSA v1.2; A03).
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).

## Not applicable

- **OWASP API Security Top 10.** No API; the worker accepts no requests.
- **Authentication, session management, password storage (ASVS 5.0).** No
  users. The access-control question is finding 1 and is about the broker.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: data`; no model, no
  tools exposed to one.
- **Rate limiting (API4:2023).** No public surface. Celery has task rate limits
  and they are a capacity decision rather than a security one here.
- **CIS Docker.** The compose file runs a stock Redis for development; the
  worker ships no image.
- **Migrations, multi-tenancy, transport security.** No database, no tenants,
  nothing listening.

---

## Verdict

**MERGE.** One `medium`, two `low`, one `info`.

The `medium` is worth acting on and is not a blocker: the shipped configuration
is loopback-only and says so, but the blueprint never states that **the broker
is the authentication boundary** — that anything able to write to the queue can
run any registered task with any arguments. One paragraph in `AGENTS.md` closes
both it and finding 2, and it belongs there rather than in this report, because
the person who needs it is the one adding the second task.

`tier: official` is not available while `provenance: generated` (ADR 0011).
