# nextjs-fullstack-app — architecture and security review

- Date: 2026-09-23
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's first blueprint with a database, and the first to carry
`migrations` — a requirement that had sat in the taxonomy since the first week
with nothing behind it.

The review of a `web` blueprint with a data layer is normally dominated by
access control. Here it is dominated by the absence of it, and the question is
whether that absence is a scope decision or a hole. It is a scope decision, and
an unusually well-declared one: there is no authentication, and the blueprint
says so four times across `overview.md` and `AGENTS.md`, including as the first
item under "What it is NOT for".

What it does well is the thing it claims: migrations are an artefact somebody
reads, and a test proves the migration produced the columns the schema
describes.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Every page and every route is public — `medium`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:243` (step 10), and the
  absence of any middleware
- **Standard:** OWASP Top 10:2025 **A01 Broken Access Control**; OWASP API
  Security Top 10 2023 **API5:2023**
- **What:** no authentication, no session, no user table, no middleware. The
  page reads the database and renders it to anybody who asks.
- **Why it matters:** the blueprint is named "full-stack app", and that phrase
  is read by most people as including users. Somebody who skims the name,
  copies the recipe and adds a second table has built a public database
  browser.
- **Mitigating, and why this is `medium` rather than `high`:** `auth` is **not
  in `requirements`**, so the resolver never offers this to somebody who asked
  for authentication. `overview.md` leads "What it is NOT for" with it,
  `AGENTS.md` repeats it under "What this does not do", and both say the
  omission is deliberate because adding it changes the data layer as well as
  the routing. A declared absence is a scope decision; what keeps this at
  `medium` rather than `low` is the name.
- **Fix:** none to the code. Worth considering whether the slug should say what
  it is — the catalog's own rule is that a verification must prove what a
  reader thinks it proves, and a name is a claim too.

### 2. The database password is a literal in `compose.yaml` and in CI — `low`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:296` (step 12) and
  `:330` (step 14)
- **Standard:** OWASP Top 10:2025 **A02 Security Misconfiguration**;
  CLAUDE.md §5b
- **What:** `POSTGRES_PASSWORD: local-development-only`, repeated in the CI
  service and in the connection string the recipe builds.
- **Why it matters:** it is the right answer for a throwaway development
  database and the wrong pattern to copy into anything else. The value names
  itself as not real, which is the catalog's own rule for example credentials,
  and the port is bound to loopback so it is not reachable from the network.
- **Fix:** none. Recorded because a reader who copies `compose.yaml` into a
  staging environment inherits it, and nothing in the file says not to.

### 3. `.env*` is git-ignored and no `.env` is ever created — `info`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:311` (step 13)
- **Standard:** CLAUDE.md §5b, mechanical protection
- **What:** the ignore file covers `.env*` before any environment file exists.
- **Why it matters:** this is the correct order and worth recording as such.
  The first `.env` a reader writes is already ignored, rather than being
  ignored after the commit that leaked it.

### 4. No connection retry, and the failure mode is a stack trace — `low`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:156` (step 5)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**
- **What:** `db()` throws when `DATABASE_URL` is missing, which is right. What
  it does not do is handle the database being unreachable — that surfaces as
  whatever `postgres` throws, inside a React server component.
- **Why it matters:** in Next, an unhandled error in a server component becomes
  a generic error page, and the reason lands in the server log. No error
  boundary is set up, so a reader whose database is down sees the default
  screen and has to know to look in the log.
- **Fix:** an `error.tsx` boundary is the Next-native answer and is one file.
  Left out here rather than added unverified, and `overview.md` lists "no error
  boundary" under what this does not do.

## What was checked and found sound

- **Migrations are generated, committed and read.** The schema is the source,
  the SQL is the output, and `AGENTS.md` says plainly that a renamed column can
  come out as a drop and an add — data loss that passes review when nobody
  opens the file. That sentence is the most valuable thing in this blueprint.
- **The test runs against a real Postgres** and asserts that the migration
  produced the columns the schema describes, including that the timestamp
  default came from the database. A mock would agree with the schema by
  construction and prove nothing (the catalog's rule that a verification must
  prove something).
- **The pool is created on first use, not at module scope.** Importing the
  client during a build would open a connection, and a build should not need a
  database. Not per request either, which is the classic way to exhaust one.
- **`closeDb()` exists with its reason written down.** A pool keeps the event
  loop alive; a suite that opens one and does not close it hangs with no
  failure and no output.
- **`DATABASE_URL` has no default.** Nothing falls back to a real database.
- **The database binds to loopback on an operating-system-chosen port.** Both
  halves matter: loopback because a database on `0.0.0.0` is reachable from
  whatever network the machine is on, and a chosen port because a fixed 5432
  collides with whatever else is already using it. The second half was found by
  running the recipe twice.
- **`withTimezone` on the timestamp**, with the reason beside it.
- **The page that reads the database declares itself dynamic**, so the build
  does not need a database.
- **Actions pinned by commit SHA**; CI runs the migration, the tests and the
  build against a Postgres service — the same three things the recipe does
  (OWASP Top 10:2025 A03; SSDF).
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).

## Not applicable

- **Authentication, session management, password storage (ASVS 5.0).** Not
  claimed; `auth` is not in `requirements` and the absence is declared four
  times.
- **BOLA / object-level authorization (API1:2023).** No owner on any row, and
  no users to own them.
- **Rate limiting (API4:2023).** No API surface beyond the rendered page.
- **Multi-tenancy.** Not claimed.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: web`.
- **CIS Docker.** The compose file runs a stock Postgres for development; the
  application ships no image.
- **WCAG 2.2.** `accessibility` is not claimed. The layout sets `lang` and uses
  semantic elements, which is a floor rather than a claim.

---

## Verdict

**MERGE.** One `medium`, two `low`, one `info`.

The `medium` is the name rather than the code. `auth` is absent from
`requirements`, so the resolver will never offer this to somebody who asked for
authentication, and the omission is declared more thoroughly than anything else
in this catalog. What remains is that "full-stack app" sounds like it includes
users, and a slug is a claim too — worth a moment's thought before this is
merged, and not a reason to hold it.

`tier: official` is not available while `provenance: generated` (ADR 0011).
