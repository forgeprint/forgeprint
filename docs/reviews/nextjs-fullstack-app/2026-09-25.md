# nextjs-fullstack-app — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.1.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Scope: the `payments: stripe` branch added in 1.1.0. The `none` branch runs
  the same actions as 1.0.0 under new step numbers; its review is
  [2026-09-23](2026-09-23.md) and stays current.
- Verdict: **MERGE**

## Summary

`options.payments` adds Stripe hosted Checkout to the full-stack blueprint, per
D11 of the expansion plan, rather than a `nextjs-saas-starter` slug that would
have been this blueprint plus a payment provider (ADR 0001).

The branch is small and does the three things that decide whether a payment
integration is safe: the webhook verifies every event against the raw body and
refuses replays, handling is idempotent by construction rather than by
convention, and the keys cannot reach the browser without a check failing.
All of it is tested with no Stripe account and no network.

The single thing a reader should know: `POST /api/checkout` is public and
unbounded, as every route in this blueprint is. Put a limit in front of it
before it faces the internet.

## Findings

### 1. The payment routes have no rate limit and no body bound — `medium`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:636` (step 18),
  `setup.md:538` (step 15, via step 19)
- **Standard:** OWASP API Security Top 10 2023, **API4:2023 Unrestricted
  Resource Consumption**
- **What:** anybody can call `POST /api/checkout` as often as they like, and
  each call is a call to Stripe. The webhook reads the whole body before it
  verifies the signature.
- **Why it matters:** the cost is Stripe API quota and server time rather than
  money or data, but it is the first thing an exposed checkout endpoint meets.
- **Mitigating, and why this is `medium`:** the blueprint has no
  authentication and says so in three places; `overview.md` names this gap
  under Cons with the standard. A limit belongs to the host or a gateway, which
  the blueprint does not assume.
- **Fix:** not at this scope. Recorded so that the first deployment adds it.

### 2. The checkout route has no cross-site request check — `low`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:636` (step 18)
- **Standard:** OWASP Top 10:2025 **A01 Broken Access Control**
- **What:** a route handler, unlike a server action, does not compare the
  `Origin` header, so another site can submit a form to `/api/checkout`.
- **Why it matters:** little today. The price is fixed on the server and the
  result is a redirect to a Stripe page the visitor then has to pay on, so a
  forged request buys nothing and learns nothing. It matters the day the route
  takes a quantity, a price or a user.
- **Fix:** when the route gains an input, check `Origin` against `APP_URL` or
  move the action to a server action. `AGENTS.md` already fixes the price to
  configuration.

### 3. The production key check runs after the port is bound — `low`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:596` (step 16),
  `setup.md:615` (step 17)
- **Standard:** OWASP Top 10:2025 **A10 Mishandling of Exceptional
  Conditions**; Twelve-Factor IX (disposability)
- **What:** Next 16 calls `register()` after `next start` is listening. A
  refused server is up for a moment, then exits 1.
- **Why it matters:** found by building it: a `register()` that throws is
  logged and Next keeps serving, which would have left a server up that could
  never take a payment. The recipe's step 35 asserts the process exits, so
  that regression cannot come back silently. The remaining window is
  milliseconds, and a request in it fails rather than succeeds.
- **Fix:** none that Next offers today; `overview.md` states it.

### 4. The placeholder check recognises markers, not validity — `info`

- **Where:** `blueprints/nextjs-fullstack-app/setup.md:392` (step 12)
- **Standard:** Twelve-Factor III (configuration)
- **What:** production refuses a missing key, a value not shaped like a Stripe
  secret, restricted or webhook key, and any value carrying a placeholder
  marker (`EXAMPLE`, `not-a-real`, `placeholder`, `changeme`). A wrong key
  that looks right passes, and fails at the first call.
- **Why it matters:** it is the check the brief asked for — an obviously fake
  key — and it says so. Checking validity means calling Stripe at startup,
  which the blueprint deliberately never does.

### 5. `payments` is a requirement one option value meets — `info`

- **Where:** `blueprints/nextjs-fullstack-app/manifest.yaml:15`
- **Standard:** the review skill's own rule that a claim wider than its
  verification is a finding
- **What:** `resolve` matches `payments` for this blueprint; the default,
  `none`, takes no payments.
- **Why it is not a defect:** the claim is verified — by the `stripe` branch's
  tests and recipe steps — and `overview.md` states under Cons which option
  meets it.

## What was checked and found sound

- **Signature verification against the raw body.** The route reads
  `request.text()`; `Stripe.webhooks.constructEvent` checks the signature with
  the secret from the environment. Tested: no signature, a signature from
  another secret, and a body that is not the one signed are all 400 and change
  nothing (OWASP API10:2023 Unsafe Consumption of APIs; API2:2023).
- **Replay.** A correctly signed event whose timestamp is ten minutes old is
  refused by Stripe's five-minute tolerance. Tested (API10:2023).
- **Idempotency by primary key in one transaction.** The event id goes into
  `stripe_events` with `ON CONFLICT DO NOTHING ... RETURNING`, and the order is
  written in the same transaction only if the id was new. A second delivery of
  the same event changes nothing and is answered 200, so Stripe stops
  retrying. A unique `checkout_session_id` means a second event about the same
  session does not create a second order either. Both are tested against the
  real Postgres the recipe already starts, not a mock (OWASP Top 10:2025
  **A08 Software or Data Integrity Failures**).
- **An order only from a paid event.** `checkout.session.completed` with
  `payment_status: 'paid'`, or `async_payment_succeeded`; an unpaid completion
  records no order. Tested. The success URL is documented as proving nothing.
- **The price is configuration, not input.** `STRIPE_PRICE_ID` from the
  environment; the request carries nothing. Success and cancel URLs come from
  `APP_URL`, not the `Host` header (API6:2023 Unrestricted Access to Sensitive
  Business Flows).
- **Keys stay on the server.** None of the four variables has the
  `NEXT_PUBLIC_` prefix. Step 34 builds with the keys set and fails if a value,
  or the name of one, appears under `.next/static`, and refuses to pass on an
  empty directory. The same check is in the generated project's CI. Checked by
  hand once in the other direction: a planted value in `.next/static` fails it
  (OWASP Top 10:2025 **A04 Cryptographic Failures**, key exposure).
- **No Stripe account, key or network call anywhere.** Signed payloads come
  from `Stripe.webhooks.generateTestHeaderString`, which exists in the pinned
  22.6.2; the checkout client is a `CheckoutClient` type the real SDK satisfies
  and a test fake implements. `stripe/stripe-mock` was not added: it would test
  the SDK against a mock of Stripe, not this code.
- **The refused server is proved to exit.** Step 35 starts the built server on
  loopback with the placeholders and asserts exit code 1 and the refusal
  message; `timeout` turns a server that keeps running into a failed step.
- **The rejection reason stays generic.** "invalid signature", not which part
  failed.
- **Pins verified on 2026-09-25:** `stripe` 22.6.2 is npm `latest` (22.7 is a
  preview tag).
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  Every key-shaped value contains `EXAMPLE` and cannot match a real key
  pattern; the one test that needs a key-shaped value builds it at run time.

## Not applicable

- **PCI DSS.** Not on the standards list, so not cited as a finding.
  `overview.md` states what hosted Checkout does (card data never reaches the
  server) and what it does not (the merchant stays in scope, typically through
  a self-assessment), and sends the reader to Stripe's guidance.
- **Subscriptions, tax, refunds, disputes, customer records.** Not claimed;
  listed under "What it is NOT for".
- **Authentication and object-level authorization (API1, API5).** The
  blueprint has no users, and says so. The webhook's signature is its
  authentication and is covered above.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: web`.

---

## Verdict

**MERGE.** One `medium`, two `low`, two `info`, no `critical` or `high`.

Finding 3 is the one worth remembering beyond this blueprint: in Next 16 an
error thrown from `register()` does not stop the server. Any blueprint that
uses the instrumentation hook as a startup gate has to exit, and has to prove
it exits.

`tier: official` is not available while `provenance: generated` (ADR 0011).
