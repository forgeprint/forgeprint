# django-web-app — architecture and security review

- Date: 2026-09-24
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21). OWASP ASVS 5.0 requirement numbers were read from the ASVS
  repository's `5.0/en` chapters on 2026-09-24.
- Reviewer: the authoring agent, following `skills/blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's third `web` blueprint and its first server-rendered one, and the
first to claim `auth` for a browser rather than for a bearer token — so the
checklist is ASVS 5.0 chapters V3 (web frontend), V6 (authentication), V7
(session management) and V13 (configuration), not the API Top 10.

The single most important thing to know before building on it: **nothing
limits how often a password can be tried**, on the site's login or the
admin's. That is declared in `overview.md` and left open, because the right
control depends on where the application is deployed.

The draft had three weaknesses of its own, found in this review and fixed
before the pull request opened; they are recorded below as resolved, because a
reader deserves to know what the first version got wrong. The most serious was
that a published placeholder key, long enough to pass the deploy check, was
also accepted by the production settings.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. Nothing limits password guessing on either login page — `medium`

- **Where:** `blueprints/django-web-app/setup.md:364` (step 12, `config/urls.py`:
  `accounts/login/` and `admin/`); declared in `overview.md`, "What it is NOT
  for"
- **Standard:** OWASP ASVS 5.0 **6.3.1** (L1) — controls against credential
  stuffing and password brute force, implemented according to the
  application's documentation — and **6.1.1** (L1), that documentation;
  OWASP Top 10:2025 **A07 Authentication Failures**
- **What:** `LoginView` and the admin login accept unlimited attempts. Django
  ships no throttle.
- **Why it matters:** a login page on the internet is attacked by credential
  lists within days, and the admin is at the path every scanner tries first.
  Password validators and a slow hasher raise the cost of each guess; they do
  not bound the number.
- **Mitigating, and why this is `medium` rather than `high`:** a reader would
  notice. `overview.md` names the gap, cites the requirement, and says what to
  do before the login page is public; `AGENTS.md` lists it under "What is not
  here". The rest of the authentication path is sound and tested (below).
- **Fix:** left open on purpose. A rate limit at the reverse proxy, a lockout
  package, or an identity provider are all correct answers, and which one
  depends on the deployment the blueprint does not choose. The blueprint that
  adds a WSGI server and a deployment target is the one that should close
  this.

### 2. A published placeholder key was accepted by production — `high`, resolved before the pull request

- **Where:** `blueprints/django-web-app/setup.md:315` (step 11,
  `production.py`), `:1020` (step 39) and the `ci.yml` of step 30/31
- **Standard:** OWASP ASVS 5.0 **13.3.1** (secrets come from a secrets
  management solution, not from the code); OWASP Top 10:2025 **A02 Security
  Misconfiguration**; CLAUDE.md §5b (example secrets are obviously fake)
- **What:** the draft ran `check --deploy` with
  `DJANGO_SECRET_KEY=not-a-real-secret-only-for-the-deploy-check-…`, written into
  both the recipe and the generated CI workflow. To pass the deploy check the
  value had to be 50 characters with five distinct ones — which is exactly
  what `production.py` checked, so the same string started production without
  complaint.
- **Why it matters:** the key signs sessions, password reset tokens and
  messages. A key that is printed in a public recipe and in every generated
  project's CI file is a key an attacker has. The label "not a real secret"
  protects nothing if the code accepts it, and copying a working value from CI
  into a deployment is an ordinary mistake.
- **Resolution:** `production.py` refuses any key containing
  `not-a-real-secret`, the phrase every placeholder in the project carries.
  The recipe and CI now generate a key for the run with
  `get_random_secret_key()` and never write it down, and
  `test_production_refuses_a_published_placeholder` proves the refusal.

### 3. HSTS defaulted to one hour — `medium`, resolved before the pull request

- **Where:** `blueprints/django-web-app/setup.md:347` (step 11)
- **Standard:** OWASP ASVS 5.0 **3.4.1** (L1): a `Strict-Transport-Security`
  header with a max-age of at least one year, applying to subdomains at L2
- **What:** the draft set `SECURE_HSTS_SECONDS` to 3600 by default, reasoning
  that a short max-age is safer during a first rollout.
- **Why it matters:** the rollout argument is real, but it made the default
  fall below the level-one requirement, and a default is what most
  deployments keep.
- **Resolution:** the default is one year; the comment and `overview.md` say to
  lower it with `DJANGO_SECURE_HSTS_SECONDS` during a first rollout, and why.

### 4. Session and CSRF cookies had no `__Host-` prefix — `low`, resolved before the pull request

- **Where:** `blueprints/django-web-app/setup.md:340` (step 11)
- **Standard:** OWASP ASVS 5.0 **3.3.1** (L1) and **3.3.3** (L2)
- **What:** production used Django's default names, `sessionid` and
  `csrftoken`, with `Secure` set.
- **Why it matters:** without the prefix, a sibling subdomain can set a cookie
  of the same name for the parent domain, which is the setup for session
  fixation and CSRF-token injection.
- **Resolution:** production names them `__Host-sessionid` and
  `__Host-csrftoken`. Django's defaults (`Path=/`, no `Domain`) already satisfy
  what the prefix requires; local development keeps the plain names because it
  runs over HTTP, where a browser would refuse a `__Host-` cookie.
  `test_production_starts_with_a_real_key_and_debug_off` asserts the name.

### 5. Authentication events are not logged — `low`

- **Where:** `blueprints/django-web-app/setup.md:412` (step 15,
  `accounts/apps.py`) — where the receivers would go
- **Standard:** OWASP ASVS 5.0 **16.3.1** (L2): all authentication operations
  are logged, successful and unsuccessful; OWASP Top 10:2025 **A09 Security
  Logging and Alerting Failures**
- **What:** logging goes to the console and request errors reach it, but a
  successful or failed login leaves no record.
- **Why it matters:** together with finding 1, a guessing attack is neither
  stopped nor visible.
- **Fix:** receivers for `user_logged_in`, `user_login_failed` and
  `user_logged_out` in `AccountsConfig.ready()`, logging the username and the
  client address — never the submitted credentials. A dozen lines; worth doing
  in the same change that closes finding 1, because the throttle and the log
  are read together.

### 6. Transitive dependencies are resolved at install time — `low`

- **Where:** `blueprints/django-web-app/setup.md:27` and `:41` (step 3)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF v1.1 PS.3; OWASP ASVS 5.0 **15.2.4**
- **What:** the three direct dependencies are pinned with `==`; `asgiref`,
  `sqlparse` and the `psycopg` binary wheel's own dependencies are whatever the
  index serves that day, with no hashes.
- **Why it matters:** the recipe is reproducible at the level the rest of the
  catalog's Python blueprints are, not byte for byte.
- **Fix:** a lock file with hashes (`pip-compile --generate-hashes` or `uv lock`)
  when the project adopts a tool for it. Recorded, not blocking; the same
  applies to `fastapi-service` and `python-cli`.

### 7. Django's password validators and ASVS disagree on one point — `info`

- **Where:** `blueprints/django-web-app/setup.md:205` (step 8)
- **Standard:** OWASP ASVS 5.0 **6.2.5** (L1): no rules limiting the type of
  characters permitted; against Django's own default validator set
- **What:** `NumericPasswordValidator` rejects a password made only of digits.
  ASVS forbids composition rules; this is a rule about composition, if a
  narrow one. The other three validators meet 6.2.1 (at least 8 characters)
  and 6.2.4 (checked against a list of common passwords — Django's holds
  20,000).
- **Why it matters:** it does not weaken anything; an all-digit password of any
  practical length is also on the common list or short. It is recorded because
  the standards list says a disagreement between references is named, not
  resolved silently.
- **Decision for the maintainer:** keep Django's default (the blueprint's
  current choice, because readers expect it) or drop the validator to follow
  ASVS to the letter.

### 8. Deployment is out of scope, and says so — `info`

- **Where:** `blueprints/django-web-app/overview.md`, "What it is NOT for"
- **Standard:** Twelve-Factor VII (port binding) and IX (disposability)
- **What:** no WSGI server, no static file serving with `DEBUG` off, no
  container image. The manifest does not claim `containerization`.
- **Why it matters:** the admin loses its styles in production until
  `collectstatic` and a server are set up. Declared, and not a defect in what
  the blueprint claims.

## What was checked and found sound

- **Default-deny authentication, enforced twice.** `LoginRequiredMiddleware`
  protects every view that does not opt out (OWASP Top 10:2025 A01; ASVS 5.0
  V8). `test_only_the_public_list_opts_out_of_the_login_requirement` reads the
  `login_required = False` marker `@login_not_required` puts on a view, across
  every route including those with parameters and the admin's namespace, and
  fails unless the opted-out set equals `PUBLIC`.
  `test_every_route_outside_the_public_list_needs_a_login` requests every
  argument-free route anonymously, which is what fails if the middleware is
  removed. This is the enforcement `go-http-service` had to add after its
  review; here it ships in 1.0.0.
- **The unauthenticated request is proved refused** — the dashboard redirects
  to login with `next`, and the admin redirects to its own login.
- **Open redirect after login is closed** (ASVS 5.0 3.7.2):
  `test_login_never_redirects_to_another_site` posts
  `next=https://example.com/` and asserts the redirect stays on the site.
- **CSRF** (ASVS 5.0 3.5.1, 3.3.2): every form carries the token, a post
  without one is proved refused (403), and logout is POST-only and proved to
  refuse GET (405).
- **Sessions** (ASVS 5.0 7.2.4, 7.4.1, 7.4.4): Django's `login()` issues a new
  session key; logout flushes the session, which the tests assert; the logout
  control is on every authenticated page. `SESSION_COOKIE_HTTPONLY` is
  Django's default (3.3.4).
- **Credential verification does not reveal which part was wrong** (ASVS 5.0
  6.3.8): the form's error is the same for an unknown user and a wrong
  password, and Django runs the hasher for unknown users too.
- **Password storage** is Django's default PBKDF2-SHA256; the MD5 hasher is
  confined to `config/settings/test.py` with a comment saying never elsewhere.
- **Configuration fails closed at startup** (Twelve-Factor III; OWASP Top
  10:2025 A10; ASVS 5.0 13.4.2): a missing `DATABASE_URL`, `DJANGO_SECRET_KEY`
  or `DJANGO_ALLOWED_HOSTS` raises while settings are imported, so no command
  and no server runs. Proved by tests that import the settings in a fresh
  interpreter with a controlled environment, and again by recipe step 40 from
  the command line. `wsgi.py` sets no default settings module, so a server
  that forgot to name one fails rather than running local settings.
- **`manage.py check --deploy --fail-level WARNING` passes** against production
  settings in the recipe and in the generated CI, with warnings as failures.
  The one silenced check, `security.W021` (HSTS preload), carries its reason;
  preloading is ASVS 5.0 3.7.4, a level-three requirement.
- **Content Security Policy with nonces and `frame-ancestors 'none'`** (ASVS 5.0
  3.4.3, 3.4.6) through Django 6's own middleware, asserted by a test; the
  admin's templates already emit the nonce. `X-Content-Type-Options: nosniff`
  is Django's default (3.4.4).
- **The TLS proxy header is opt-in** (OWASP Top 10:2025 A02; the principle
  ASVS 5.0 15.3.4 states for forwarded client addresses — trust a forwarded
  field only where a proxy guarantees it): trusting `X-Forwarded-Proto` by
  default would let a client claim HTTPS; the setting and its reason are in
  `production.py`.
- **Errors are visible and generic** (OWASP Top 10:2025 A09; ASVS 5.0 16.3.4,
  16.5.1): console logging replaces Django's default, which with `DEBUG` off
  and no `ADMINS` sends request errors nowhere; `DEBUG` is off in production,
  so the client gets the plain error page.
- **The custom user model is in the first migration**, and
  `test_every_model_change_has_a_migration` plus the CI's
  `makemigrations --check` catch a model change without a migration.
- **CI** pins `actions/checkout` and `actions/setup-python` to commit SHAs and
  has read-only permissions (OWASP Top 10:2025 A03; SLSA v1.2 build track).
- **The local database binds to loopback** on a port Docker chooses; its
  password is labelled `local-development-only`. `--no-sync` affects only the
  throwaway local cluster. Its health check goes over TCP, so it cannot report
  healthy while the image's temporary initialisation server is still running
  (OWASP Top 10:2025 A10: a dependency that is not ready is reported as not
  ready).
- **No secrets, no personal data, no employer information** (CLAUDE.md §5b).
  Every value that looks like a credential is labelled
  `local-development-only` or `not-a-real-secret`, and production refuses the
  latter.

## Not applicable

- **OWASP API Security Top 10.** `project_type: web`; there is no API surface.
- **Object-level authorization (ASVS 5.0 V8, API1).** No model has an owner
  yet. `AGENTS.md` says the first one filters by owner in the query.
- **Password change, reset and registration (ASVS 5.0 6.2.2, 6.2.3, 6.4.3,
  6.2.12).** Not wired; `overview.md` declares all three absent.
- **MFA and out-of-band authentication (ASVS 5.0 6.5, 6.6).** Not claimed.
- **CIS Docker Benchmark.** No image is built; the only container is the local
  development database, whose host and daemon are the reader's.
- **OWASP LLM 2025 and Agentic 2026.** `project_type: web`.
- **Multi-tenancy.** Not claimed; `overview.md` points at
  `dotnet-multitenant-saas-api`.

---

## Verdict

**MERGE.** One `high`, one `medium` and one `low` resolved before the pull
request opened; one `medium`, two `low` and two `info` open.

The open `medium` is the one a reader must act on before the login page is
public, and the blueprint says so in the place a reader looks. It is not closed
here because the right control depends on a deployment the blueprint
deliberately does not choose. Finding 5 belongs in the same change.

`tier: official` is not available while `provenance: generated` (ADR 0011).
