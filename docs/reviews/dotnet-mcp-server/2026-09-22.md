# dotnet-mcp-server — architecture and security review

- Date: 2026-09-22
- Blueprint version: 1.0.1
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due 2026-12-21)
- Reviewer: maintainer's Claude Code agent, `/arch-review`
- Verdict: **CHANGES**

## Summary

An MCP server in C# on the official `ModelContextProtocol` SDK, with one tool,
tests that assert the tool is discoverable as well as correct, and a protocol
probe that speaks to the built server rather than to the class.

One finding, and it is the same one `ts-mcp-server` has: the `http` transport
serves an unauthenticated MCP endpoint, and the specification names that as an
attack surface on the machine it runs on. This blueprint documents the absence
of authentication — but frames it as a concern for servers "reachable beyond
localhost", which is where the specification disagrees.

The manifest claims `tier: official`. One `high` finding is open, so **rule 23
blocks that tier** until it is closed.

## Findings

### 1. The HTTP transport has no access control, and the documentation puts the boundary in the wrong place — `high`

- **Where:** `blueprints/dotnet-mcp-server/setup.md` step 17 (`Program.cs`,
  `http` branch: `WithHttpTransport()` and `app.MapMcp()`), and
  `blueprints/dotnet-mcp-server/overview.md`, "What it is NOT for"
- **Standard:** MCP specification 2026-07-28, _Security Best Practices_ —
  "Local MCP Server Compromise": a server meant to run locally **SHOULD**
  _"Restrict access if using an HTTP transport, such as: Require an
  authorization token; Use unix domain sockets or other IPC mechanisms with
  restricted access"_, and the named attack is _"An attacker accesses an
  insecure local server that's left running on localhost via DNS rebinding."_
  Also OWASP Top 10 for Agentic Applications 2026.
- **What:** `MapMcp()` serves the MCP endpoint with no token, no `Origin`
  check and no other restriction. `overview.md` says under "What it is NOT
  for": _"Authentication in front of the HTTP transport. There is none. A
  server reachable beyond localhost needs auth added deliberately."_
- **Why it matters:** the omission is documented, which is why this is not
  worse — but the sentence tells the reader the risk starts when the server
  leaves the machine. It does not. Every process on the host can call these
  tools, and a page the user visits can reach the port by DNS rebinding, which
  defeats the same-origin protection that would otherwise stand in the way. The
  reader who adds a tool that reads a file or calls an internal API is relying
  on a boundary that is not there, and the blueprint told them it was.
- **Fix:** correct the sentence first — it is one line and it removes the
  misdirection. Then pick one: a bearer token read from configuration with the
  server refusing to start without it, or `Origin` validation, which is the
  direct answer to rebinding. `AGENTS.md` should carry the rule that adding a
  tool with any side effect means adding authentication first.

### 2. `stdio` is the safer default and the blueprint does not say so — `low`

- **Where:** `blueprints/dotnet-mcp-server/manifest.yaml` (`options.transport`,
  `stdio` first) and `overview.md`
- **Standard:** MCP specification 2026-07-28 — _"Use the `stdio` transport to
  limit access to just the MCP client"_ is listed first among the mitigations
- **What:** both transports are presented as equivalent choices; `stdio` is
  first in the option list, which is what `test-setup` picks by default, but
  nothing says why that order.
- **Why it matters:** the specification's first recommendation for a local
  server is stdio, precisely because the process boundary _is_ the access
  control. A reader choosing between the two on convenience should know one of
  them is the security answer.
- **Fix:** one sentence in "Trade-offs made on your behalf": stdio is the
  default because the client owns the process, and http is for when something
  other than the client has to reach the server — which is also when
  authentication stops being optional.

## What was checked and found sound

- **The tool contract is explicit.** `[McpServerToolType]` and
  `[McpServerTool]` with `[Description]` on the method and on the parameter,
  and a test asserting the attributes are present — so a tool that silently
  stops being discoverable fails the build rather than disappearing.
- **Tool surface is minimal.** One `echo`, no filesystem, no network, no
  process spawning (OWASP LLM 2025, excessive functionality).
- **The probe drives the real server.** `scripts/probe.mjs` speaks MCP to the
  built DLL over stdio, which is what catches a wrong entry point or anything
  written to stdout.
- **The HTTP check does not assume a port.** The server is started on
  `--urls http://127.0.0.1:0`, and the recipe reads the chosen address out of
  the server's own log rather than guessing — so the check can never be
  answered by an unrelated process.
- **No token handling**, so the specification's prohibition on token
  passthrough cannot be violated.
- **No state handles**, so state handle hijacking does not apply.
- **Supply chain.** SDK pinned through `global.json`, package versions
  explicit, actions pinned to commit SHAs, workflow permissions read-only
  (SSDF, SLSA).
- **Absences are documented.** Resources, prompts, client-side use, registry
  packaging — each is named in "What it is NOT for" rather than left to be
  discovered.

## Not applicable

- **OAuth, consent, confused deputy, scope minimisation, SSRF (MCP spec).** No
  authorization flow, no third-party proxying, no outbound fetching.
- **CIS Docker.** No container in this blueprint.
- **OWASP API Security Top 10.** `project_type: agent`.
- **NIST SP 800-218A.** Applies to developing generative AI models.
