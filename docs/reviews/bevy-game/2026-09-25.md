# bevy-game — architecture and security review

- Date: 2026-09-25
- Blueprint version: 1.0.0
- Standards: `docs/review-standards.md` as checked 2026-09-22 (next re-check due
  2026-12-21)
- Reviewer: maintainer's Claude Code agent, following
  `skills/blueprint-arch-review`
- Verdict: **MERGE**

## Summary

A generated blueprint, so the review is not optional (ADR 0011, CLAUDE.md §5c).
The catalog's Rust `game` blueprint: Bevy 0.19.1 as two crates, the rules as
ECS plugins in a crate that compiles no renderer, window or audio, and a thin
binary that draws them. It claims `testing` and `ci`, runs no server, stores
nothing, takes no input from a network and handles no secret, so most of the
application-security standards have nothing to attach to; the review is about
the build, the boundary, and whether the tests prove what the blueprint says.

The review found one `medium` in the first draft: the boundary that keeps the
rules headless was checked by the recipe once and never again by the
generated project's CI. It was fixed before the pull request opened. What
remains is disclosed in `overview.md`: rendering, input feel, audio,
performance, Windows and macOS, and whether the binary starts are not proven
by any automated check.

The manifest claims `tier: community` and `provenance: generated`.

## Findings

### 1. The headless boundary was checked at setup and never again — `medium`, resolved in 1.0.0

- **Where:** first draft of `.github/workflows/ci.yml`; now
  `blueprints/bevy-game/setup.md:886` (step 12, the `The rules crate stays
headless` step) and `:963` (step 18)
- **Standard:** Hexagonal architecture (ports and adapters) — the dependency
  direction between the rules and the adapters that present them; NIST SSDF
  v1.1 **PW.7** (review and analyse code to verify it meets requirements),
  applied as a check that runs on every change
- **What:** the recipe's step 18 lists `game`'s dependency tree and fails on
  `bevy_render`, `bevy_winit`, `bevy_audio`, `bevy_gilrs`, `wgpu` or `winit`.
  The generated CI ran fmt, clippy, the tests and the binary build, none of
  which fails when a rendering feature is added to `game/Cargo.toml` — the
  runner can build the renderer.
- **Why it matters:** the boundary is the blueprint's central design claim and
  `AGENTS.md` tells an agent it is enforced. Checked only at setup, it would
  hold for the first commit and erode silently from the second: a rule reads
  a `Window`, the tests still pass because nothing in them has one, and the
  logic is no longer testable headless.
- **Fix (done):** the `check` job runs the same `cargo tree` listing and
  fails with a message when any of the six crates appears. `/game-deps.txt`
  is ignored by git. `AGENTS.md` names both places the check runs.

### 2. The generated CI runs no advisory scan — `low`

- **Where:** `blueprints/bevy-game/setup.md:852` (step 12, `.github/workflows/ci.yml`)
- **Standard:** OWASP Top 10:2025 **A03 Software Supply Chain Failures**; NIST
  SSDF v1.1 **RV.1** (identify and confirm vulnerabilities on an ongoing
  basis)
- **What:** Bevy is pinned exactly and `Cargo.lock` is committed and used with
  `--locked`, but nothing in CI checks the 426 locked packages against the
  RustSec database. Checked by hand for this review: every package in the lock
  file the recipe produced on 2026-09-25 was queried against OSV, which
  mirrors RustSec, and none has an advisory, including unmaintained notices.
- **Why it matters:** an advisory published next month against a transitive
  crate would not be noticed. The exposure is small — a single-player game
  that opens no socket and parses no untrusted file — which is why this is
  `low`.
- **Fix:** add `cargo audit` or `cargo deny check advisories` to CI when the
  game grows a network or file-loading surface. Left open: the rust-axum and
  rust-cli blueprints make the same call, and a scan that downloads an
  advisory database belongs in the project's CI, not in the recipe.

### 3. Three platforms claimed, one built — `info`

- **Where:** `blueprints/bevy-game/manifest.yaml:11`; disclosed in
  `blueprints/bevy-game/overview.md`, "What CI can prove, and what it cannot"
- **Standard:** NIST SSDF v1.1 **PW.8** (test executable code to verify it
  meets requirements), read as: a claim is as wide as what verifies it
- **What:** `platforms: [linux, windows, macos]`. The recipe and the generated
  CI build on Linux only. Nothing in the code is Linux-specific, and Bevy
  supports all three.
- **Why it is only `info`:** the gap is stated where a reader looks, in the
  same section as rendering and input. Recorded so that a future
  `tier: verified` claim is made only after somebody builds on the other two.

### 4. The view is compiled, linted and linked, never run — `info`

- **Where:** `blueprints/bevy-game/setup.md:760` (step 10, `app/src/view.rs`)
  and `:966` (step 19)
- **Standard:** NIST SSDF v1.1 **PW.8**
- **What:** `app/src/view.rs` adds sprites and writes the window title. No
  test executes it: it needs a window and a GPU, and neither exists on a CI
  runner.
- **Why it is only `info`:** the design makes the untested part as small as it
  can be — it reads the rules' components and resources and writes nothing
  back — and `overview.md` says plainly that rendering, input feel and whether
  the binary starts are not proven.

## What was checked and found sound

- **Boundaries and dependency direction** (Hexagonal architecture; Clean
  Architecture's dependency rule). `app` depends on `game`; `game` depends on
  nothing of `app`'s. The rules crate asks Bevy for `std`, `bevy_state` and
  `keyboard` only (`setup.md:61`), and step 18 plus the CI check prove its
  dependency tree holds no renderer, window, audio or gamepad crate.
- **Test strategy** (SSDF PW.8). Thirteen headless tests drive the real
  plugins through `app.update()` with a fixed frame length and real
  `KeyboardInput` messages, and assert on the world. Before the recipe was
  written, ten deliberate breakages of the rules were each made by hand (no
  set ordering, no normalised diagonal, no arena clamp, losing checked before
  winning, no despawn on leaving a round, no order on restart, restart allowed
  mid-round, no score reset, a clock that ticks after the round, a fixed step
  per frame); every one failed at least one test. Two breakages survived the
  first round, so one test was strengthened and one added until they did not.
- **Scheduling as a correctness property.** `systems_that_share_data_run_in_a_declared_order`
  (`setup.md:671`) builds `Update` and `OnEnter(Playing)` with Bevy's
  ambiguity detection set to error, so an unordered data race between systems
  is a test failure rather than a platform-dependent bug.
- **Error handling** (OWASP Top 10:2025 A10). The rules' systems iterate
  queries and cannot fail on an empty world; the one `Single` parameter, the
  primary window at `setup.md:822`, makes Bevy skip the system when the window
  is gone rather than panic. Nothing parses input from outside the process.
- **Supply chain** (A03; SLSA v1.2 build track, as far as a project that
  publishes nothing reaches it). `bevy = "=0.19.1"`; `Cargo.lock` is written
  by the recipe, committed, and every later command uses `--locked`. The
  resolver chose versions compatible with the declared `rust-version`, and the
  same lock file builds and tests under Rust 1.95.0 as well as 1.98.1. `unsafe_code = "forbid"`
  for the workspace. No `rust-toolchain.toml`, so the recipe downloads nothing
  outside crates.io.
- **CI** (SSDF PO.3, PS.1; SLSA). Every action pinned by commit SHA, each SHA
  checked against its tag on 2026-09-25 (`actions/checkout` v7.0.1,
  `Swatinem/rust-cache` v2.9.2, and `dtolnay/rust-toolchain`'s `v1` commit of
  2026-09-12). `permissions: contents: read`; `persist-credentials: false` on
  both checkouts; toolchains pinned (`1.98.1`, `1.95.0`); an `msrv` job that
  builds on exactly the declared `rust-version`. No `pull_request_target`, no
  secrets, no write permission, so the build cache cannot be written from a
  fork's pull request with anything but that pull request's own scope.
- **The recipe** (CLAUDE.md §3.2, rule 20). `lint-setup` passes. Every step is
  one file or one command with a verification; nothing needs `sudo`, a system
  package or a host other than crates.io. The window binary builds and links
  on `rust:1.98.1-slim-trixie`, which has no X11, ALSA, udev or Wayland
  development package, because the three features that need one are off.
- **Secrets and configuration** (Twelve-Factor III; CLAUDE.md §5b). There are
  none: no configuration is read, no credential is needed to build, test or
  play, and no example value looks like one.
- **What it does not do** is said in `overview.md` under "What it is NOT for":
  the browser (with `phaser-web-game` named), an editor workflow (with
  `godot-game` named), 3D, audio, gamepads, native Wayland, multiplayer and
  the mobile stores.

## Not applicable

- **OWASP ASVS 5.0 and the OWASP API Security Top 10 2023.** No
  authentication, session, access control, API or network surface. The game
  opens no socket and reads no file at run time.
- **OWASP Top 10 for LLM Applications, Agentic Applications, and the MCP
  references.** No model, agent or MCP server.
- **CIS Docker Benchmark.** No image or Dockerfile; the dry runs used
  containers, the blueprint does not.
- **WCAG 2.2.** `requirements` does not claim `accessibility`, and a canvas
  game with keyboard-only input is not accessible in the WCAG sense. Not a
  finding, because nothing claims it.
- **SLSA provenance attestations.** The blueprint publishes no artefact;
  `requirements` does not claim `cd`.
