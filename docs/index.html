Every new project starts cold

You hunt down the requirements, write the rule file by hand, wire up the MCP servers, pick the plugins, and get the setup steps wrong twice before they work. Hours of it — repeated by everyone, on every project, forever.

That knowledge is not hard to write down. It is just never written down in a form another agent can use.

Without Forgeprint

  • Search for a starting point, find five, compare them by hand
  • Write AGENTS.md from memory, forget half of it
  • Wire MCP servers one at a time, from their own READMEs
  • Tell the agent how to review, test and ship — again, in every project
  • Discover the gaps only when something fails

With Forgeprint

  • Describe yourself in one sentence; the resolver asks what it still needs
  • Get one blueprint, with the reason it was chosen
  • The rule file, the skills and the MCP configuration arrive together
  • Experts bring a way of working, with checklists and sources behind it
  • The recipe is executed in CI before it ever reaches you

Three questions, four units

A blueprint answers what you are building. Two more questions come up in the same breath — how the agent should work, and with which tools — and each has its own unit. A crew packages the answers under a name.

What are you building?

Blueprint

A project package: AGENTS.md, skills, MCP configuration, and setup.md — a recipe whose every step ends in the check that proves it worked.

How should the agent work?

Expert

A way of working, not a persona. It names what it produces, the checklists it applies, and the sourced references it rests on.

With which tools?

Integration

A pinned, permission-documented install recipe for somebody else's MCP server. Forgeprint hosts no third-party code.

All of it, under one name?

Crew

Up to six experts and their integrations, named by slug. It copies nothing, and says what it is for — and what it is not for.

How it works

You talk to your agent normally. Forgeprint answers in structured data, and your agent does the work. It installs nothing and runs nothing on your machine — every tool returns text.

  1. You say who you are
  2. Your agent calls resolve
  3. One blueprint comes back
  4. It asks rather than guesses
  5. You answer
  6. It fetches the package
  7. Context and recipe arrive together
  8. Your agent runs the recipe

What it looks like

Four conversations, one for each unit. The tool calls are shown the way your agent makes them.

YouI know C#. I want to build a multi-tenant SaaS API.

resolve { languages: ["C#"], goal: "multi-tenant SaaS API" }

Your agentOne blueprint fits: dotnet-multitenant-saas-api — chosen because you already write C#, and it covers multi-tenancy. Two things are still open: Postgres or SQL Server, and one shared database with a tenant column, or one database per tenant?

YouPostgres, one shared database.

Your agentI have the recipe: numbered steps, pinned versions, and a check after each one. Shall I start in this folder?

Ten tools, three jobs

Everything Forgeprint does is one of these calls. Each returns text; none of them runs anything.

What makes it different

A resolver, not a list

One answer, weighted so a language you already know beats everything else.

A recipe, not a description

setup.md is a script: pinned versions, each step ending in the check that proves it worked.

A gate, not a junk drawer

Schema validation, a real setup run and a duplicate report on every pull request.

Standards, not another format

AGENTS.md, SKILL.md and marketplace.json as they already exist.

Composition, not copies

A crew names experts and integrations by slug. At most six members, and a line saying what it is not for.

Any agent, on the record

Nine agents registered from their vendors' own docs, each with a date. Tested means tested.

How to contribute

One folder is one unit — a blueprint, an expert, a crew or an integration — and that folder is the contribution. Everything the pipeline does is a command you can run on your own machine; hosted CI is a convenience here, never a dependency.

Get it running

git clone https://github.com/forgeprint/forgeprint.git
cd forgeprint
pnpm install
pnpm run build
pnpm forgeprint validate

How the repository is laid out

blueprints/<slug>/
What you build: manifest, AGENTS.md, overview, setup.md
experts/<slug>/
How the agent works: SKILL.md, checklists, references
crews/<slug>/
Named packages of experts and integrations
integrations/<slug>/
Pinned install recipes for third-party MCP servers
schema/
Manifest schemas, the taxonomy, and agents.yaml
packages/
The CLI, the MCP server and the catalog pages
docs/decisions/
Every architectural decision, with the reasoning kept

The contribution flow

  1. Check whether it already exists

    One unit per combination: one blueprint per stack and requirements, one expert per role, domain and seniority.

  2. Write it from something that works

    The blueprint-author skill turns a working project into a blueprint.

  3. Pass the gate locally

    validate, lint-setup, similarity, render-check and a real setup run.

  4. Open the pull request

    Say what is closest and why yours is not a change to it.

Questions people actually ask

Does Forgeprint run anything on my machine?

No. Every tool returns text. Your agent is what reads the recipe and runs the commands, and you can read every step before it does.

Is it only for Claude Code?

No. Nine agents are registered, each traced to the vendor's own documentation with the date it was read. Claude Code is the first that has run a whole recipe end to end; the others are marked as documented, not tested, until somebody runs one.

What is an expert — a persona?

No. An expert is a way of working: what it produces, the checklists it applies, and references with versions and the date they were last checked.
