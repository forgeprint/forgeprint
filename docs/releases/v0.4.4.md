The first release where nothing on the path holds a credential. npm goes up
over OIDC, the MCP Registry follows in the same job over OIDC, and no token
exists on any machine or in any secret store.

Nothing the catalog serves changed. This is the release path.

## The MCP Registry publishes from the tag now

It was the last by-hand step, and it resisted for a while.
`mcp-publisher login github-oidc` takes no arguments: inside Actions it
authenticates as this repository, and the registry grants exactly the namespace
[`server.json`](https://github.com/forgeprint/forgeprint/blob/main/server.json) needs.

```
granted to:  repo:forgeprint@.../forgeprint@...:ref:refs/heads/main via github-oidc
permissions: [{"action":"publish","resource":"io.github.forgeprint/*"}]
lifetime:    300 seconds
```

Before that was measured, six attempts at the documented by-hand path produced
three logins that reported **success** and granted `io.github.<person>/*` —
never the organization. The reasons are worth writing down, because every one
of them looked like something else:

| What happened                                      | What it actually was                                                   |
| -------------------------------------------------- | ---------------------------------------------------------------------- |
| the step said to set `MCP_GITHUB_TOKEN`            | mcp-publisher 1.8.1 reads no such variable; the token goes in `-token` |
| `-token` with an empty value printed a device code | an empty token is not an error — it falls back to the device flow      |
| the device flow said "Successfully logged in"      | it authenticates the person without the organization                   |
| "log in now, publish later"                        | the registry token expires **300 seconds** after it is issued          |

The registry step has to follow npm, because the registry proves ownership by
reading `mcpName` out of the **published** package. It prints what the login
granted before it publishes: that measurement used a branch ref and a release
runs from a tag, so the grant is shown rather than assumed.

## A slow registry is not a failed publish

0.4.3 put both packages on npm correctly and turned its own release workflow
red. npm accepted `forgeprint-mcp@0.4.3` and said so; the registry was still
serving the previous version two and a half minutes later; and the only outcome
for "the client said yes and the registry has not caught up" was `failed`.

A published version is immutable, so that gap is propagation, and reporting it
as failure is worse than saying nothing — it invites a re-run of a release that
already happened. It is its own outcome now, reported as accepted, with the
command that confirms it. The wait also goes from two and a half minutes to
five, which is not the fix: no window is long enough to be a guarantee.

## The fallback is still there

`forgeprint release <version>` publishes from a laptop and finishes the
registry step on its own, skipping whatever the registry already serves.
[ADR 0002](https://github.com/forgeprint/forgeprint/blob/main/docs/decisions/0002-actions-optional.md) is why: Actions being
unavailable delays a release, it does not block one.

## Upgrading

Nothing to change. `npx -y forgeprint-mcp` picks up the server and
`npm i -g forgeprint` the tooling.
