Four versions in one release. 0.2.6, 0.2.7 and 0.2.8 were written and never
cut, so what follows covers everything since 0.2.5.

The catalog went from five blueprints to seven, and for the first time two of
them were written by a tool rather than by a person. That is the change worth
reading carefully, and it is declared rather than quiet.

## The catalog

Two new blueprints, both filling gaps that were measured rather than guessed:

- **`python-mcp-server`** — the catalog had an MCP server blueprint in
  TypeScript and one in C#, and the Python SDK is downloaded at a comparable
  scale. Deliberately parallel to the other two: the same two transports, the
  same shape of test, the same proof that a foreign `Origin` is refused with 403. It uses the SDK's own `TransportSecuritySettings` rather than
  hand-written middleware, so the safe configuration is the one you get for
  free.
- **`astro-content-site`** — the first `web` blueprint, and the first to carry
  `seo` or `accessibility` at all. Its tests read the built HTML and assert
  what a crawler and a screen reader actually get, because a template can be
  correct while the output is wrong.

Both are `provenance: generated` and `tier: community`. `python` joined the
`stack` vocabulary to make the first one expressible.

## Generated blueprints, and saying so

A blueprint drafted by a tool can pass everything the machine checks and still
be wrong in the way that matters: plausible steps, in a plausible order, that
nobody has ever depended on. CI cannot tell the difference and neither can a
reader, unless we say so ([ADR 0011](../decisions/0011-generated-blueprints.md)).

So the manifest records `provenance: human | generated`, defaulting to `human`
— every blueprint written before this field existed was written by a person,
and any other default would be a lie about all of them. **The schema refuses a
generated blueprint at `tier: official`**, not as a review guideline but as a
validation error. `verified` stays reachable: running a setup is something a
person can do without having written it, and `official` is about authorship.

The MCP server and the site both carry _"Generated, CI-tested, not manually
verified"_ wherever such a blueprint appears.

The field name had to be freed up. The record of which project a blueprint was
derived from is now `derived_from`, with its URL under `url`.

## Deciding what to build next, from evidence

`skills/catalog-research` now says where to look and insists on numbers that
can be fetched rather than articles quoting them: the npm, PyPI and NuGet
download APIs and the GitHub API, each row carrying the date it was read. The
first report is [2026-09-23](../research/2026-09-23-demand.md) — fifteen stack
combinations and fifteen MCP servers, with two cautions stated in the document
because both have produced confident nonsense elsewhere: a directory's server
count is not an install count, and downloads are not developers.

What it found: of the fifteen strongest combinations, four were covered and
eleven were not. Two of those eleven are now blueprints. It runs monthly.

## `forgeprint release`

Cutting 0.2.5 by hand took six commands and produced three wrong diagnoses,
none of them about the release and all of them about reading npm's output as
though it meant what it said.

- `404 Not Found` on publish is a rejected token, not a missing package.
- `409 Cannot publish over previously staged version` means "this version
  already exists". It arrives _after_ a publish that worked, and nothing is
  staged ([npm/cli#9889](https://github.com/npm/cli/issues/9889)).
- `npm view --prefer-online` served the previous version for minutes after the
  package page showed the new one — which nearly turned a finished release into
  an attempt to skip a version number that was never stuck.

So the command does not believe the publish. It publishes one package at a
time, asks the registry what happened, retries because the registry lags, and
treats an error as an error only if the registry agrees. Around that: a clean
tree, a pushed HEAD, every package at the version with a changelog entry for
it, and CI green on the commit about to be tagged — it waits for a run still in
progress rather than refusing. The first run writes a draft of the notes and
stops, so a human rewrites them before anything immutable exists.

Without Actions it reports the CI state as unknown and lets the maintainer
decide ([ADR 0002](../decisions/0002-actions-optional.md)).

## Smaller things

- **`suggested_alongside`.** `provides.mcp` and `provides.skills` had been in
  the schema and the index since the first version and were read by nothing. A
  blueprint could name the MCP servers it expects and neither the agent nor a
  reader of its page would hear about them.
- **Recipes run against Git Bash on Windows**, not the WSL launcher, which
  starts and then reports `execvpe(/bin/bash) failed` when no distribution is
  installed — so every step of every recipe failed for a reason that was not
  the recipe. `FORGEPRINT_BASH` overrides the search.
- **WCAG 2.2 is on [the standards list](../review-standards.md)**, with WCAG
  3.0 recorded beside it as a Working Draft that is _not_ used in a review. The
  review skill gained the rule the first accessibility review had to invent: a
  claim wider than its verification is a finding, because `resolve` matches on
  `requirements` and sends people to a blueprint on the strength of the word.
- A recipe may name the domains RFC 2606 and RFC 6761 reserve for
  documentation. A step that proves a server refuses a foreign `Origin` has to
  send one.

## Upgrading

Nothing to do. No tool option changed meaning and no blueprint slug moved. If
you read `docs/index.json` directly, note that `provenance` is now a string and
the object that used to carry that name is `derived_from`.
