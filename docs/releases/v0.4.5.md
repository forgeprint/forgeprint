One fix in the tooling, and it was found by following the instruction the tool
printed.

## `get` writes the recipe it tells you to run

`forgeprint get` is the path for agents with no MCP client
([ADR 0013](https://github.com/forgeprint/forgeprint/blob/main/docs/decisions/0013-agent-agnostic.md)). It wrote the agent's
context file, then said:

```
next  read setup.md and run it step by step: TypeScript HTTP Service
```

It did not write `setup.md`. The one file the entry exists for had to come from
somewhere the command does not name, which for an agent without a client is
nowhere.

It writes the recipe now, with `--options` resolved rather than handed over as
comment guards — an unresolved block is two recipes and the reader has to know
which half applies. A field nobody chose stays guarded **and is named**, so the
gap is visible:

```
$ forgeprint get ts-http-service --agent claude-code
wrote  CLAUDE.md
wrote  setup.md

next  run setup.md step by step: TypeScript HTTP Service
      framework not chosen — those blocks are still guarded; pass --options to resolve them
```

## Also since 0.4.4, outside the packages

- **A failed release can be finished without a new version number.** A
  tag-triggered run uses the workflow file _from the tag_, so a bug in
  `release.yml` cannot be fixed by re-running the tag. `workflow_dispatch` now
  takes a version: it publishes that version while checking out **its tag**, so
  the corrected workflow comes from the default branch and the content comes
  from the tag. Three releases had been re-numbered before this existed, and
  0.4.4 was the first one recovered instead.
- **[Scenario D's materials](https://github.com/forgeprint/forgeprint/blob/main/docs/scenario-d)** — the three prompts, the
  acceptance checks a script can hold honestly, and the recording sheet.
  Committed before any run, because a check written after watching a run is a
  check that run passes.

## Upgrading

`npm i -g forgeprint` the tooling. The server did not change.
