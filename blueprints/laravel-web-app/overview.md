# Laravel Web App

A Laravel 13 web application on SQLite, with login, registration and logout
through Laravel Fortify, a dashboard only a signed-in user can reach, Blade
views styled with Tailwind 4 and built by Vite 8, PHPUnit feature tests, and a
CI workflow.

**Generated, CI-tested, not manually verified.** The recipe executes on every
push like every other blueprint here. Nobody has run a real application on it
first, which is what `tier: official` means in this catalog and why this is
`community`.

## What you get

- The official `laravel/laravel` 13.10.1 skeleton with the framework pinned to
  13.33.0 and Fortify to 1.40.0, and the frontend packages pinned exactly
  rather than by caret range.
- SQLite as a file in the project: no database server, no container, nothing
  to start before `php artisan migrate`.
- Login, registration and logout, with Blade forms written for this project and
  the endpoints provided by Fortify. Registration asks for a password of at
  least twelve characters and, in production only, refuses one that appears in
  a public breach corpus.
- A login rate limit: five attempts a minute per account and address, twenty a
  minute per address, with a test proving the sixth attempt is refused even
  with the right password.
- A `/dashboard` route inside an `auth` middleware group, and a test proving a
  guest is redirected to the login page.
- The encryption key generated by the recipe into a git-ignored `.env`, never
  written into anything committed.
- A recipe that proves the configuration survives `config:cache` and the routes
  survive `route:cache` — the two things a production deploy does that a
  laptop does not.
- `.github/workflows/ci.yml`: Composer install and audit, the Vite build, Pint
  in check mode and the test suite, with every action pinned by commit.

## Options

None. The research behind this blueprint found four official Laravel starter
kits (React, Vue, Svelte, Livewire) — one more than the three values an option
may have, and each changes the language of the frontend. This blueprint is the
Blade-and-Fortify base underneath all of them.

## What it fits

- A server-rendered web application with user accounts, written by somebody who
  knows PHP or wants to.
- A team that wants the framework's own conventions — Eloquent, Blade,
  migrations, feature tests — rather than a set of choices on top of them.
- A small product, an internal tool or a prototype that should start with
  authentication instead of adding it in week three.
- Learning where Laravel's seams are: what Fortify owns and what the
  application owns, why `env()` stays in `config/`, and why a cached
  configuration changes what the tests talk to.

## What it is NOT for

- **A single-page application.** There is no React, Vue or Svelte here and no
  Inertia. For a React front end use Laravel's React starter kit directly, or
  `nextjs-fullstack-app` if the back end does not need to be PHP.
- **An API for somebody else's front end.** There are no API routes, no tokens
  and no Sanctum. For an API, `dotnet-web-api`, `fastapi-service`,
  `go-http-service` or `ts-http-service` start in the right shape.
- **Authorization.** Being signed in is the only check. There are no roles, no
  policies and no admin area; `AGENTS.md` says how to add a policy and the test
  that proves it, and until somebody does, every signed-in user is equal.
- **The rest of the account lifecycle.** No password change, no password
  reset, no email verification, no two-factor authentication, no passkeys.
  Fortify supports all five; they are off because each needs views, mail or a migration, and a
  feature turned on without them is a route that answers with an error page.
- **A static site.** If nothing changes per request and nobody logs in,
  `astro-content-site` is smaller in every dimension.
- **Deployment.** No Dockerfile, no web server configuration, no queue worker,
  no host assumed. `.env.example` describes a laptop: a server needs
  `APP_ENV=production`, `APP_DEBUG=false` and `SESSION_SECURE_COOKIE=true` set
  in its own environment, and `AGENTS.md` says why.

## Trade-offs made on your behalf

- **Fortify with hand-written Blade views, not a starter kit.** The official
  starter kits are the documented way to begin, but they are installed from
  their `main` branch: their last tagged releases on Packagist date from
  February 2025, before Laravel 13, so a recipe cannot pin one. Fortify is
  what those kits use for authentication, it is tagged, and it is pinned here.
  The cost is plain forms instead of a component library.
- **Registration only, among Fortify's features.** Fortify's defaults turn on
  everything it has. This blueprint turns on what it builds views for. Password
  reset is the one most applications need next; it needs a mailer and two
  views, and `AGENTS.md` says where they go.
- **SQLite, not MySQL or PostgreSQL.** It is Laravel's own default since
  version 11 and means the recipe needs no service. It is a real database
  and fine for a single server; it is the wrong choice for several application
  servers sharing one database. Switching is a `.env` change and a server.
- **PHPUnit, not Pest.** PHPUnit is what the skeleton ships with; Pest is what
  the starter kits ship with. Both run through `php artisan test`; adding Pest
  later is a `composer require` and does not invalidate these tests.
- **A twelve-character password minimum**, above Laravel's default of eight,
  and a breached-password check in production only. The check is Laravel's
  own `uncompromised()` rule: it sends the first five characters of the
  password's SHA-1 hash to the Have I Been Pwned range API, never the password.
  Production-only because tests and local work should not reach a third-party
  service; the cost is that the tests never exercise it, and that the
  framework lets a password through when the service cannot be reached.
- **The skeleton's web font is removed.** Its Vite configuration downloads a
  font from a font service during the build; a build that needs a third-party
  host fails offline and on a locked-down CI runner.
- **The framework is pinned exactly.** `composer update` will not move it;
  upgrading is a deliberate `composer require laravel/framework:<version>`.

## Pros

- **Authentication that is tested at the HTTP level**: the guest redirect,
  a successful login, a wrong password, the rate limit, registration, a short
  password refused, and logout — each a test.
- **The rate limit is proved rather than configured.** The test sends five
  wrong passwords and then the right one, and asserts a 429.
- **Production configuration is exercised by the recipe.** `config:cache` and
  `route:cache` run, and a grep proves nothing outside `config/` calls
  `env()`.
- **No service to run.** PHP, Composer and Node are the whole toolchain.
- **CI audits dependencies**: `composer audit` fails the build on a published
  advisory, and the recipe runs it too.

## Cons

- **Nobody has run this in anger.** See the notice above.
- **No authorization** beyond "signed in". It is the first thing a real
  application needs after this, and the easiest to forget.
- **No password reset and no password change.** A user who forgets their
  password, or wants a new one, has no way to do it without somebody editing
  the database.
- **Registration has no rate limit** and no email verification, so anybody can
  create accounts as fast as they can submit the form.
- **Plain forms.** No component library, no dark mode, no client-side
  validation.
- **A yearly major version.** Laravel releases one major a year and supports
  each for two years of security fixes; this blueprint will need a new version
  for Laravel 14.

## Cost of adoption

About ten minutes on a machine with PHP 8.3 or newer, Composer 2 and Node.js
22.12 or newer. Most of it is Composer and npm downloading packages. The recipe
was run in CI on Linux with PHP 8.3 — the lowest version Laravel 13 supports —
and Node.js 22.

## Compared with the alternatives here

- **`nextjs-fullstack-app`** — the other server-rendered `web` blueprint with a
  database. TypeScript instead of PHP, Postgres instead of SQLite, and no
  authentication. If the team writes TypeScript, start there and add
  authentication; if it writes PHP, start here.
- **`astro-content-site`** — static pages, no server. The right choice when
  there are no accounts.
- **`dotnet-web-api`** — authentication and CI as well, but an API with bearer
  tokens rather than pages with a session. Pick it when the front end is a
  separate application.
