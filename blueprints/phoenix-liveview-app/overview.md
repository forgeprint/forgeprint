# Phoenix LiveView App

A Phoenix 1.8 web application on Postgres where the interesting page is a
LiveView: the server holds the state, pushes changes down a websocket, and no
JSON API and no client framework sit in between.

## What you get

- **Phoenix 1.8.15 and LiveView 1.2.12**, generated by `mix phx.new` at a
  pinned installer version, with Bandit as the HTTP server. Every direct
  dependency is pinned to an exact version in `mix.exs`; `mix.lock` pins the
  rest.
- **A page that is pushed to.** `/counter` holds no state of its own. Clicking
  its button calls a context, which writes and broadcasts; the number changes
  only when the broadcast comes back. Three tests hold that apart from a local
  re-render, including one that increments from a different process entirely
  and asserts the mounted client saw it.
- **Authentication from `mix phx.gen.auth`** in its 1.8 shape: magic-link
  sign-in, a token table, sudo mode for changing an email or a password, and a
  scope assigned on every request. `pbkdf2_elixir` hashes passwords, so the
  project builds with no C toolchain. `/counter` is behind it, and the test
  proves both doors are shut — the ordinary HTTP request and the websocket
  mount that follows it.
- **Ecto migrations against a real Postgres**, from `postgres:18.6-alpine` in
  `compose.yaml` on a port Docker chooses. The recipe also applies them with
  the production configuration, which is what a deployment actually does.
- **A production configuration that refuses.** `DATABASE_URL`,
  `SECRET_KEY_BASE` and `PHX_HOST` have no defaults; a secret under 64 bytes,
  or equal to the development one, is refused by name. Six tests read
  `config/runtime.exs` the way a boot reads it, and the recipe also runs a
  production command with no secret and records the refusal.
- **A content security policy** on the browser pipeline, wide enough for a
  LiveView socket and nothing else, and Sobelow set to fail on a low-confidence
  finding — which is how the missing policy was found in the first place.
- **The gate in one command.** `mix precommit` runs compile with warnings as
  errors, the unused-lock check, `mix format --check-formatted`, Sobelow, the
  Elixir Security Advisories through `mix_audit`, and the suite. The generated
  `.github/workflows/ci.yml` runs the same list with every action pinned by
  commit and `contents: read`.

## Options

None. Postgres is the database, LiveView is the front end, and magic links are
the way in; changing any of those changes what the blueprint is for rather
than how it is configured.

## What it fits

- An application whose pages change while somebody is looking at them —
  dashboards, queues, chat, anything with a second person in it — where you
  would otherwise write an API, a client framework and the code that keeps
  them agreeing.
- A team that already knows Elixir, or is willing to learn it, and wants the
  concurrency model rather than the syntax.
- A first Phoenix project that has to be defensible: the security scan, the
  advisory check and the production refusals are wired in before the first
  feature, not after the first incident.

## What it is NOT for

- **A JSON API with no HTML.** Nothing here is worth carrying for that. There
  is no Phoenix API blueprint in the catalog yet; `go-http-service`,
  `fastapi-service` or `ts-http-service` are the closest things that exist.
- **A page that never changes after it is rendered.** A marketing site or a
  blog pays LiveView's cost — a websocket per visitor, a process per socket —
  and gets nothing for it. `astro-content-site` is built for that.
- **A team with no Elixir and a deadline.** The runtime is excellent and the
  language is not the hard part; the operational model is. `rails-web-app` and
  `django-web-app` reach the same shape of application through a stack most
  teams can already hire for.
- **Anything that needs to be styled today.** There is no CSS build here (see
  the trade-offs), so the generated markup renders unstyled until you add one.
- **A release you can `docker run`.** No Dockerfile, no release configuration.
  `mix phx.gen.release --docker` writes both, and this blueprint would be
  claiming something it never executed if it shipped them.

## How it differs from the other server-rendered web blueprints

|                    | `phoenix-liveview-app`                          | `rails-web-app`                                 | `django-web-app`          |
| ------------------ | ----------------------------------------------- | ----------------------------------------------- | ------------------------- |
| Language           | Elixir                                          | Ruby                                            | Python                    |
| Database           | Postgres in a container                         | SQLite                                          | Postgres or SQLite        |
| Updates after load | Pushed over a websocket, proven by a test       | Full requests and Turbo                         | Full requests             |
| Authentication     | Magic links, tokens, sudo mode (`phx.gen.auth`) | Password, sessions with a lifetime              | Password, Django's views  |
| Session expiry     | Token lifetimes from the generator              | An absolute 30-day maximum, enforced and purged | Django's default          |
| Background work    | None                                            | Solid Queue, with a recurring job               | None                      |
| Security gate      | Sobelow, `mix_audit`, CSP                       | Brakeman, bundler-audit                         | Django's `check --deploy` |
| Container          | Database only                                   | The application image is built and started      | Database only             |

The three answer the same question — a server-rendered application with users
— and the answer to _which_ is almost always the language the team already
writes. Pick this one when the pages change while somebody is watching them.

## Trade-offs made on your behalf

- **No Tailwind, no daisyUI, no heroicons.** The Phoenix 1.8 generator pulls
  the Tailwind binary and two asset packages from a source-hosting site rather
  than a package registry, and this catalog keeps recipe downloads on
  registries. `--no-tailwind` removes all three; esbuild, which is what
  actually bundles the LiveView client, comes from npm and stays. The cost is
  real: the application renders unstyled until you add
  `{:tailwind, "~> 0.5"}` yourself. The class names are all still in the
  markup, so that is one dependency and one command.
- **`pbkdf2_elixir` rather than argon2 or bcrypt.** Both of those are NIFs and
  need a C toolchain the recipe would then have to declare and CI would have
  to keep. PBKDF2 is acceptable under the OWASP Password Storage Cheat Sheet;
  argon2id is better, and switching is one dependency and one config line.
  With magic links as the default way in, most accounts never have a password
  at all.
- **A counter as the demonstration.** It is the smallest thing that can prove
  a server-pushed update reaches a client without inventing a domain nobody
  asked for. It is also the first thing to delete.
- **An `Agent` rather than a table.** The counter is process state, so it
  resets when the node restarts and the Ecto sandbox cannot roll it back —
  which is why its test is `async: false`. A durable version belongs in
  Postgres, broadcasting after the transaction commits, and `AGENTS.md` says
  so.
- **No Dockerfile and no release.** `mix phx.gen.release --docker` is one
  command away. Shipping an image the recipe never builds or starts would be a
  claim nobody has checked.
- **`force_ssl` lives in `config/prod.exs`.** Phoenix reads it at compile
  time, so the obvious place — `runtime.exs` — accepts it and ignores it. A
  test asserts it is in the file that works.

## The security posture you inherit

The generated authentication is good, and it is not finished. These are the
decisions it makes for you, so that none of them is a surprise on the day it
matters. Each one is measured against OWASP ASVS 5.0.

- **Your email provider is the authentication factor.** The only way in is a
  link sent by mail, so whoever controls the mailbox controls the account.
  ASVS **6.3.6** rules email out as an authentication mechanism at Level 3;
  below that it is a normal trade-off, and it is the same one every "email me
  a link" product makes. Add a second factor before anything Level 3 depends
  on this.
- **There is no rate limiting on the sign-in endpoint.** ASVS **6.1.1** and
  **6.3.1** (both Level 1) ask for anti-automation and for documentation of
  it; `phx.gen.auth` generates neither. The tokens have enough entropy that
  guessing one is not the risk — sending somebody a hundred sign-in emails
  is. Put a limiter in front of `POST /users/log-in` and the registration
  LiveView before you launch, and write down what it allows.
- **Sessions last 14 days, absolutely, with no inactivity timeout.** Magic
  links last 15 minutes and email-change links 7 days; all three are
  `phx.gen.auth` defaults, in `lib/liveview_app/accounts/user_token.ex`. ASVS
  **7.3.2** wants the absolute maximum chosen deliberately, **7.3.1** wants an
  inactivity timeout, and **7.1.1** wants both written down — this paragraph
  is that, and changing the numbers is changing three module attributes.
  Note that 15 minutes is longer than the 10 that ASVS **6.5.5** sets for an
  out-of-band request at Level 2.
- **The content security policy names the websocket schemes.** `default-src`
  is `'self'`, but `connect-src` also carries bare `ws:` and `wss:`, because
  `'self'` does not reliably cover a plain-`ws` socket on an http page. A bare
  scheme matches any host, so narrow it to your own origin once the deployment
  has a name. Nothing third-party can load to exploit it while `default-src`
  holds; this is depth, not the wall.
- **`mix.exs` pins the direct dependencies and `mix.lock` is generated.** Two
  people running this recipe six months apart get identical direct versions
  and whatever Hex resolves underneath them. Commit `mix.lock` on the first
  day; after that, `mix deps.get --check-locked` in CI makes the tree
  reproducible for everyone else.

## What CI cannot prove

- **That LiveView works in a browser.** `Phoenix.LiveViewTest` drives the
  socket in process; it never loads `app.js`, never opens a websocket, and
  never runs the client. The recipe bundles the JavaScript and checks it is
  there, and the production server is started and asked for two pages over
  HTTP, but no browser is involved. A CSP that is too strict for a real
  browser, or a broken bundle, would pass every check here.
- **That magic-link sign-in works end to end.** In test the mailer is
  `Swoosh.Adapters.Test` and in development it is a local mailbox. Nothing
  sends mail, so nothing proves that your provider will. Configure a real
  adapter before the first release: with magic links as the only way in, a
  mailer that does not work is an application nobody can enter.
- **That the pinned versions stay correct.** They were read from hex.pm on
  2026-09-30 and resolved against Elixir 1.20.4 on OTP 29. The weekly CI run
  is what notices when one is yanked or an advisory appears.
- **That a second browser sees the update.** The test proves a broadcast made
  in another _process_ reaches a mounted client, which is the same mechanism;
  it does not open two sockets.

## Cost of adoption

Twenty minutes on a machine that already has Elixir 1.20 on OTP 29, Git,
Docker and curl — most of it compiling dependencies twice, once for test and
once for production. Nothing is installed globally except Hex, rebar3 and the
`phx_new` archive, all from Hex itself. There is no account to create and no
paid service anywhere in it.
