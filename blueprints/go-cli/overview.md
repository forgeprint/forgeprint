# Go CLI

A command-line tool in Go on Cobra, with the commands tested through the real
parser and a binary that builds from a checkout.

**Generated, CI-tested, not manually verified.** The recipe executes on every
push like every other blueprint here. Nobody has built a real tool on it first,
which is what `tier: official` means in this catalog and why this is
`community`.

## What it fits

- A tool that has to ship as one file with no runtime. `go build` produces a
  binary somebody can copy to a server, which is the reason most command-line
  tools are written in Go at all.
- Anything in the Kubernetes and container world, where Cobra is the shape
  every neighbouring tool already has — `kubectl`, `docker`, `hugo`, `helm`.
- An internal tool that will be run in CI and in shell scripts, because exit
  codes and stderr are treated here as the interface rather than as an
  afterthought.
- Learning Cobra without inheriting the package-level state that
  `cobra-cli init` generates.

## What it is NOT for

- **Releasing.** No cross-compilation matrix, no `-ldflags` version stamping,
  no GoReleaser, no checksums or signatures. A release is a set of decisions,
  and doing it halfway here would be worse than not doing it.
- **Configuration files or environment binding.** No Viper. Flags and arguments
  only. Precedence between file, environment and flag is a real design question
  and it is not answered here.
- **Shell completion.** Cobra generates it; this does not install it.
- **Interactive tools.** No prompts, no spinners, no colour. A tool that asks
  questions only works when a human is watching.
- **A plugin system.** Subcommands as separate executables are a Cobra
  pattern and are not set up here.

## Pros

- **`NewRootCommand` is a constructor.** This is the whole argument of the
  blueprint and it is deliberately not what `cobra-cli init` produces. A
  package-level `rootCmd` keeps flag values in package-level variables, so the
  second test in a run sees the `--shout` the first one set — a flake that is
  genuinely hard to diagnose. Every test here builds a fresh tree and points it
  at a buffer.
- **The tests drive the command tree.** Argument count, flag spelling, the
  error. A test that called `greet.Greet` directly would pass while `--shout`
  was misspelled in the flag definition, which is the failure that happens.
- **`SilenceUsage` and `SilenceErrors` are on**, so a typo answers with one
  line instead of two screens of help text. Most Go tools get this wrong by
  leaving the defaults.
- **`go vet` runs in the recipe and in CI**, which catches the class of mistake
  the compiler allows.
- **Cobra is pinned** and `go.sum` is generated by the recipe, so the build is
  reproducible in a way most of this catalog's blueprints are not.
- **The recipe checks what a user sees**: runs the tool, reads the output,
  reads `--help` for the command name, asserts a bad invocation is non-zero.

## Cons

- **Nobody has run this in anger.** See the notice above.
- **Go's error handling is verbose by design**, and the test file shows it:
  three tests, each checking an error it does not expect. That is idiomatic Go
  and it is more lines than the same tests in the other two CLI blueprints.
- **The module path is a placeholder.** `example.com/example-cli` has to be
  changed before anything imports it, and changing it later touches every file.
- **One example command.** You are meant to delete `greet`. If you wanted a
  catalogue of patterns — nested groups, persistent flags, config precedence —
  this is not it.
- **Cobra is large for a small tool.** For three flags, the standard library's
  `flag` package is enough and has no dependencies. Cobra earns its place at
  the second subcommand, not the first.

## Compared with the alternatives here

- **`node-cli`** and **`python-cli`** — the same three layers, in TypeScript on
  Commander and in Python on Typer. Pick by what the surrounding repository
  already is. The one real difference is distribution: Go gives you a binary
  with no runtime, and the other two need Node or Python on the machine.
