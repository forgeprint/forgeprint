# Angular App

An Angular 22 single-page application in TypeScript: standalone components,
zoneless change detection, signals for state, a lazily loaded feature behind a
functional route guard, one HTTP interceptor every request goes through, and a
production build per locale that fails when the initial bundle passes its
budget or a message has no translation. Static files out; no server in it.

**Generated, CI-tested, not manually verified.** The recipe executes on every
push like every other blueprint here. Nobody has built a real application on
it first, which is what `tier: official` means in this catalog and why this is
`community`.

## What you get

- Angular 22.2 generated by `ng new` from a pinned CLI, then every dependency
  pinned exactly: standalone, zoneless (no `zone.js` installed), Tailwind 4,
  TypeScript 6 with `strict`, `noUncheckedIndexedAccess` and `strictTemplates`.
- `src/app/core/api.ts`: an `API_BASE_URL` token (default `/api`, same origin)
  and a functional `HttpInterceptorFn` that prefixes it, adds a 10-second
  deadline, and refuses absolute URLs and `..` in any spelling before a
  request is sent.
- A `notes` feature loaded with `loadChildren`: a store of signals provided on
  the feature's route, responses checked by a parser before they are typed, a
  page that lists and posts notes, and a `CanDeactivateFn` that asks before
  discarding an unsaved draft.
- Built-in i18n with `@angular/localize`: custom message IDs, `$localize` in
  TypeScript, an extraction target, an en-GB translation, and a build that
  refuses a missing translation.
- Vitest with jsdom through the Angular CLI's own `ng test` — what `ng new`
  now chooses by default, so no Karma and no browser download. 21 tests: the
  interceptor's refusals and deadline, the store against
  `HttpTestingController`, the guard in an injection context, and the real
  routes through `RouterTestingHarness`.
- angular-eslint 22.5 on ESLint 10: the recommended and template accessibility
  rules, plus four project rules — OnPush everywhere, an i18n ID on every text
  node, no `fetch`, and no `HttpClient` in a component.
- A CI workflow with pinned actions that runs lint, type-check, tests,
  extraction and the localized production build from the lock file.

## Options

None. The obvious candidates — Karma instead of Vitest, SCSS instead of
Tailwind, server rendering — each change enough files that they would be
different blueprints rather than switches.

## What it fits

- A front end for an API that already exists: an admin tool, a dashboard, a
  line-of-business application behind a sign-in.
- A team that wants the framework to decide the structure: dependency
  injection, a router with guards and lazy loading, an HTTP client with
  interceptors and a testing backend, and a CLI that generates code in the
  house shape. Most of what a React SPA assembles from libraries is here in
  one version-locked release.
- An application that must ship in more than one language and wants
  translations compiled into the bundle rather than loaded at runtime.
- Somebody joining the many existing Angular codebases, who wants a new one
  built the way Angular itself now recommends — standalone, zoneless, signals —
  rather than the way most of those codebases were started.

## What it is NOT for

- **Anything that needs a server.** No server rendering, no prerendering, no
  API routes, no database. Use **`nextjs-fullstack-app`**.
- **Pages search engines must index**, or content that changes rarely. The
  first response is an empty `<app-root>`. Use **`astro-content-site`**.
- **A React team.** The concepts here — decorators, DI, RxJS at the HTTP layer,
  Angular's template syntax — are a real learning cost. **`vite-react-spa`** is
  the same job, a client-only SPA in front of somebody else's API, built from
  React, React Router and Vite.
- **The API itself.** Use `ts-http-service`, `fastapi-service`,
  `go-http-service` or `dotnet-web-api` for that half.
- **Users and sign-in, forms, end-to-end tests.** None is here. The one guard
  protects a draft from being lost, not a page from being seen.
- **Security headers and error reporting.** No Content-Security-Policy, HSTS or
  frame policy is set: those are response headers, and they belong to whatever
  serves the files. No error-reporting service either; uncaught errors reach
  Angular's `ErrorHandler`, which logs to the console.
- **More i18n than message translation.** What is set up and proved is
  compile-time translation of marked text and a `lang` per locale. There are no
  ICU plural or select messages, no right-to-left layout, and no switching
  language at runtime.

## Trade-offs made on your behalf

- **Vitest in jsdom, not Karma in Chrome.** Vitest is the CLI's default for
  new projects, and in jsdom it runs without downloading a browser. The price is that jsdom
  does no layout: focus order, contrast and anything visual go untested.
  Angular's experimental Vitest browser mode, or Playwright, is the next step
  when those matter — both download a browser from outside the npm registry.
- **The CLI's builders, not a Vite config.** `@angular/build` uses Vite and
  esbuild underneath, but the configuration is `angular.json`. You give up
  direct access to the bundler for a toolchain the Angular team upgrades with
  `ng update`.
- **Signals for state, RxJS only at the HTTP edge.** `HttpClient` returns
  observables and the store turns them into signals once. No NgRx. Not
  `httpResource` either, though it is stable since Angular 22 and would make
  `load()` shorter: the same class also posts, and one owner of the list is
  simpler than a resource with a mutation beside it. Swapping reads to
  `httpResource` is a fair change once a feature only reads.
- **Compile-time i18n, not a runtime library.** Translations are inlined by
  the build: no extra request, no flash of untranslated text, and a missing
  translation fails the build. The cost is one build and one output folder per
  locale, and a host that routes `/en-GB/` and `/en-US/` to their folders.
- **British English as the second locale.** The catalog is English-only, so the
  proof of a translated build is `Organize` becoming `Organise`. The
  mechanism does not care which language the targets are in.
- **A same-origin API by default.** `/api`, expected behind the same host as
  the app, so there is no CORS policy and no API URL in the bundle. An API
  elsewhere is one provider in `app.config.ts` and a CORS decision on that API.
- **Custom message IDs.** `@@notesHeading` instead of Angular's content hash, so
  fixing a typo in the English does not orphan every translation of it.

## Pros

- **The framework provides what a React SPA has to pick**: router, DI, HTTP
  client with interceptors and a test backend, i18n, a build with budgets — one
  version, upgraded together by `ng update`.
- **Current Angular, not the Angular in most tutorials.** No NgModules, no
  zone.js, signals instead of `BehaviorSubject` for state.
- **The claims are tested.** Removing the `..` check or the guard from the
  route fails a test; both were tried.
- **The build refuses the two regressions that are easy to miss**: a feature
  imported eagerly past the budget, and a message nobody translated.
- **No browser download anywhere in the toolchain.**

## Cons

- **Nobody has run this in anger.** See the notice above.
- **More concepts than a React SPA** before the first feature: decorators,
  injection contexts, the template compiler, RxJS.
- **A larger initial bundle.** About 270 kB raw, 77 kB compressed, for two
  small pages — mostly the framework.
- **One build per locale**, and a host that needs a fallback to `index.html`
  in each locale's folder, or reloading a deep link is a 404.
- **Node.js 22.22.3 or newer.** Angular 22 and jsdom both declare it.

## Cost of adoption

About five minutes on a warm npm cache: `ng new`, one install of roughly 550
packages, then type-check, lint, tests, extraction and two production builds
(one proving the budget refuses). Needs Node.js 22.22.3 or newer and npm. No
Docker, no database, no browser download, no account anywhere.

## Compared with the alternatives here

- **`vite-react-spa`** — the same architecture: a static, client-only app in
  front of an API somebody else owns. Choose it for React and for a smaller
  set of concepts; choose this one for a framework that ships the router, DI,
  HTTP layer, i18n and generators itself and upgrades them together.
- **`nextjs-fullstack-app`** — React with a server that renders pages and owns
  a Postgres database. Choose it when the application owns its data.
- **`astro-content-site`** — static HTML at build time with no JavaScript by
  default. Choose it for content; choose this one for an application.
