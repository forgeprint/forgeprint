# TanStack Start App — agent context

A TanStack Start application: React, TanStack Router's file-based routes, server
functions, and a Nitro build that runs as a Node server. Read this before adding
a route, a server function, or anything that touches the session.

> This blueprint was generated from the catalog's demand research and its
> recipe runs in CI, but nobody has reviewed the steps by hand. Treat it as a
> starting point that works, not as a design somebody has shipped.

## The shape

```
src/routes/                 one file per route; the file name is the URL
src/routes/__root.tsx       the HTML document every page renders inside
src/routes/_authed.tsx      the guard: a pathless layout with a beforeLoad
src/routes/_authed/         every route that needs a signed-in user
src/routeTree.gen.ts        generated by `dev` and `build`; committed, never edited
src/server/                 code that only runs on the server
src/server/auth.ts          the server functions: current user, sign in, sign out
src/server/config.ts        the one place environment variables are read
src/server/session.ts       the sealed session cookie
src/server/password.ts      scrypt hashing and the AUTH_USER format
src/server/rate-limit.ts    the per-address limit on sign-in attempts
src/auth/                   shapes and the guard, shared by browser and server
src/start.ts                request middleware: CSRF protection for server functions
src/server.ts               the server entry: config check at load, security headers
e2e/                        requests against the built server in .output/
```

## Where the server boundary is

In this framework a single file can hold code for both sides, and the build
decides what reaches the browser. That is convenient and it is the main way to
leak something. The rules:

- **Anything that needs a secret is inside a `createServerFn` handler, or in a
  module under `src/server/` that only a handler imports.** The build replaces a
  handler with an HTTP call in the browser bundle; code outside a handler is
  bundled as written. A secret read at module scope in a route file is shipped
  to every visitor.
- **`src/auth/` and `src/notes.ts` must not import from `src/server/`.** They
  are imported by route components and so end up in the browser.
- **The recipe checks the built client bundle for `scrypt`, `SESSION_SECRET`
  and the development secret.** If that check fails after a change, something
  server-only crossed the line; move it, do not relax the check.

## Every server function is a public endpoint

`createServerFn` creates a URL anybody can call with any payload, whether or not
a page of yours ever calls it that way.

- **Validate input in `.validator(...)`**, with a Zod schema from `src/auth/`
  or next to the function. Refuse a bad request with
  `throw new Response(..., { status: 400 })`: a thrown `Error` becomes a 500,
  which says the server failed when the caller did.
- **Authorize inside the handler.** A route guard protects a page; it does not
  protect the server functions the page calls. A function that returns or
  changes a user's data calls `getCurrentUser()` itself.
- **CSRF protection lives in `src/start.ts`.** It refuses a server-function call
  whose `Sec-Fetch-Site`, `Origin` or `Referer` says another site, or that has
  none of them. Do not remove it, and do not add a `filter` that skips a
  function that changes state. The e2e suite proves the 403.

## Authentication rules that are not style preferences

**The session is a sealed cookie.** `useSession` from Start encrypts and signs
it with `SESSION_SECRET`; the browser holds it but cannot read or change it. It
is `HttpOnly`, `SameSite=Lax`, `Secure` in production, and expires after eight
hours, enforced when the cookie is unsealed as well as by the browser. A
tampered cookie is no session; the e2e suite proves that. The session lives
only in the cookie: signing out deletes the browser's copy but cannot revoke one
somebody else holds, and rotating `SESSION_SECRET` is the only way to end every
session at once. If you need revocation, keep a session id on the server.

**Configuration is read only in `src/server/config.ts`.** `SESSION_SECRET` must
be at least 32 characters; `AUTH_USER` is `username:scrypt:<salt>:<hash>`.
Development falls back to published, obviously fake values. The production
build refuses both the missing and the published values, and `src/server.ts`
checks at load time so a misconfigured server logs `Refusing to serve: ...` and
answers 503 to everything, rather than serving public pages and failing only at
sign-in.

**`import.meta.env.PROD` decides production, not `NODE_ENV`.** Vite replaces it
at build time, so the production build cannot be talked into development
behaviour by an environment variable.

**Sign-in clears the session before writing the user into it.** A session
identifier planted before sign-in must not become an authenticated one.

**A redirect target after sign-in is a path on this site or nothing.**
`safeRedirect` refuses `//host` and `/\host`, which browsers read as another
site. The same schema reads `?redirect=` on the sign-in page.

**One message for a wrong username and a wrong password, and scrypt runs either
way**, so neither the text nor the timing says which was wrong.

**Sign-in is rate-limited before the password is checked**: ten attempts per
client address per fifteen minutes, then 429 with `Retry-After`. The check comes
first because scrypt costs the server as much as it costs the guesser. The count
lives in process memory (`src/server/rate-limit.ts`), so several instances or a
restart each start from zero, and behind a proxy every client shares the
proxy's address; move the limit to the proxy or a shared store before either
matters. Do not read `X-Forwarded-For` unless a proxy you control sets it.

**Security headers are set in `src/server.ts`** on every rendered response: a
policy that forbids framing, `<base>` and off-site form targets, plus
`nosniff` and a referrer policy. It does not restrict scripts; that needs a
nonce on every inline script server rendering writes.

**There is exactly one account.** It comes from `AUTH_USER`. To support more,
replace `readAuthUser` and `verifyCredentials` with a lookup in a real store;
keep the constant-work comparison and the single error message.

## Routes, params and search

- **A search parameter is declared with `validateSearch`**, using a Zod schema
  with `.default()` and `.catch()`, so a missing or bad value becomes a sensible
  value instead of an error page. `/notes?page=abc` redirects to `?page=1`.
- **A typed path parameter is parsed in `params.parse`.** When the segment is
  not valid, throw `notFound()` there: a thrown validation error is a 500.
- **Data is loaded in `loader`, keyed by `loaderDeps`** for anything read from
  search params. A loader that reads a store calls a server function; the
  in-memory `src/notes.ts` is example data to delete.
- **`Link` and `redirect` are type-checked against the route tree.** If one
  stops compiling after a rename, the compiler found a broken link; fix the
  call, do not cast it.
- **`src/routeTree.gen.ts` is regenerated by `npm run dev` and `npm run build`.**
  Run one of them after adding or renaming a route file, then commit the
  regenerated file. The type check and the unit tests import it.

## Commands

```bash
npm run dev          # development server on port 3000, development secret
npm run build        # production build in .output/, regenerates the route tree
npm start            # the built server; reads PORT and HOST
npm run typecheck
npm test             # unit tests: config refusals, hashing, schemas, the guard
npm run test:e2e     # starts the built server and makes real requests to it
printf '%s' "$PASSWORD" | npm run --silent hash-password -- <username>
```

The TanStack CLI (`npx @tanstack/cli ...`) sends usage telemetry by default.
Run it with `TANSTACK_CLI_TELEMETRY_DISABLED=1`, and re-pin `package.json`
afterwards if it adds anything: it writes `latest` for TanStack packages.

## When you are asked to add a protected page

1. Create `src/routes/_authed/<name>.tsx` with `createFileRoute('/_authed/<name>')`.
   The URL is `/<name>`; the guard is inherited, not repeated.
2. Read the user with `Route.useRouteContext().user`.
3. If the page loads data, write a server function that calls
   `getCurrentUser()` itself and refuses when it returns null.
4. Run `npm run build` to regenerate the route tree, then `npm run typecheck`.
5. Add an e2e case: the page redirects without a cookie and answers 200 with one.

## What this does not do

- **Registration, password reset, more than one account, roles.** One account
  from the environment is the whole user model.
- **A shared rate limit.** The sign-in limit is per process; see above.
- **A database.** Nothing here persists anything.
- **A script policy or HSTS.** The Content-Security-Policy restricts framing,
  `<base>`, form targets and plugins, not scripts; HSTS belongs at the proxy
  that terminates TLS.
