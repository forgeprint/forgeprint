# Tauri Desktop App

A desktop app on Tauri 2 for Windows, Linux and macOS: the logic in a plain
Rust crate that builds and tests without a webview, a Tauri shell that exposes
it as one IPC command behind a least-privilege capability, a strict content
security policy, and a Vite + TypeScript frontend tested with Vitest.

**Generated, CI-tested, not manually verified.** The recipe executes on every
push like every other blueprint here, but it does **not** compile the desktop
shell — read "What CI can prove" before relying on it. Nobody has shipped an
app on it, which is what `tier: official` would mean and why this is
`community`.

## What you get

- A Cargo workspace with `rust-version = "1.85"`, the 2024 edition,
  `unsafe_code` forbidden and a committed `Cargo.lock`:
  - `app-core/` — the logic, with no dependencies at all. `greet` validates
    its input (trimmed, not empty, at most 64 characters, no control
    characters) and has six unit tests.
  - `src-tauri/` — the shell on **tauri 2.11.6** and **tauri-build 2.6.3**,
    pinned with `=`. One `#[tauri::command]` wraps `app_core::greet`. It is
    outside the workspace's `default-members`, so a bare `cargo test` never
    needs a webview.
- **Access control on the app's own command.** `build.rs` lists `greet` in
  Tauri's app manifest, which turns on the ACL for it, and the one capability
  file grants `allow-greet` to the `main` window and nothing else — not
  `core:default`, no plugin, no remote origin.
- **A strict CSP** in `tauri.conf.json`: `default-src 'self'`, IPC in
  `connect-src`, `object-src`, `base-uri`, `form-action` and `frame-ancestors`
  all `'none'`; `freezePrototype` on; `withGlobalTauri` off. No shell, fs,
  http or opener plugin.
- **Tests that hold the surface still.** `src/tauri-policy.test.ts` fails when
  the capability grants more than the app's own commands, when `build.rs` and
  `generate_handler!` disagree, when the CSP changes, when a window or a
  capability file is added unpinned, or when any Tauri plugin crate or package
  appears. `src/commands.test.ts` pins the command name and argument names the
  frontend sends.
- **Shell tests through the real ACL.** `cargo test -p app` builds the app on
  Tauri's mock runtime with the real configuration and capability, calls
  `greet` from the main window, gets the refusal message for a blank name, and
  is refused `plugin:app|version`, which `core:default` would have allowed.
- A frontend on **Vite 8.3.1**, **TypeScript 6.0.3** (strict) and **Vitest
  5.0.1**, with `@tauri-apps/api` 2.11.1 and `@tauri-apps/cli` 2.11.5, and a
  committed `package-lock.json`.
- Icons generated by the pinned CLI from a placeholder the recipe draws, so
  the shell's build script finds `icon.ico` on Windows.
- A CI workflow, actions pinned by commit SHA, `contents: read`: fmt, clippy
  and tests for the core crate, the frontend's type check, tests and build; an
  MSRV job on Rust 1.85.0; the shell built on Linux, Windows and macOS with
  `tauri build --no-bundle`, with clippy and its tests on Linux.

## What CI can prove, and what it cannot

This catalog's recipe test proves that the core crate formats, passes clippy
with warnings as errors and passes its tests; that the frontend type-checks,
passes its tests and builds with no inline script; that the whole workspace,
the shell included, resolves into a lock file whose every crate declares Rust
1.85 or lower; that the shell's Rust is formatted; that `tauri.conf.json`
passes the Tauri CLI's own schema validation; and that the capability, the
CSP and the plugin list are what the tests say.

It **cannot** prove any of these, and this blueprint does not pretend to:

- **That the shell compiles.** On Linux, the `tauri` crate links against
  WebKitGTK 4.1, libsoup 3 and GTK 3, which come from the system package
  manager and need administrator rights to install. The runner the catalog
  tests on does not have them, and a recipe here may not use `sudo`. The
  generated CI installs them in a pinned container, where the job is root,
  and builds the shell there, on Windows and on macOS — so the proof arrives
  on the **first push of the generated project**, not before.
- **That a window opens.** Nothing here starts the app. The shell's tests run
  on Tauri's mock runtime, which exercises the IPC and the access control but
  not a webview.
- **That the CSP is right for WebView2.** `connect-src ipc: ipc.localhost`
  follows Tauri's documented policy, with the Windows IPC origin written
  without its scheme (CSP then matches it against the page's `http` scheme,
  as Tauri serves it). It was reasoned from the CSP specification, not
  observed on Windows. If IPC falls back to slower `postMessage` there, the
  console says so and this is the line to look at.

For what it is worth as evidence: the files this recipe writes were built in
a `rust:1.98.1-bookworm` container with the three libraries the generated CI
installs — `cargo clippy -p app -D warnings`, `cargo test -p app` and
`tauri build --no-bundle` — on 2026-09-25, by the tool that drafted the
blueprint. That is recorded in the CHANGELOG as local evidence, not as CI.

### The one step that is yours

Install the webview's system libraries once, before the first
`npm run tauri dev`. On Debian and Ubuntu that is `libwebkit2gtk-4.1-dev`,
`libxdo-dev` and `libssl-dev` (with `build-essential`); other distributions,
and Windows and macOS, are listed on Tauri's
[prerequisites page](https://v2.tauri.app/start/prerequisites/). Windows 10
and 11 ship WebView2; macOS needs Xcode's command-line tools.

## What it fits

- A desktop app for Windows, Linux and macOS where the interface is web
  technology and the work is Rust: file processing, local data, device or
  system access that a browser does not allow.
- Somebody who knows Rust or TypeScript and wants the other side kept small
  and tested, with the boundary between them written down.
- A tool that must be small to download and start fast: the app uses the
  operating system's webview instead of shipping a browser.
- A team that wants the security surface — what the page can call — to be a
  reviewed, tested file rather than a default.

## What it is NOT for

- **Something that could be a web app.** If it needs no file system, no
  local process and no offline install, a desktop app is a distribution and
  update problem you do not need. Pick **`vite-react-spa`** for a client-only
  app, or **`nextjs-fullstack-app`** when it needs a server.
- **Identical rendering everywhere.** Tauri uses WebView2 (Chromium) on
  Windows and WebKit on macOS and Linux, and WebKitGTK trails Safari. A layout
  or API that works in one can fail in another. If pixel-identical Chromium on
  every platform matters more than size, Electron is the tool; this catalog
  does not have an Electron blueprint (the expansion plan chose Tauri for its
  smaller, CI-friendly toolchain).
- **Mobile.** Tauri 2 targets iOS and Android too, but nothing here does:
  no mobile targets, no `lib` crate types for them, and `platforms` does not
  list them.
- **Shipping signed installers today.** Code signing, macOS notarization,
  installers built in CI, the auto-updater and its signing key are all left
  out. They need certificates, accounts and secrets this catalog will not
  hold. `npm run tauri build` produces unsigned installers locally; Windows
  SmartScreen and macOS Gatekeeper warn on them.
- **A command-line tool.** Pick **`rust-cli`** or **`go-cli`**.

## Trade-offs made on your behalf

- **Vanilla TypeScript, no UI framework.** The app is one form; React, Vue or
  Svelte would be the largest dependency in it. Add one with its Vite plugin
  when the interface earns it — nothing in the shell changes.
- **The shell is not in `default-members`.** `cargo test` and `cargo clippy`
  at the root cover the core crate only, so they run anywhere. The price: the
  shell needs `-p app` to be built or tested, and a contributor who never runs
  that never compiles it. CI runs it on every push.
- **An app manifest for one command.** Without `build.rs` listing `greet`,
  Tauri lets every window call every app command, and the capability would
  not matter for it. Listing it means every new command takes a permission
  line — four edits instead of two — which is the point.
- **No `core:default`.** Tauri's own templates grant it. It allows the page
  to call window, event, path, app, image, menu, resources, tray and webview
  commands that this page does not use.
- **The ACL is checked by tests, not by a schema alone.** Tauri refuses an
  unknown permission at build time; nothing refuses a known one that is too
  broad. `src/tauri-policy.test.ts` does, by listing what is allowed.
- **Exact pins, and two lock files.** `=2.11.6` means `cargo update` cannot
  move Tauri; a security release has to be noticed and applied. There is no
  advisory check in the generated CI (`cargo audit` and `npm audit` fetch
  their databases from outside the registries this catalog allows); add one.
- **Container for the Linux shell job.** `apt-get` needs root, and the
  runner's user is not root. A pinned `rust` image is root without `sudo`
  anywhere in the workflow. The apt packages themselves are not version
  pinned: Debian bookworm's are what they are on the day.
- **Rust 1.85 floor, 1.98.1 in CI.** Every crate in the lock file declared
  1.85 or lower on 2026-09-25; the MSRV job builds only the core crate on
  1.85, because the shell would need the system libraries there too.
- **No `rust-toolchain.toml`**, as in `rust-cli`: rustup would download a
  toolchain in the middle of the recipe from a host that is not a package
  registry.

## Pros

- The security surface is small and pinned: one command, one capability, one
  window, no plugin, a strict CSP, each held by a test that fails loudly.
- The logic is plain Rust with no framework types, so most of the app's tests
  run in seconds on any machine and in any CI.
- The app is small: no bundled browser, and a Rust binary.
- The generated CI builds the shell on all three platforms from the first
  push.

## Cons

- The catalog's own CI never compiles the shell; see above.
- Three webviews to test against, and WebKitGTK on Linux is the one that
  surprises.
- Every command costs four edits. The tests keep them consistent; they do not
  make them fewer.
- The Linux system libraries are an install step outside the recipe, and a
  first-time contributor on Linux hits it before anything else.
- macOS and Windows CI minutes bill at a multiple of Linux on a private
  repository.

## Cost of adoption

About two minutes for the recipe on a warm cache: `npm install` fetches the
frontend and the Tauri CLI, and `cargo generate-lockfile` reads the index for
roughly four hundred crates without building them. The first shell build on a
developer machine takes several minutes. Tools: Rust 1.85+ with rustfmt and
clippy, Node.js 22.12+ with npm, and — to build the shell — the webview
libraries above.

## Compared with the alternatives here

- **`vite-react-spa`** — the same frontend tooling for a browser app. No Rust,
  no installer, no system access; choose it when the browser is enough.
- **`rust-cli`** — Rust without a window. Choose it when a terminal is the
  interface.
- **`godot-game`** — the other desktop-shaped blueprint; a game engine, not an
  app shell.
